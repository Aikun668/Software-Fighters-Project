# 当前对话系统的问题说明与改造原则

> **用途**
>
> 这是“对话底座救援”的前置诊断文件，不是实现计划，也不是需求清单。
>
> 任何人或 Agent 在修改聊天、路由、画像、上下文、Prompt、知识库、SSE 之前，必须先读它。它要解释的是：系统为什么会答得离谱，为什么不能继续靠增加意图、增加 Agent 或多塞上下文来解决，以及这轮改造必须坚持什么原则。

## 0. 一句话判断

当前系统不是“模型太差”，也不是“Agent 数量还不够”。

它更像一个：

> **能力很多，但普通对话主链路没有收敛的原型系统。**

系统已经具备聊天接口、SSE、历史会话、画像、Router、TutorAgent、多个生成能力和安全检查等基础设施；但它没有先保证最常见的事情——用户随便问一句正常的学习问题时，系统能稳定听懂、稳定回答、稳定结束。

因此目前的风险不是“功能少”，而是：

> **每增加一个能力、一个 Intent、一个上下文来源，都可能干扰原本最该简单的聊天。**

本轮优先级必须从 Agent-first 改成 Conversation-first。

---

## 1. 当前用户真正需要的是什么

在大多数输入里，用户并不是在表达一个精确的“业务标签”。

用户说：

- 我感觉 TCP 一直没搞懂。
- 这个再讲简单一点。
- 为什么？
- 你刚才那个例子我没听明白。
- 那线程呢？
- 不对，我说的是虚拟内存。

这些话在产品层的真实含义是：

> **请结合正在聊的内容，像一个可靠的学习助手一样继续回答。**

用户并不关心系统内部把它叫 tutor_question、diagnose、learning_path、code_example 还是 knowledge_graph。

只有少数请求是真的在要求系统执行特殊能力，例如：

- 帮我出 5 道题。
- 画一张流程图。
- 给我制定 7 天学习计划。
- 帮我找几个学习资源。

所以系统的正确默认假设是：

> **用户是在聊天和学习问答。除非证据非常明确，否则不要把他送进复杂能力流程。**

---

## 2. 问题一：前端存在两条聊天链路，导致整个调试结论不可信

### 现象

当前已知存在两套聊天相关实现：

1. frontend/src/api/chat.ts：真实请求后端、解析 SSE。
2. frontend/src/views/AITutor.vue：通过 simulateStreamResponse、预设问题和默认回答，在本地模拟流式输出。

这意味着页面上出现的一段回答，可能根本没有来自后端。

### 为什么危险

如果前端优先走模拟路径，那么会发生下面几种误判：

- 后端已经修好，但页面仍展示旧的本地答案，开发者误以为后端没修好。
- 后端实际报错，但页面用默认回答掩盖了错误，开发者误以为系统正常。
- 测试一个新 Prompt、一个 Router 或一个 Agent 时，用户看到的结果却来自预设文案。
- SSE 显示“像在流式输出”，但真实网络、异常和 done 事件根本没有被验证。

这种状态下，任何“回答质量评估”都是污染过的。

### 必须达成的原则

> 页面只能通过真实聊天客户端调用 POST /internal/api/chat。

本地 Mock 如果确实要保留，只能是显式的开发开关，默认关闭；不能成为 AITutor.vue 的兜底回答来源。

后端失败时，页面应该诚实显示失败并允许重试，而不是假装系统回答了。

## 3. 问题二：把自然语言理解过早变成了关键词分类

### 当前倾向

auto 模式主要依据 IntentRegistry 的关键词评分与置信度，把输入匹配到 tutor_question、solve_problem、diagnose、learning_path、resource_gen、exercise_gen、visualize、profile_building、flashcard_gen、code_example、knowledge_graph 等 Intent。

多个意图还会生成多个 CenterTask 和 ExecutionPlan。

### 根本问题

自然语言不是表单。

同一句话常常同时有多个可能解释，但用户只期待一个自然、连贯的回答。例如：

> 我最近在学操作系统，但是进程和线程还是有点乱，你能举个真实例子讲一下吗？

它可能带有“答疑”“诊断”“举例”“学习路径”甚至“代码示例”的影子，但它本质上还是普通问答。

如果 Router 必须先把它塞进一个或多个标签，就会出现两类错误：

1. **误路由**：看到“例子”就进入 code_example；看到“不会”就进入 diagnose；看到“图”就进入 visualization。
2. **过度编排**：一个本来 3 秒可回答的问题，被拆成多个 CenterTask、多个 Agent、多个结果再聚合，反而丢失重点、变慢、变怪。

这里不是 Intent 系统完全没用，而是它被放在了错误的位置。

### 正确理解

Intent 不应再承担“决定所有对话去哪里”的责任。

它应降级为一个保守的 CapabilityGate，只判断一件事：

> **用户是否明确要求一个专用产物或专用工作流？**

一级判断只保留：

- NORMAL_CHAT
- PLAN
- RESOURCE
- EXERCISE
- VISUALIZATION

其中 NORMAL_CHAT 是默认，证据不足时必须选它。

### 禁止的错误做法

- 不能因为出现“知识图谱”四个字，就自动生成知识图谱。
- 不能因为用户说“我不会”，就自动进入能力诊断。
- 不能因为用户说“举个例子”，就自动调用代码生成。
- 不能因为一句话命中了两个关键词，就立刻创建多个任务。

> **分类可以是辅助证据，但不能压过正常人对一句话的常识理解。**

## 4. 问题三：画像每轮全量注入，会污染当前回答

### 当前可能做法

TutorAgent 可能将学生画像、历史、知识库与当前消息一起放进 Prompt。画像里可能包含学习水平、偏好、薄弱项、目标、历史结论等信息。

画像本身不是问题；**无差别全量注入**才是问题。

### 为什么会让回答变差

模型会把上下文中出现的内容都当成当前回答的强信号。全量画像会带来至少五类风险：

1. **无关干扰**
   用户问“TCP 为什么三次握手”，但 Prompt 里同时塞了长期目标、其他课程、练习记录、兴趣和旧问题。模型的注意力被稀释，回答变长、变散、甚至跑题。

2. **过度个性化**
   模型会为了“利用画像”而强行提及用户过去的目标、偏好或经历，哪怕它和当前问题无关。用户会感觉系统在硬套人设。

3. **陈旧事实污染**
   画像中的“薄弱点”“学习阶段”“偏好”可能已经过期，或者只是一次对话里的暂时结论。模型会把它当成稳定事实，导致错误地降低、抬高或扭曲解释难度。

4. **画像被当作真相**
   画像往往是系统推断出来的，不是用户每次明确确认的事实。把推断写得像硬事实，会放大系统之前的误判。

5. **提示词竞争**
   Prompt 越长，真正最重要的当前问题越容易被稀释。更多信息不等于更强，尤其对于一次简单解释。

### 正确原则

画像不是“每轮必传的背景档案”，而是一个按需选择的工具。

只有当某个画像字段能实际改变本轮回答时，才允许注入。例如：

| 当前问题 | 可以注入 | 不应注入 |
|---|---|---|
| 解释傅里叶变换 | 数学基础一般；偏好先直观再公式 | 去年练过的英语词汇；长期职业目标 |
| 给一周学习计划 | 本周可用时间；当前课程；已确认薄弱点 | 宠物、无关项目经历 |
| TCP 三次握手为什么这样设计 | 当前在学网络；偏好举例解释 | 完整人生目标；所有历史练习 |

系统需要 ProfileSelector。它的目标不是“尽可能用上画像”，而是：

> **只保留会改变本轮回答质量的最少画像信息。**

如果拿不准，就不注入。

## 5. 问题四：历史消息不是越多越好，粗暴截取会让对话越聊越乱

### 两种相反但同样危险的做法

1. 全量历史都塞进去：太长、噪声多、旧话题和旧结论会干扰当前问题。
2. 简单 messages[-10:]：看似节省 Token，但可能切断完整的问答对、遗漏“不是，我刚才说错了”这类关键纠正。

两者都会让模型错误理解“我们现在在谈什么”。

### 正确的历史管理方式

对话上下文应是：

> 最近完整轮次 + 早期摘要 + 当前消息。

其中：

- 最近轮次保留原文，用于承接“那这个呢”“为什么”“再讲简单点”。
- 更早内容压缩为摘要，只保留已确认主题、已解决点、当前卡点和明确偏好。
- 当前用户消息优先级最高，尤其是纠正语句。

例如：

历史摘要：

> 用户已理解 IP 与 MAC 的区别，目前在学习 TCP 建立连接，偏好用生活例子解释。

最近对话：

> 用户：TCP 为什么需要三次握手？  
> 助手：……  
> 用户：不是，我刚才想问的是挥手。

当前问题必须覆盖摘要中的旧主题。

### 必须避免

- 不能将旧摘要当作比当前输入更可靠的事实。
- 不能截断半个 user/assistant 轮次。
- 不能把所有历史都当作同等重要。
- 不能因为有历史，就忽略用户正在纠正或换题。

## 6. 问题五：裸 API 不是产品级聊天系统

### 需要先澄清的事实

直接调用第三方模型 API 并不等于“模型坏了”或“模型在故意胡说”。

模型 API 本质上是一个概率生成器。它只会根据它收到的系统指令、上下文、工具结果和当前消息，生成一个看起来合理的下一个回答。

如果系统给它的输入有噪声、冲突、陈旧信息或错误路由，它依然会努力把这些东西组织成一句看起来连贯的话。结果就可能显得非常自信、非常完整、但并不贴合用户问题。

这就是“裸 API 乱奔”的真正含义：

> **不是 API 没能力回答，而是产品没有给它足够稳定、干净、可控的回答条件。**

### 最常见的失控来源

- System Prompt 同时要求聊天、规划、诊断、资源生成、可视化，目标互相竞争。
- 历史、画像、RAG 内容一股脑塞入。
- Router 已经误判，模型被要求完成错误任务。
- 知识库检索结果不相关，但被强行要求参考。
- 模型返回异常、截断或重复后，系统直接送到用户面前。
- 没有对同一组问题做回归测试，只凭“这次好像还行”判断。

### 正确的产品认知

最终回答质量大致受以下因素共同限制：

> 模型能力 × 路由正确性 × 上下文相关性 × Prompt 清晰度 × 检索证据质量 × 输出约束 × 异常处理 × 评测反馈

任何一项明显变差，用户都会觉得“模型怎么这么离谱”。

因此，当前优先任务不是继续换模型，而是先让输入和流程稳定。一个清晰的较普通模型，通常会比一个被错误上下文淹没的强模型更可靠。

## 7. 问题六：复杂的多 Agent 编排不应占据最常见路径

现有结构可能是：

用户输入  
→ Intent 识别  
→ RouterAgent  
→ ExecutionPlan  
→ CenterTask  
→ 多个 Center / Agent  
→ ResultAgent  
→ Validator  
→ SSE

它用于明确的复杂任务是合理的。

但如果“你好”“再讲简单点”“线程呢”也走这条链路，就相当于用航天发射流程去回应一句课堂追问。

### 产生的后果

- 延迟更高。
- 任一环节理解偏差都会累积。
- ResultAgent 可能把多个本不需要的结果揉成一段泛泛回答。
- Debug 成本急剧上升：很难知道问题到底出在 Router、某个 Center、Agent、聚合还是前端。
- 使用者会感到系统“有时聪明，有时突然很奇怪”。

### 正确分工

80% 常见请求应尽量短：

用户 → TutorAgent → Answer

只有明确的生成与行动请求才进入：

用户 → CapabilityGate → RouterAgent → ExecutionPlan → ResultAgent

这不是“删除多 Agent”，而是把它放回适合的地方：

> **复杂系统服务复杂任务；普通对话保持普通。**

---

## 8. 问题七：现有 Validator 不能伪装成“答案正确性证明”

回答校验有价值，但第一阶段必须克制。

可靠的机械检查包括：

- 空回答
- 明显重复
- 输出被截断
- 内部 Prompt 或结构化 JSON 泄露
- 输出语言明显错误
- 流没有正常结束

这些问题可以高置信地检测和重试。

但不应该第一阶段让一个 LLM 再判断“原回答是否正确”，然后相信它说“正确”。

那只是把一次不确定的生成变成两次不确定的生成，容易制造一种假的可靠感。

知识准确性应当通过以下方式逐步提高：

1. 干净、相关、可追溯的知识库证据；
2. 任务级评测集；
3. 必要场景下的引用与工具验证；
4. 人工抽检和错误样例回灌。

---

## 9. 问题八：没有 Evaluation，就无法知道系统到底有没有变好

“这版好像自然一点”不够。

没有评测集时，开发会陷入：

- 今天改 Prompt，感觉好一点；
- 明天改 Router，某个例子更好；
- 后天发现上下文追问又坏了；
- 继续改，最后不知道哪次改动导致退化。

系统需要一套最初只有 50–100 条也可以的评测集，覆盖：

- 普通学习问答；
- 多轮上下文；
- 用户纠正；
- 歧义追问；
- 明确能力请求；
- 不该触发能力的输入；
- SSE 异常和终止。

至少观察：

| 指标 | 它回答的问题 |
|---|---|
| Routing Accuracy | 该不该调用能力时判断对了吗？ |
| Capability False Trigger Rate | 普通聊天有没有被误送进生成模块？ |
| Context Consistency | 有没有听懂上一轮和本轮纠正？ |
| Answer Relevance | 有没有回答当前问题？ |
| Hallucination Review Rate | 有没有明显无依据编造？ |
| SSE Done Rate | 流是否正常结束？ |
| Sanity Failure Count | 空、重复、截断、泄露有没有出现？ |
| Latency | 简单问题有没有被处理得过慢？ |

评测的作用不是为了追一个漂亮分数，而是让每一次改动都有证据。

> 从“我觉得这次不错”，变成“这次把误触发从 18% 降到 4%，但上下文承接退化了 2 条”。

## 10. 这轮改造中最容易犯的错误

以下做法看上去很努力，实际上会让系统更乱：

1. 看到回答离谱，就再加几个 Intent。
2. 看到模型没利用画像，就把画像塞得更多。
3. 看到某次上下文丢失，就把历史窗口从 10 条加到 50 条。
4. 看到 Agent 没选对，就再加一个 Router 或 Reviewer。
5. 看到某个问题回答差，就只为这句话加一条硬编码 Prompt。
6. 还没测清真实聊天链路，就先改后端或换模型。
7. 还没有评测集，就同时改 Prompt、Router、RAG、画像和前端。
8. 把“复杂架构”误认为“可靠产品”。

这些都属于向不稳定地基继续加楼层。

---

## 11. 本轮必须遵守的决策

### 默认路径

任何 auto 输入先按 NORMAL_CHAT 处理，只有明确能力请求才进入特殊路由。

### 画像与历史

最少、相关、可解释。不存在“为了个性化所以每轮都塞”的默认规则。

### API 与 Prompt

Prompt 是约束模型的工具，不是堆积说明书的仓库。优先保证当前问题、相关上下文、目标输出清楚无冲突。

### 多 Agent

保留，但从普通聊天主干撤出。它是能力层，不是用户每句话都必须经过的中间层。

### Validator

先做异常检测和安全降级；正确性由评测和证据体系逐步保障。

### 评测

任何改变聊天主链路的修改，都要能在同一套样例上复跑。没有基线，不宣称“变稳定了”。

### 开发顺序

1. 统一真实前端与后端聊天链路；
2. 让 TutorAgent 成为默认处理器；
3. 引入保守 CapabilityGate；
4. 建立 ContextBuilder；
5. 增加输出健全性检查；
6. 建立评测和回归；
7. 再逐个恢复资源、练习、图解等能力的迭代。

---

## 12. 给后续 Agent 的工作指令

在本项目中，以下原则优先于“多做功能”：

- 首先确认当前页面回答来自真实后端，而非 Mock。
- 先查证再修改；不要根据文件名猜后端路径或调用关系。
- 对普通对话，优先让 TutorAgent 回答；不确定就不要调用能力模块。
- 改动画像、历史或 RAG 时，解释“为什么这条信息与当前问题相关”。
- 不要因为一次失败就加新的 Agent、Intent 或全局 Prompt 规则。
- 每次修改只改变一个主要变量，并运行对应的回归。
- 出现回答异常时，先检查链路、路由、上下文和检索证据，再怀疑模型本身。
- 不做无关重构；保持现有接口可运行，逐阶段收敛。
- P0–P4 未达到评测门槛前，不扩展资源生成、图解生成或新的多 Agent 流程。

最后记住：

> 这个项目下一阶段的目标，不是让系统看起来更像一个复杂的 Agent 平台。
>
> 而是让它先成为一个可以连续聊 20 分钟、不会突然“闹鬼”的学习助手。
