# 产品主线与业务编排约束

> **定位**：本文件是后续需求分析、功能设计和 AI 服务改造的共同约束。它不替代接口文档、具体实现方案或测试计划；它规定的是：一个新需求应先落入哪个业务域、谁拥有编排权、代码不得跨越哪些边界。
>
> **适用范围**：Python AI 服务为主，前端与 Java 后端按各自边界配合。现有接口保持兼容的前提下渐进式收敛，不要求一次性重写。

---

## 1. 产品第一定位

系统首先是一个能够连续对话、稳定辅导学习的助手，而不是默认调度所有 Agent 的平台。

用户最常见的行为是提问、追问、纠正和要求换一种解释。因此，系统遵守以下默认原则：

```text
普通输入 → 默认进入对话辅导
只有用户明确要求专项产物或行动 → 才进入专项能力
```

不把关键词本身当成进入复杂流程的理由。

| 用户说法 | 产品判断 | 是否进入专项能力流 |
| --- | --- | --- |
| “进程和线程再讲简单一点” | 连续答疑 | 否 |
| “举个真实例子” | 连续答疑 | 否 |
| “我不会 TCP，怎么办” | 解释或诊断式答疑 | 否 |
| “给我做 7 天 TCP 学习计划” | 明确要求学习计划 | 是 |
| “生成 5 道进程调度选择题” | 明确要求练习 | 是 |
| “画一张 TCP 握手图” | 明确要求可视化产物 | 是 |
| “帮我做计划，再生成题目” | 两个专项目标 | 默认不自动并发；先完成主目标，再由用户触发下一项 |

一次自然语言请求默认只选择一个主业务域。专项能力完成后可以给出下一步建议，但不得自动启动另一个 Center。

---

## 2. 业务域与唯一入口

只有以下业务域可以接住用户目标。每个业务域只能有一个对 API 暴露的主入口。

| 业务域 | 用户真正想完成什么 | 唯一业务入口 | 默认内部执行 |
| --- | --- | --- | --- |
| 对话辅导 | 理解、追问、纠正、举例、解释 | `TutorCenter` | `TutorAgent` |
| 学习计划 | 形成或调整学习路径 | `PlanCenter` | `LearningPathWorkflow` |
| 学习资源 | 得到文章、代码、PPT、文档等资源 | `ResourceCenter` | `ResourceGenWorkflow` |
| 练习评估 | 出题、解题、批改、错因分析 | `ExerciseCenter` | 专项 Agent，必要时 Workflow |
| 可视化理解 | 得到图解、图谱、流程图 | `VisualizationCenter` | 可视化 Pipeline |

`Profile`、RAG、知识图谱数据、LLM 客户端、评测、导出器等均为支撑能力，不是用户业务入口。它们只能被业务域按需调用，不能反过来控制用户流程。

---

## 3. 唯一入口规则

所有对外 API 遵守以下结构：

```text
API → 一个且仅一个 Center → Agent 或 Workflow → 结果 / 事件
```

禁止以下旁路：

```text
API → Agent
API → Workflow
API → 手写多个 Agent 的执行顺序
```

允许的关系是：

```text
API → 对应 Center
Center → Agent
Center → Workflow → Agent
```

当前关键入口的目标归属如下：

| 当前入口 | 目标业务入口 |
| --- | --- |
| `/api/chat` | `AutoCenter` 做保守分流后，委派一个业务 Center |
| `/tutor/chat` | `TutorCenter` |
| `/resources/generate` | `ResourceCenter` |
| `/plans/create-from-path` 及计划相关端点 | `PlanCenter` |
| 练习相关端点 | `ExerciseCenter` |
| 图解、图谱相关端点 | `VisualizationCenter` |

`AutoCenter` 是统一自然语言入口的分发器，不是另一个拥有独立业务流程的 Center。它只能决定请求进入哪个业务域，不能复制计划、资源、练习或可视化的下游业务流程。

---

## 4. Center、Agent 与 Workflow 的职责边界

### 4.1 Center：业务负责人

Center 对外代表一个用户目标，负责解释请求、选择内部执行方式并返回统一的业务结果。

Center 可以：

- 判断本业务域内任务是简单任务还是复杂任务；
- 调用本业务域的 Agent；
- 启动本业务域的 Workflow。

Center 不可以：

- 处理 HTTP、SSE 等传输细节；
- 调度其他业务域；
- 在多个文件复制同一业务流程。

### 4.2 Agent：完成一件局部智能工作

Agent 只承担一项局部智能职责，例如讲解、检索、出题、批改或生成 PPT 内容。

Agent 不可以：

- 决定用户应进入计划、资源、练习或可视化；
- 调度多个业务域；
- 依赖 HTTP、前端页面或 SSE 传输细节。

### 4.3 Workflow：只服务同一业务域的多阶段流程

仅在满足任一条件时使用 Workflow：

- 存在明确前后依赖，例如“目标 → 拆解 → 排期”；
- 存在跨步骤状态需要保存；
- 存在质量门控、重试或回退；
- 用户能感知到多个业务阶段。

因此：

```text
普通问答：TutorCenter → TutorAgent
学习计划：PlanCenter → LearningPathWorkflow → Goal / Decompose / Schedule
资源生成：ResourceCenter → ResourceGenWorkflow → Director → 专项资源 Agent
```

`Director` 只允许在资源工作流内部选择资源 Agent，不能成为全局请求路由器。

---

## 5. 三类决策必须分开

| 决策类型 | 唯一所有者 | 示例 |
| --- | --- | --- |
| 请求级分发 | `AutoCenter` / `CapabilityGate` | 这句话是普通答疑，还是明确要求学习计划？ |
| 业务内编排 | 对应 Center / Workflow | 学习计划需要先拆知识点再安排时间 |
| 专项执行选择 | 业务域内部 | 资源生成应选择 PPT Agent 还是 Code Agent？ |

名称相似不代表职责可互换。请求级路由、业务内 Workflow 判断与资源 Agent 选择不得混为一个“万能路由器”。

---

## 6. 统一对话的保守分流规则

统一聊天只允许两条主路径：

```text
不确定或普通输入
→ NORMAL_CHAT
→ TutorCenter
→ TutorAgent

明确专项请求
→ CapabilityGate
→ 一个专项 Center
→ 该业务域自己的流程
```

必须遵守：

1. `NORMAL_CHAT` 是默认结果。
2. 一次请求只选择一个主业务域。
3. 证据不足时不触发专项能力。
4. 专项能力完成后只能建议下一步，不能自动启动下一 Center。
5. 画像、历史和知识库只作为辅助信息，不能压过当前用户明确表达的目标。
6. “再讲简单一点”“举例”“为什么”“我不会”等表达默认属于对话辅导，不得仅因关键词进入资源、可视化、诊断或计划流程。

## 7. 前端、Java、Python 的边界

```text
前端：收集用户目标；由按钮触发明确专项能力；渲染事件与结果
Java：鉴权、会话与业务数据持久化；转发 AI 请求与 SSE
Python API：协议校验、安全；调用一个 Center；转换响应与 SSE
Center：业务入口、业务内选择与统一结果
Workflow / Agent：AI 执行
```

Java 与 Python API 均不得承担“Goal → Decompose → Schedule”之类的业务顺序。`internal_api.py` 的拆分必须发生在业务逻辑迁出之后；不得通过仅拆文件来制造新的 Fat Controller。

## 8. 后续修改与验收顺序

### P0：立边界，不改变业务行为

1. 将本文件作为新增需求和代码评审的共同约束。
2. 为关键端点登记：业务域、唯一 Center、是否流式、当前下游链路。
3. 新增功能必须先写一张四格卡：`用户目标 → 业务域 → Center → Agent / Workflow`。
4. 暂停新增跨 Center 的自动编排。

### P1：优先消除确定存在的旁路

1. 所有计划端点只调用 `PlanCenter`，Goal → Decompose → Schedule 只保留一处。
2. 所有资源端点只调用 `ResourceCenter`，`ResourceGenWorkflow` 不再被 API 直调。
3. 每一步保持现有 API 契约，并用状态码、响应字段与 SSE `done/error` 事件回归验证。

### P2：收统一聊天主路径

1. `/api/chat` 的普通输入稳定走 `TutorCenter`。
2. 仅明确专项请求进入一个专项 Center。
3. 普通聊天不再默认走多 Center 并行或串行聚合。
4. `ResultAgent` 不再承担跨业务域的默认总调度；其职责逐步收敛为业务域内结果整理或由 Center 替代。

### P3：迁逻辑后再拆 API 与统一事件

1. 将计划、图谱、导出等领域逻辑迁出 API 层。
2. API 层收敛为“校验 → 一个 Center → 序列化 / SSE”。
3. 在业务入口和结果语义稳定后，再定义统一事件模型；不为了流式一次性重写全部执行框架。

---

## 9. 新需求的强制检查清单

任何新功能进入开发前，必须回答：

```text
1. 用户要完成什么？
2. 它属于哪个唯一业务域？
3. 它应该由哪个 Center 接住？
4. Center 内部是直接调用一个 Agent，还是必须启动 Workflow？
5. 是否真的需要跨业务域？默认答案：不需要。
```

如果无法回答以上问题，则不得直接向 API、Agent 或 Workflow 中追加逻辑。

---

## 10. 成功标准

当以下条件成立时，系统从“功能堆叠的原型”进入“可持续演化的工程系统”：

- 任一端点都能明确指向一个业务主入口；
- 同一种业务流程只有一个编排位置；
- 普通对话保持短链路，不被专项能力干扰；
- 新功能有明确落点，不再自然长进 `internal_api.py`；
- 新开发者无需靠猜，也能回答谁负责路由、谁负责编排、谁负责执行和谁负责状态。
