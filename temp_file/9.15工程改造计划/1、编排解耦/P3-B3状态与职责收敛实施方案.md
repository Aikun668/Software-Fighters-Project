# P3-B3 实施方案（状态范围收敛 + ResultAgent 职责收敛）

> 依据：P3-B 方案 §一 的 **B7 + B8**；P3-B2 验收记录 §六 遗留项。
> 本文件**未跟踪**。
> **摸底后的重要修正**：B7/B8 原先被定性为"行为变更轮"，但逐行核对后发现——
> **绝大部分收敛可以做到零行为变化**（命名 / 协议 / 并发正确性 / 映射表化），
> 只有"真正迁移职责"与"合并双层图"才是行为变更。故建议再切一刀。

## 零、摸底结论（带证据）

### 0.1 ⚠️ 头号发现：`_current_on_token` 是**真实的并发缺陷**，不只是"风格问题"

| 项 | 证据 |
|---|---|
| 写入 | `app/agents/base_agent.py:131` `self._current_on_token = on_token`（`run()` 内，`input_state.pop("_on_token")` 之后，128–140） |
| 恢复 | `base_agent.py:135-139` 用进入时的 `prev_on_token` 恢复 / `delattr` |
| 读取 | **全仓唯一**读取点：`app/agents/tutor_agent.py:358`（`_respond_node` 内） |
| 实例生命周期 | `internal_api/_get_tutor_agent`（`internal_api/__init__.py:180-188`）是**单例**，被 `_get_tutor_center`（191–205）注入 → `/tutor/chat` 路径**长生命周期复用同一实例** |

**风险链**：两个并发 `/tutor/chat` 请求 → 同一 `TutorAgent` 实例 → 请求 B 的 `run()` 在请求 A 的 `ainvoke` 期间写入自己的 `_current_on_token`（131）→ A 的 `_respond_node`（358）读到的是 **B 的回调** → **token 串流到错误的请求**。

> 现状"看起来正常"只是因为：`ChatCenter` 路径下 `AutoCenter` 未注入 `tutor_agent`（`chat_center.py:91-95`），
> `auto_center.py:86` 每次 `TutorAgent()` 新建 → 那条路无共享。**但 `/tutor/chat` 走单例**，风险成立。
>
> 处置：改用 `contextvars`（每请求/每协程上下文隔离），单请求语义**逐字不变**，并发语义修正。

### 0.2 `ResultAgent` 的真实形状：**它其实已经不是"跨业务域总调度"**

| 项 | 证据 |
|---|---|
| 唯一公开入口 | `execute(plan, event_queue=None)`（`app/centers/result_agent.py:93-196`） |
| 分发形态 | `_execute_task`（198–216）**硬编码 if-链** `auto/plan/resource/exercise/visualization` → 各 Center 的 `execute` |
| 唯一生产调用者 | `ChatCenter`（`chat_center.py:220` 与 `:333`）—— **没有任何别的 Center 调用它** |
| 逐请求状态 | **无**。`aggregated = AggregatedResult()` 是 `execute` 局部变量（109）；实例属性只有 5 个 Center 引用（82–91） |
| 仍持有的职责 | ① 串行任务循环（112–184）② SSE 事件拼装：token 逐字流 + `partial=True` finalize（129–178）③ `done` 载荷组装：summary / next_steps / profile_delta / results（186–196）④ 正文合成 `_ensure_user_visible_response`（256–272）+ `_summarize_product`（274–304） |
| **已迁走的职责** | 正文聚合、推荐抽取、多 done 收敛、缺 done 兜底、错误补发 —— **都在 `ChatCenter.stream_chat`**（`chat_center.py:335-469`） |

**结论**：`ResultAgent` 的**实际调用关系已经是"聊天域内部组件"**，与 GUIDE P2 的目标（"不再承担跨业务域的默认总调度"）
在**调用拓扑上已经达成**；欠的只是 ① **命名**（`ResultAgent` 名不副实）② **职责边界**（是否继续持有 SSE 拼装与正文合成）。
→ 因此"命名对齐 + 边界登记"是**零行为变化**；"职责真正迁移"才是行为变更。

### 0.3 双层图 / 穿透私有节点：本质是**"Workflow 复用 Agent 局部节点"缺少公开协议**

| 项 | 证据 |
|---|---|
| `ProfileWorkflow` 图（5 节点） | `profile_workflow.py:55-72`：`extract` / `merge` / `completeness_check` / `response` / `complete` |
| 其中**纯转发** | `_extract_node`（79-82）→ `profile_agent._extract_node`；`_merge_node`（84-87）；`_response_node`（103-106） |
| 其中**自有逻辑** | `_completeness_check_node`（89-101，纯算术）、`_complete_node`（108-123，固定文案 + `logger.info`） |
| ⚠️ **节点集不一致** | `ProfileAgent` 图有 5 节点（`profile_agent.py:105-109`），含 `semantic_judge`(106) 与 `audit`(108)；**外层图没有这两个** |
| `LearningPathWorkflow` 穿透 | `learning_path.py:70` 调 `path_agent._draft_node`、`:88` 调 `path_agent._revise_node`（绕过 `run()`） |

**两个独立问题**：
1. **穿透私有节点**（跨类调 `_` 开头方法）：`ProfileWorkflow` ×3、`LearningPathWorkflow` ×2 → 应提升为**公开节点 API**。**零行为变化**。
2. **双层图 + 节点集不一致**：外层图**漏掉了** `semantic_judge` / `audit`。合并两层会让这两节点开始执行 → **行为变更**（画像抽取质量会变），且无法判断"漏掉"是有意还是疏忽 → **不能自动合并**，须登记并向产品确认。

## 一、建议范围：把 P3-B3 再切成 a / b

| 轮次 | 内容 | 性质 |
|---|---|---|
| **P3-B3a** | ① `_current_on_token` → `contextvars`（修并发缺陷）② 私有节点 → 公开节点 API（穿透合法化 + 契约禁用跨类私有调用）③ `_execute_task` if-链 → 显式映射表 ④ `ResultAgent` 命名/边界对齐（重命名 + "唯一调用者是 ChatCenter" 契约） | **零行为变化**（①为并发修正，单请求语义不变） |

## 三、P3-B3a 技术方案（草案）

### 3.1 `contextvars` 替换实例属性（`base_agent.py` + `tutor_agent.py`）

```python
# app/agents/base_agent.py
from contextvars import ContextVar

_current_on_token: ContextVar = ContextVar("current_on_token", default=None)

async def run(self, input_state: dict) -> dict:
    on_token = input_state.pop("_on_token", None)
    token = _current_on_token.set(on_token)
    try:
        ...
    finally:
        _current_on_token.reset(token)
```

- 节点侧（`tutor_agent.py:358`）：`on_token = _current_on_token.get()`
- **行为等价性**：单请求内 `get()` 值与旧实例属性在 `ainvoke` 期间的值**相同**（同一协程上下文）；
  并发时各自隔离 → 修掉 §0.1 的串流。
- 保留 `self._current_on_token` 兼容读？**不必**（全仓唯一读取点是 `tutor_agent.py:358`，一处改完）。
  契约测试锁"`_current_on_token` 不再作为实例属性被赋值"。

### 3.2 节点公开 API（`profile_agent.py` / `path_agent.py`）

| 旧（私有） | 新（公开） |
|---|---|
| `ProfileAgent._extract_node` | `ProfileAgent.extract` |
| `ProfileAgent._merge_node` | `ProfileAgent.merge` |
| `ProfileAgent._response_node` | `ProfileAgent.respond` |
| `PathAgent._draft_node` | `PathAgent.draft` |
| `PathAgent._revise_node` | `PathAgent.revise` |

- 调用点同步：`profile_workflow.py:81/86/105`、`learning_path.py:70/88`。
- ⚠️ **点名的测试耦合**：`tests/test_tutor_agent.py` 里有 `_respond_node` 的断言（那是 `TutorAgent` 的节点，**不在改名范围**，须区分清楚）。
- 新增契约：**禁止跨类调用下划线开头的节点方法**（AST 断言：`profile_workflow` / `learning_path` 内不出现 `._*_node(`）。

### 3.3 `_execute_task` 映射表化（`result_agent.py:198-216`）

```python
def _center_for(self, mode: str):
    return {
        "auto": self.auto_center, "plan": self.plan_center,
        "resource": self.resource_center, "exercise": self.exercise_center,
        "visualization": self.visualization_center,
    }.get(mode)
```
- 未知 mode 的 error `CenterResult` 分支（210–216）语义逐字保留（含错误文案与 status）。

### 3.4 `ResultAgent` → `ChatTaskDispatcher`（含边界契约）

- 类名 + 模块名（`app/centers/result_agent.py` → `app/centers/chat_task_dispatcher.py`）。
- docstring 写明：**唯一调用者是 `ChatCenter`**；职责 = 聊天域内"plan.tasks → 各 Center → 事件流"；
  聊天级终态策略在 `ChatCenter.stream_chat`（附行号）。
- 新增契约：`ChatTaskDispatcher` 的引用者集合 == {`chat_center.py`}（复用 P3-A 的 `_referencing_files` 手法）。
