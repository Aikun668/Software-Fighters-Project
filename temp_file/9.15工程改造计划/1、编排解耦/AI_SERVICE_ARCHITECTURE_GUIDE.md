# Python AI Service：渐进式架构收敛方案（方向指导）

## 文档目的

本文件给出当前项目的重构方向、目标边界和实施顺序。它不是具体代码设计，也不要求一次性重写；执行时必须以现有接口契约和真实测试结果为准。

配套问题说明：`AI_SERVICE_ARCHITECTURE_ISSUES.md`。

## 最终目标

把系统从“HTTP 路由可任意跳到 Agent/Workflow/业务逻辑”的状态，收敛为：

```text
Internal HTTP API
        ↓
业务入口（Center / Use Case）
        ↓
复杂任务：Workflow；简单任务：Agent
        ↓
共享 Service / 基础设施 / LLM
```

核心原则：

> API 只处理协议；每个业务能力只有一个主入口；只有一个层级拥有某一种编排权。

这里的“业务入口”可以继续使用现有 `Center` 概念，不必马上引入新的 `usecases/` 目录。关键不是名字，而是让 Center 从“可选包装层”变成各业务域对 API 暴露的唯一入口。

## 推荐职责边界

| 层级 | 应负责 | 不应负责 |
| --- | --- | --- |
| `internal_api` | 请求校验、认证/安全入口、调用一个业务入口、协议/SSE 响应 | 计划计算、Agent 顺序、跨 Agent 业务编排 |
| Center（业务入口） | 该业务域的请求解释、选择简单 Agent 或复杂 Workflow、统一业务结果 | 在多个文件复制同一业务流程；处理 HTTP 细节 |
| Workflow | 需要多阶段、可恢复/可审计状态、质量门控、循环修复的业务流程 | 成为所有简单问答的默认容器；直接理解 HTTP |
| Agent | 单一智能职责：构造上下文、检索、调用 LLM、局部后处理 | 跨业务域调度、拥有多业务流程的最终决策权 |
| Service | 可复用领域规则、数据访问、模型客户端、校验器、分类器 | 挂载 HTTP Router；偷偷发起完整业务流程 |
| `events` / streaming 工具 | 事件契约、SSE 编码、流式适配 | 计划/资源等领域业务判断 |

## 三种“决策”必须分开管理

| 决策类型 | 唯一责任位置 | 当前对应模块 | 建议 |
| --- | --- | --- | --- |
| 用户请求去哪个业务域 | 统一聊天的请求级分发器 | `RouterAgent` + `intent_extractor` | 保留为一套请求级机制，`intent_extractor` 只提供分类/参数能力，分发器做最终选择 |
| 内容属于什么领域 | 内容分类 Service | `domain_router` | 保留但改用更准确的语义名称，例如 `domain_classifier`；不参与执行单元选择 |
| 资源任务使用哪个专项 Agent | 资源 Workflow 内部 | `Director` | 只在资源生成链内部存在；改成体现资源选择语义的名称，避免与通用“导演/编排”混淆 |

不要把三者合并为一个万能 Router。它们输入相似，但决策粒度不同。要收敛的是**规则的所有权和命名**，不是强行把所有判断塞进同一个文件。

## 每个业务域的唯一主入口

建议先明确如下归属：

| 业务域 | API 唯一调用对象 | 内部执行方式 |
| --- | --- | --- |
| Tutor/chat | `TutorCenter` | 简单链路委派 `TutorAgent`；必要时由 Center 统一接入画像、流式、降级等横切策略 |
| 资源生成 | `ResourceCenter` | 委派 `ResourceGenWorkflow`；资源专项 Agent 选择只发生在 Workflow 内 |
| 学习计划 | `PlanCenter` | 统一拥有 Goal → Decompose → Schedule 与计划状态相关的业务流程 |
| Profile | `ProfileCenter` 或既有 `ProfileWorkflow` 的单一门面 | 依据复杂度确定，但 API 只能调用这一处门面 |
| 统一自然语言入口 | `AutoCenter` / 请求分发入口 | 只负责识别目标业务域后委派对应 Center，不能复制下层业务流程 |

这不是要求所有调用链都变长。例如 Tutor 的内部仍可以是 `TutorCenter → TutorAgent → LLM`。关键是 API 不再自己绕过 `TutorCenter`。

## 分阶段实施建议

### P0：先立边界和安全线，不改行为

目标：在动结构之前，确保每次迁移都能验证“外部行为没被悄悄改坏”。

应完成：

1. 为每个端点登记“业务域、唯一入口、是否流式、当前下游链路”。优先覆盖 `/tutor/chat`、`/resources/generate`、计划相关 8 个端点和统一聊天入口。
2. 给关键端点补契约测试：请求结构、成功响应/SSE 事件顺序、常见错误码、模型参数安全校验。
3. 为每个业务入口补最少的调用链日志/trace id，使日志可回答“本次请求进入哪个 Center、运行了哪个 Workflow/Agent”。
4. 冻结新增旁路：新增端点不得直接在 API 内编排多个 Agent/Workflow，不得复制既有业务顺序。

验收标准：迁移前后可比较关键端点的状态码、响应字段与 SSE `done/error` 事件；每个关键请求可从日志追到唯一业务入口。

### P1：优先消除明确的重复编排

目标：先解决最容易产生行为分叉的两处重复，而不是马上全面拆目录。

应完成：

1. 选定 `PlanCenter`（或等价的计划业务门面）为计划能力唯一主入口。
2. 将 `internal_api.py` 内的 Goal → Decompose → Schedule 重复编排迁出；计划端点只调用计划业务入口。
3. 把计划进度、里程碑、今日任务、掌握度、图谱匹配等规则逐步归入计划业务服务/计划 Center，而不是继续留在 API。
4. 选定 `ResourceCenter` 为资源生成唯一主入口；其内部统一调用 `ResourceGenWorkflow`。端点不再直连 Workflow。
5. 在保持原接口不变的情况下删除第二份重复流程，并用契约测试覆盖迁移。

验收标准：搜索代码后，同一套计划三段式只存在一个编排位置；所有资源生成入口都汇入同一个业务入口；API 不含此类执行顺序。

### P2：收拢 API 层，先迁逻辑再拆文件

目标：把 `internal_api.py` 真正变为协议层，而不是把 2400 行平均切开。

迁移顺序建议：

1. 先迁计划业务逻辑（收益最大）。
2. 再抽出流式/SSE 适配、事件清洗、统一错误到独立共享模块。
3. 抽出多模态消息构建与解析、安全校验、模型参数清洗等纯能力模块。
4. 统一单例/依赖获取方式，避免端点各自维护 `_get_xxx`。
5. 当路由函数都稳定为“校验 → 调一个业务入口 → 序列化”后，才按业务域把单文件升级为 `internal_api/` 包。

推荐的落地结构是语义化的中间版：

```text
app/
├─ internal_api/        # Java → Python 的内部 HTTP 入口
│  ├─ router.py
│  ├─ tutor.py
│  ├─ resources.py
│  ├─ plans.py
│  ├─ profile.py
│  └─ ...
├─ centers/             # 每个业务域唯一入口
├─ workflows/           # 多阶段 LangGraph 流程
├─ agents/              # 单一智能执行单元
├─ services/            # 复用规则/基础设施能力
├─ events/              # SSE 事件契约与编码
├─ schemas/             # 请求、响应、业务 State
└─ core/                # config、logging、LLM client、依赖装配
```

不要求一次性移动所有文件。可以先保留兼容导入，再逐步替换调用点；每一小步都必须通过 P0 的契约测试。

验收标准：路由函数不再包含计划计算或多 Agent 顺序；同类 SSE 行为使用同一适配方式；`internal_api.py` 的拆分按业务域而不是按“随便凑行数”。

### P3：收敛路由和状态机规则

目标：让未来功能不会重新制造第二套编排与路由。

应完成：

1. 写一页架构约定，明确三类决策的名称、所有者、输入输出和禁止跨层调用规则。
2. 将请求级关键词表/意图提取能力收敛为一个可复用来源；`RouterAgent` 只负责从分类结果做业务域分发。
3. 重命名会误导职责的模块和节点，尤其区分“资源 Agent 选择”“领域分类”“流程节点判断”。
4. 明确 Workflow 与 Agent 的状态范围：Workflow 状态跨业务阶段；Agent 状态只服务其局部执行。简单任务不因“看起来高级”而额外套 Workflow。
5. Code Review 增加检查项：API 是否只调用一个业务入口？是否新增了重复编排？是否把执行路由塞进分类 Service？

验收标准：新开发者能根据目录与约定回答“谁负责路由、谁负责状态、谁负责编排、谁负责执行”，不需要靠猜。

## 建议暂缓的事情

- 不要先全量重命名目录、推倒 `centers` 或把全部逻辑强行改为 LangGraph。
- 不要为了文件短而把业务规则拆成大量没有语义的小工具文件。
- 不要把请求级路由与资源 Workflow 内部选 Agent 粗暴合并。
- 不要在没有契约测试前搬动 SSE、错误响应和安全校验；这些地方最容易出现“接口没报错但前端坏了”。
- 不要在 P1 未完成前扩展新的资源类型、计划链路或新的多 Agent 编排。

## 重构过程中的判断准则

当你犹豫一段新逻辑应该放哪时，用这四个问题判断：

1. 它是否理解 HTTP、Header、SSE 格式？是：API/streaming 层。
2. 它是否决定一个业务请求该走聊天、计划、资源还是画像？是：请求级分发入口。
3. 它是否是某业务域内部的多阶段状态和质量控制？是：该业务域 Workflow/Center。
4. 它是否是多个地方都能复用、且不决定完整业务流程的能力？是：Service。

若一段代码同时回答了两个以上问题，优先把它拆开；这通常就是下一处 Fat Controller 或重复编排的起点。

## 成功的定义

本轮成功不以“目录看起来高级”为标准，而以以下事实为标准：

- 任一端点都能明确指向一个业务主入口。
- 计划、资源等同一能力不再存在两份独立的业务顺序。
- API 层可被读成简单的协议转换层。
- 出现问题时，可以沿着固定链路快速定位：`端点 → Center → Workflow/Agent → Service/LLM`。
- 新功能有明确落点，不再自然长进 `internal_api.py`。

做到这些，项目就从“功能已堆起来”进入“可以持续演化的工程系统”。
