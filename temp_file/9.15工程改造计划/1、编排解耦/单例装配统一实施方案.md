### 0.2 锁不一致（第 1 项收尾内容）

| 类别 | 数量 | 工厂 |
|---|---|---|
| 双检锁（`if None: with lock: if None: ...`） | 7 | chat_center, tutor_center, exercise_center, resource_center, plan_center, graph_center, intent_extractor |
| 裸 `if None:`（无锁） | 11 | profile_agent, tutor_agent, content_agent, exercise_agent, path_agent, mindmap_agent, code_agent, profile_workflow, path_workflow, inquiry_service, graph_service |

**⚠️ 诚实判断：这不是当前可见缺陷。**
现有 48 个端点全部是 `async def`，跑在事件循环单线程上；工厂内部的构造（含 `_get_mock_flag()`、`_get_exercise_agent()` 等互调）**全程同步、无 `await` 让出点**。因此在当前架构下「检查 None → 构造 → 赋值」不会被交错，无锁工厂**不会**真的重复构造。

加锁是**纵深防御加固**（对未来引入异步初始化、多线程 worker、或同步端点跑线程池的情形），**不是修一个已观测到的 bug**。这一条必须如实登记，不能写成「修复竞态」。
—— 也正因如此，「响应字节零变化」在本轮**天然成立**。

## 一、这次要解决什么

**只做三件收尾事，全部局限在 `internal_api.py` 的装配区块内部，不改任何调用点：**

1. **统一锁语义** —— 11 个无锁工厂补齐与另 7 个一致的双检锁（纵深防御，见 §0.2 的诚实判断）。
2. **收拢声明** —— 把 B/C/D 三处散落声明合并进 A 区，形成单一「依赖装配」区块。
3. **统一工厂文书** —— 18 个工厂补统一 docstring，各写清「唯一装配点 / 构造物 / 测试 patch 目标」，与既有 5 个已带 docstring 的工厂（`_get_tutor_center` / `_get_exercise_center` / `_get_resource_center` / `_get_plan_center` / `_get_graph_center`）体例一致。

**预期净效果**：`internal_api.py` 行数 **+约 45 行**（1417 → 约 1460）。

> 关于「文件变大」：本区块是需要长期存在的装配代码，且第 5 步拆包时会**整块**成为 `internal_api/__init__.py` 的内容（见 §八）。增大的方向与最终目标不冲突。

## 二、本轮明确不做

| 不做的事 | 原因 |
|---|---|
| 抽出 `app/core/deps.py` / `dependency_registry` | 会同时打断 A/B/C 三类共 38 处注入点，重演 `extract_knowledge_nodes` 遗留坑 |
| 引入 `_resolve(singleton, lock, factory)` 辅助函数 | 18 个工厂都靠**函数内惰性 import**（`from app.agents.x import X` 写在工厂体内）避免导入期开销；helper 需要把 import 提到 lambda 外或模块级，反而更长、且改变导入时机。**helper 在这里不划算** |
| 改任何端点调用点 | 40 个端点 / 41 处调用点全部保持 `_get_xxx()` 字面形态，C 类断言才成立 |
| 动 `_get_mock_flag`（硬编码 `return False`，14 处引用） | 属 GUIDE 第 3 步「模型参数清洗」范畴，**越界**。仅在本轮登记为已知项 |
| 把惰性 import 提升到模块级 | 改变导入期开销与潜在循环导入，风险远大于收益 |
| 新增依赖注入框架 / 容器 | 48 个端点规模不需要，且与「显式优于魔法」的项目风格相悖 |

## 四、技术方案

### 4.1 收敛后的装配区块形态（目标态）

```python
# ═══════════════════════════════════════════════════════════════
# 依赖装配（惰性单例）
#
# 全文件唯一允许构造 Center / Agent / Workflow / Service 的位置。
# 路由层只能通过 _get_xxx() 取用；48 个端点无一例外。
#
# ⚠️ 注入点冻结：既有测试依赖
#   ① internal_api._get_xxx          （monkeypatch 目标，8 个名字）
#   ② internal_api._xxx_singleton    （直改状态变量，3 个变量）
#   ③ inspect.getsource 里的 _get_xxx() 字面文本
#   三者在拆包（第 5 步）落地前均不得漂移。
# ═══════════════════════════════════════════════════════════════

# ── 状态（单一声明区） ──────────────────────────────────────────
_chat_center_singleton = None
_chat_center_lock = threading.Lock()

_profile_agent_singleton = None
_profile_agent_lock = threading.Lock()

...（18 个状态变量 + 11 个新增锁，按上表顺序排列）

_intent_extractor: IntentExtractor | None = None
_intent_extractor_lock = threading.Lock()
```

> 说明：**已带锁的 7 个工厂体一字不改**（含 5 个带 docstring 的收口点工厂），只做「搬声明」；仅 11 个无锁工厂的**函数体**从
> ```python
>     if _x_singleton is None:
>         from app... import X
>         _x_singleton = X(...)
> ```
> 变为
> ```python
>     if _x_singleton is None:
>         with _x_lock:
>             if _x_singleton is None:
>                 from app... import X
>                 _x_singleton = X(...)
> ```
> —— 函数内 import 位置不变、构造参数不变、返回语句不变，**`_get_tutor_agent()` 等字面文本不受影响**。

### 4.2 为什么「同模块收敛」能同时满足 GUIDE 与注入点冻结

| 约束 | 满足方式 |
|---|---|
| GUIDE：「统一单例/依赖获取方式」 | 18 个工厂收进单一区块 + 统一双检锁 + 统一 docstring |
| A 类注入点 | 工厂名与所在模块不变 → `internal_api._get_x = stub` 仍生效 |
| B 类注入点 | 状态变量名与所在模块不变 → 直改仍生效（工厂体读的仍是该模块全局） |
| C 类注入点 | 端点调用形态与工厂体关键字面文本不变 |
| D 类注入点 | 名字集合不变 |
| 响应字节零变化 | 调用点零改动 + 同步构造时序不变 |

### 4.3 显式保留的「防退化锁」

新增契约测试中固化为断言（防止后续轮次无意破坏）：

- 18 个工厂名**全部存在**且可调用；3 个负向名字**全部不存在**
- 每个惰性工厂的函数体内**都出现 `with _x_lock`**（锁语义不回退）
- 状态声明**只出现在一个区块**（不重新散落）
- 端点体内**不出现** `Center(` / `Agent(` / `Workflow(` / `Service(` 直连构造（唯一装配点不回退）

## 八、与第 5 步（拆包）的衔接

**关键前瞻结论：装配区块的最终归宿是 `internal_api/__init__.py`，不是 `app/core/deps.py`。**

理由即 §0.4：A/B/C 三类注入点都要求 `internal_api.<name>` 可读可写。拆包后 `internal_api` 变成一个包，`internal_api._chat_center_singleton = X` 设置的是**包 `__init__` 的属性**；若工厂体位于 `internal_api/deps.py`，它读的是 `deps` 自己的模块全局 → 注入点再次失效。

因此第 5 步的正确拆法是：

```
internal_api/
├─ __init__.py     # 装配区块（状态 + _get_xxx）+ router 聚合 include
├─ tutor.py        # 路由
├─ resources.py
├─ plans.py
└─ ...
```

即本轮 §4.1 收敛出的**单一装配区块，正是第 5 步要整块搬进 `__init__.py` 的那一块**。本轮把声明收拢到一处，客观上就是在为那次搬迁做准备。

反之，若本轮把工厂拆到 `app/core/deps.py`，第 5 步就得**再改一次 38 处注入点**——两轮各疼一次。这是选择「同模块收敛」的核心理由。
