# 聊天域编排收口方案

> **用途**：资源域收口完成后，下一阶段只处理统一聊天入口的业务编排边界。本方案用于锁定范围、唯一入口、编排责任和验收条件；本文件本身不授权立即修改代码。

**目标：** 在不改变 `/internal/api/chat` 请求格式、用户可见 SSE 事件和普通对话默认行为的前提下，让 `ChatCenter` 成为统一聊天的唯一业务入口，并消除 API、`ChatCenter`、`ResultAgent` 之间重复的流式终态编排。

**推荐架构：** API 只负责请求校验、SSE 序列化和 HTTP 响应；`ChatCenter` 负责聊天业务入口、能力判定、路由和聊天级终态策略；`ResultAgent` 负责按执行计划调用各业务 Center 并产生执行事件；各业务 Center 只负责自己的业务。资源域的直接接口保持现状，不在本轮重新改动。

**技术栈：** Python、FastAPI、asyncio、现有 `StreamEvent`、`ChatCenter`、`ResultAgent`、`CapabilityGate`、`RouterAgent`、各业务 Center、pytest。

**方向约束：** [产品主线与业务编排约束.md](../0、产品方向与约束/产品主线与业务编排约束.md)

---

## 一、这次要解决什么

当前资源域已经完成了“API → ResourceCenter → ResourceGenWorkflow”的单一入口收口。统一聊天入口仍然存在另一类问题：同一次聊天的执行和流式终态由多个层共同负责。

当前链路大致是：

```text
/internal/api/chat
  → internal_api._unified_chat()
  → ChatCenter.route()
  → ChatCenter.execute()
  → ResultAgent.execute()
  → AutoCenter / PlanCenter / ResourceCenter / ExerciseCenter / VisualizationCenter
  → StreamEvent
  → internal_api._unified_chat() 再做正文聚合、推荐抽取、error/done 收敛
  → SSE
```

目前各层的责任并不完全重叠，但边界已经开始交叉：

| 位置 | 当前职责 | 本轮处理方向 |
| --- | --- | --- |
| `internal_api._unified_chat()` | 路由调用、事件转 SSE、正文聚合、推荐抽取、延迟 done、补 error/done | 保留协议适配；把业务级流式策略移入 `ChatCenter` |
| `ChatCenter` | CapabilityGate、RouterAgent、ExecutionPlan、ResultAgent 执行和路由审计 | 成为统一聊天业务入口 |
| `ResultAgent` | 多 Center 执行、token Queue、center start/end、局部 content/error/done | 保留为内部执行编排器，不再成为 API 可直接进入的业务入口 |
| 各业务 Center | 计划、资源、练习、可视化或普通答疑 | 保持各自领域边界，不互相调度 |
| `ResourceCenter.stream_generate()` | 直接资源接口的 Workflow 队列和终态 | 本轮保持不变 |

核心判断不是 `internal_api.py` 文件太长，而是**统一聊天的业务结果仍需要 API 重新理解和拼装**。因此本阶段先收口聊天编排，不直接拆 API 文件。

## 二、范围与明确不做的事

### 本轮范围

1. 统一聊天 `/internal/api/chat` 的唯一业务入口和执行调用链。
2. `ChatCenter` 与 `ResultAgent` 的职责边界。
3. 普通对话、明确能力请求、追问、错误和唯一 done 的聊天级事件行为。
4. 将推荐抽取、正文收集和终态收敛从 API 业务函数迁移到聊天域内部。
5. 为上述行为建立离线契约、同进程 HTTP/SSE 和必要的真实服务验收记录。

### 本轮禁止扩张

- 不修改 `/internal/resources/generate`、`/internal/inquiry/resolve` 的资源接口契约。
- 不修改 `ResourceGenWorkflow`、资源 Prompt、资源质量门控或专项资源 Agent。
- 不改 Java、前端、数据库和会话持久化。
- 不把所有旧 API 立即拆成多个文件。
- 不引入 Redis Streams、Kafka、WebSocket、EventBus 或分布式任务执行器。
- 不在本轮把所有 Agent 的 `run()` 一次性改成异步生成器。
- 不直接进行 LangGraph 全局 streaming 迁移。
- 不先引入 `run_id`、递增序号、断线重连协议；这些属于聊天域收口后的统一事件模型阶段。

## 三、唯一入口、默认路径与编排 owner

### 3.1 唯一业务入口

统一聊天的唯一业务入口定义为：

```python
ChatCenter.stream_chat(...)
```

具体参数沿用现有请求数据，不新增公开请求字段。它负责：

1. 调用现有 `route()` 得到 `ExecutionPlan`；
2. 调用内部 `ResultAgent` 执行计划；
3. 聚合聊天正文，供推荐抽取和终态判断使用；
4. 在最终 done 前处理聊天级推荐和错误状态；
5. 对外保证聊天流以唯一公开 done 结束。

API 路由不得直接调用 `RouterAgent`、`ResultAgent`、任意业务 Center 或推荐抽取函数。

### 3.2 默认路径

普通自然语言默认走：

```text
CapabilityGate.NORMAL_CHAT
  → 单任务 CenterTask(mode="auto", intent="tutor_question")
  → ResultAgent
  → AutoCenter
  → TutorAgent
  → token / content / done
```

默认路径必须保持现有产品语义：没有明确要求生成计划、资源、练习或图形时，不得因为关键词误判而进入能力工作流。

### 3.3 能力请求路径

当 `CapabilityGate` 判定为明确能力请求时，保持现有二级路由：

```text
CapabilityGate
  → RouterAgent
  → ExecutionPlan
  → ResultAgent
  → 对应业务 Center
```

`CapabilityGate` 负责一级能力边界，`RouterAgent` 负责能力内部的任务计划，`ResultAgent` 负责执行计划；三者不能互相取代。

### 3.4 编排责任

| 层级 | 唯一责任 |
| --- | --- |
| API | 校验输入、调用 `ChatCenter.stream_chat()`、将 `StreamEvent.to_sse()` 写入 `StreamingResponse` |
| `ChatCenter` | 聊天业务入口、能力判定、计划入口、聊天级正文/推荐/终态策略、路由审计 |
| `ResultAgent` | 执行 `ExecutionPlan`，调用各 Center，产生执行过程事件和内部结果 |
| 业务 Center | 完成自己的业务，不调用其他业务 Center，不拥有全局路由权 |
| `StreamEvent` | 表达执行过程和结果，不决定业务路由 |

## 四、目标调用链

目标链路如下：

```text
POST /internal/api/chat
  → API 校验与 sanitize
  → ChatCenter.stream_chat()
      → ChatCenter.route()
      → ResultAgent.execute()
          → AutoCenter / PlanCenter / ResourceCenter / ExerciseCenter / VisualizationCenter
      → ChatCenter 收集正文与内部 done
      → ChatCenter 执行推荐抽取和聊天终态收敛
      → yield StreamEvent
  → API 只做 event.to_sse()
  → sse_heartbeat_generator()
```

### 公开事件顺序

普通聊天成功路径至少保持以下语义：

```text
center_start
→ token* 或 content*
→ center_end
→ recommendation?                  # 有知识点候选时才出现
→ done                              # 恰好一个，最后一个业务事件
```

能力型资源、计划或练习路径可以没有 token，但必须在 done 数据中携带真实业务产物；不得因为没有 token 就被 API 误判为空回答。

失败路径保持：

```text
已有业务事件*
→ error                             # 必须可被前端读取
→ done                              # 恰好一个，最后一个
```

推荐抽取超时或失败只影响推荐事件，不得阻塞 done，也不得让页面无限等待。

## 五、候选方案与选择

### 方案 A：渐进式收口到 ChatCenter（推荐）

保留当前 `StreamEvent` 和 `ResultAgent` 的主要行为，新增聊天域内部的 `stream_chat()` 外壳，将 `_unified_chat()` 中的正文聚合、推荐抽取和终态收敛移动到 `ChatCenter`。

优点：

- 对前端和 Java 的影响最小；
- 可以先锁定业务 owner，再演进事件模型；
- 能保留当前 token 旁路和资源/计划等非 token 产物；
- 每一步都可用现有 HTTP/SSE 测试验证。

代价：短期仍然保留现有 `ResultAgent` 的 Queue 与部分内部事件逻辑，不会一次性得到完整的 Agent-native streaming。

### 方案 B：现在直接改成 LangGraph 原生 streaming

让 TutorAgent、ResourceGenWorkflow 和其他 Agent 都直接暴露 LangGraph stream，再由 API 统一消费。

不选原因：当前统一聊天的业务 owner 和终态责任尚未收干净。此时接入框架原生事件会把路由、事件翻译、终态收敛和前端兼容问题同时扩大，难以判断回归来自架构边界还是框架流模式。

### 方案 C：先拆 API 文件或引入全局 EventBus

按路由拆分 `internal_api.py`，再用全局事件总线连接 Center、SSE 和日志。

不选原因：文件大小和传输设施不是当前根因；这会扩大工作区、引入新的生命周期与背压问题，且不能自动解决“谁拥有聊天终态”的问题。

本轮采用方案 A。

## 六、实施任务边界

### Task 1：锁定统一聊天现状契约

**检查/测试文件：**

- `ai-service/tests/test_sse_contract.py`
- `ai-service/tests/test_result_agent.py`
- `ai-service/tests/test_api.py`
- 新增或扩展 `ai-service/tests/test_chat_center_stream_contract.py`

先固定以下行为，改代码前必须能在测试中说明：

- 普通聊天默认进入 `NORMAL_CHAT → TutorAgent`；
- 明确资源/计划/练习请求不回落为普通 Tutor；
- token 顺序保持不变；
- 资源/计划等无 token 产物仍能成功结束；
- 推荐抽取发生在 done 之前，但超时不能阻塞 done；
- 成功、业务错误、管线异常、空产物都能以唯一 done 结束；
- 同一请求只产生一次模型生成。

### Task 2：增加 `ChatCenter.stream_chat()` 业务入口

**修改文件：**

- `ai-service/app/centers/chat_center.py`

新增聊天域内部流式入口，保留现有 `route()` 和 `execute()` 的兼容调用方式，先不改变公开 HTTP 接口。

该入口必须接收现有聊天必要信息：消息、历史、模式、学生画像、用户 ID、会话 ID 和风格；不得把 FastAPI `Request` 或 `StreamingResponse` 传入 Center。

`stream_chat()` 内部只允许出现一套聊天级正文收集、推荐抽取和终态收敛逻辑。推荐抽取应继续使用现有超时预算；失败只记录并跳过推荐，不改变主回答。

### Task 3：收窄 `/api/chat` 路由

**修改文件：**

- `ai-service/internal_api.py`

`_unified_chat()` 最终只保留：

1. `sanitize_model()` 和基础输入校验；
2. 调用 `_get_chat_center().stream_chat(...)`；
3. 将 `StreamEvent` 转换为 SSE 文本；
4. 返回 `StreamingResponse(sse_heartbeat_generator(...))`。

从 API 业务函数中移除：

- `assistant_content` 的业务聚合；
- `extract_knowledge_nodes()` 调用；
- 推荐超时控制；
- done 延迟和多 done 收敛；
- 空正文判断和 error/done 合成。

这些行为不是删除，而是移动到聊天域内部，并由测试证明公开事件语义不变。

### Task 4：确认 `ResultAgent` 的内部边界

**检查/必要时修改文件：**

- `ai-service/app/centers/result_agent.py`
- `ai-service/app/centers/chat_center.py`

确认 `ResultAgent` 只负责：

- 按 `ExecutionPlan` 顺序调用业务 Center；
- 产生 center start/end、token、content、业务 error 等执行事件；
- 聚合 Center 结果供 `ChatCenter` 使用。

它不得承担 API 协议，也不得被 API 直接获取。聊天级推荐和最终公开 done 由 `ChatCenter.stream_chat()` 统一处理，避免 `ResultAgent` 和 API 同时拥有终态拼装权。

### Task 5：依赖装配与资源边界回归

**检查文件：**

- `ai-service/internal_api.py` 中 `_get_chat_center()`；
- `ai-service/app/centers/chat_center.py` 中 `_get_result()`；
- `ai-service/app/centers/resource_center.py`；
- `ai-service/tests/test_resource_center_api_contract.py`。

生产路径必须满足：

- `/internal/api/chat` 只有一个 `ChatCenter` 入口；
- 直接资源接口仍通过 `_get_resource_center()`；
- 资源域的 `ResourceCenter.stream_generate()` 不被聊天收口重新改写；
- 不新增第二套资源 Workflow 队列或第二个公开资源生成入口；
- 测试替身可以注入，不通过全局状态互相污染。

本 Task 不要求把所有 Agent 工厂统一重构，只处理会影响聊天入口唯一性的装配问题。

### Task 6：真实接口与人工结果验收

**验收对象：**

- `/internal/api/chat` 普通中文提问；
- `/internal/api/chat` 明确资源或计划请求；
- `/internal/resources/generate` 资源直接接口回归；
- `/internal/inquiry/resolve` 追问解析接口回归。

必须将离线测试、同进程 ASGI HTTP/SSE、真实 LLM、人工可见结果和未执行项分开记录。真实 LLM 未配置时，不能把真实生成验收写成通过。

## 七、验收标准

### 结构边界

- [ ] `/internal/api/chat` 路由不直接调用 `RouterAgent`、`ResultAgent`、业务 Center 或推荐抽取。
- [ ] `ChatCenter.stream_chat()` 是统一聊天唯一业务入口。
- [ ] `ResultAgent` 是聊天内部执行计划的唯一多 Center 编排器。
- [ ] 普通聊天默认走 `NORMAL_CHAT → TutorAgent`。
- [ ] 能力请求仍由 CapabilityGate、RouterAgent、ResultAgent 按各自职责处理。
- [ ] 资源直接接口的 `ResourceCenter` 入口和 Workflow 唯一调用点不回退。

### 离线行为

- [ ] 普通聊天 token 流顺序与迁移前一致。
- [ ] 资源/计划/练习的结构化 done 结果不被误判为空正文。
- [ ] 推荐抽取成功时在 done 前出现，超时时仍按预算结束。
- [ ] 管线异常产生可读 error，并以唯一 done 收尾。
- [ ] 正常结束但内部缺少 done 时，聊天域补发且只补一个 done。
- [ ] 取消 SSE 消费时不留下后台执行任务。
- [ ] 一次请求只触发一次模型生成。

### 真实 HTTP/SSE

- [ ] HTTP 状态码和 `text/event-stream` 保持兼容。
- [ ] 最后一个业务事件是 done，且 done 恰好一个。
- [ ] 中文内容不乱码，token/content 与最终结构化结果可对账。
- [ ] 前端现有事件类型无需新增兼容分支即可消费本轮结果。
- [ ] 真实 LLM、Java 联调、前端人工检查未执行时，明确写为未执行。

### 工作区范围

- [ ] 本轮只修改聊天入口、聊天 Center/ResultAgent 边界、相关测试和验收记录。
- [ ] 不混入资源 Prompt、计划域、Java、前端或无关文档清理。
- [ ] 不覆盖当前工作区已有删除项、验收临时文件和未跟踪报告。
- [ ] `git diff --stat` 与提交列表已单独核对。

## 八、完成条件

只有同时满足以下条件，聊天域编排收口才可以关闭：

1. API 路由不再拥有聊天业务级流式终态逻辑；
2. `ChatCenter.stream_chat()` 成为统一聊天的唯一业务入口；
3. `ResultAgent` 成为内部多 Center 执行 owner；
4. 普通聊天、能力请求、资源结构化产物、错误和追问行为保持兼容；
5. 离线契约、同进程 HTTP/SSE 和真实验收证据分别记录；
6. 真实 LLM 或人工检查未执行时，明确保留为未执行，不以 pytest 替代；
7. 资源域直接接口的收口状态不被本轮回退。

---

## 九、本阶段之后的顺序

聊天域收口完成后，才进入统一事件模型阶段：

```text
聊天域编排收口
  → 最小统一 StreamEvent 元数据（run_id、seq、终态标记）
  → LangGraph 原生 streaming 试点普通聊天
  → 再扩展到检索、工具和更多 Agent
```

在统一聊天 owner 尚未稳定前，不开始全局 LangGraph streaming，也不引入分布式事件基础设施。

## 十、已知风险

1. **流式展示与完整质量检查存在时间差。** 已经发送给用户的 token 无法撤回；本轮保留现有策略，不把聊天域收口误认为质量门控改造。
2. **推荐抽取是额外 LLM/知识服务调用。** 它必须被限制在终态前的明确超时预算内，不能决定主回答是否完成。
3. **取消和客户端断开需要真实运行验证。** 离线取消测试只能证明任务清理逻辑，不能替代生产服务和浏览器行为检查。
4. **工作区当前仍有历史删除项和验收临时文件。** 它们不属于本轮聊天实现，必须保持边界，不能顺手清理。
