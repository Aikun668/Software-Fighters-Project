# 计划域收口实施方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 在不改变 `/internal/plans/create-from-path` 对外请求、成功响应和错误响应契约的前提下，让 `PlanCenter` 成为学习计划生成的唯一业务编排入口。

**架构：** 保留 FastAPI 路由、`CreatePlanFromPathRequest` 与 `api_success`/`api_error`。API 将请求参数交给一个 `PlanCenter`，由 Center 统一完成 Goal → Decompose → Schedule、计划步骤与知识图谱节点匹配、里程碑标准化；API 只负责协议校验、调用一个 Center 和序列化结果。

**技术栈：** Python、FastAPI、pytest、现有 `CenterTask` / `CenterResult`、现有 GoalAgent / DecomposeAgent / ScheduleAgent、现有 GraphService 与 exercise categorization service。

**方向约束：** [产品主线与业务编排约束.md](../0、产品方向与约束/产品主线与业务编排约束.md)

## 全局约束

- 不新增接口路径，不修改 `CreatePlanFromPathRequest` 的字段含义。
- 成功响应仍为 `{"success": true, "data": {...}}`；成功 `data` 必含 `course_id`、`total_steps`、`steps`、`title`、`milestones`、`estimated_days`、`daily_capacity`、`concept_graph`、`summary`。
- 步骤为空仍返回 HTTP 400 与 `GENERATION_FAILED`；其他未处理异常仍返回 HTTP 500 与 `INTERNAL_ERROR`。
- `PlanCenter` 是计划生成唯一编排位置；`internal_api.py` 不得直接构造或顺序调用 `GoalAgent`、`DecomposeAgent`、`ScheduleAgent`。
- 本轮不改前端、Java、聊天路由、资源生成、知识图谱其他端点或流式事件格式。
- 不做数据库持久化语义变化；`user_id` 继续作为 API 契约字段保留，即使当前生成链不使用它。

## 现状与目标调用链

### 当前调用链

```text
/plans/create-from-path
  → internal_api.py 直接构造 GoalAgent / DecomposeAgent / ScheduleAgent
  → API 内部手写 Goal → Decompose → Schedule
  → API 内部匹配知识图谱节点、标准化里程碑
  → api_success
```

`PlanCenter.execute()` 中已经有一份 Goal → Decompose → Schedule；因此同一业务存在两份编排。

### 迁移后调用链

```text
/plans/create-from-path
  → _get_plan_center()
  → PlanCenter.create_from_path(...)
      → GoalAgent → DecomposeAgent → ScheduleAgent
      → 计划步骤与知识图谱节点匹配
      → 里程碑标准化
  → api_success
```

`PlanCenter.execute(CenterTask)` 必须继续保留，供 `ResultAgent` 既有的计划能力调用；新的 `create_from_path()` 与 `execute()` 必须复用同一份计划生成逻辑，不能再复制一套三段式。

## Task 2：让 PlanCenter 拥有唯一的计划生成流程

**文件：**

- 修改：`ai-service/app/centers/plan_center.py`
- 测试：`ai-service/tests/test_plan_center_api_contract.py`
- 回归：`ai-service/tests/test_p1_agents.py`

**接口：**

```python
class PlanGenerationError(Exception):
    """计划生成完成但没有有效步骤，供 API 映射为现有 400 错误。"""

class PlanCenter:
    async def create_from_path(
        self,
        *,
        topic: str,
        course_id: str,
        student_profile: dict,
    ) -> dict: ...
```

**实现要求：**

- 提取一个共享私有方法，完成 Goal → Decompose → Schedule 并产出统一的计划 payload；`execute()` 与 `create_from_path()` 都调用该方法。
- `execute()` 继续返回 `CenterResult(event_type="plan")`，保持 `ResultAgent` 调用者不变。
- `create_from_path()` 在共享 payload 上补 `course_id`，将步骤转换为现有 API 所需格式，并返回纯 `dict`；Center 不返回 `JSONResponse`，不使用 FastAPI 类型。
- 将 `_enrich_steps_with_nodes()` 与 `_normalize_milestones()` 的领域逻辑迁入 `PlanCenter` 的私有方法，保持现有精确匹配、LLM 分类兜底、步骤排序和资源类型建议。
- 通过可选依赖注入支持离线测试：Center 可接收假的图谱服务和步骤分类器；未注入时仍调用现有 `get_graph_service()` 与 `categorize_exercises()`。
- 空 `steps` 时抛出 `PlanGenerationError`；不要在 Center 中构造 HTTP 400。

- [ ] **Step 1：添加 `PlanGenerationError` 和 `create_from_path()` 的失败测试目标。**

  先只声明异常和方法签名，使 Task 1 的导入及失败路径可运行；方法仍可临时抛出 `NotImplementedError`。不要改 API。

- [ ] **Step 2：抽取共享的三段式生成方法。**

  将 `_run_new_plan()` 中的 Goal、Decompose、Schedule 顺序提取为一个只返回计划 payload 的私有方法。`_run_new_plan()` 调用它后封装既有 `CenterResult`；不要保留第二份 Agent 调用代码。

- [ ] **Step 3：实现步骤匹配与里程碑标准化。**

  将 API 中的 `_enrich_steps_with_nodes()` 迁为 `PlanCenter` 私有方法，保持如下行为：

  - 先通过动态图谱节点 `name/id` 精确匹配；
  - 未匹配步骤在静态节点存在时调用 `categorize_exercises` 兜底；
  - 每个输出步骤均有 `step_order`、`topic`、`knowledge_node_id`、`status`、`estimated_days`、`topic_difficulty`、`suggested_resource_types`；
  - 最终按 `step_order` 排序；
  - 字符串里程碑转换为 `milestone_id`、`after_step`、`description`；已规范的字典里程碑原样保留。

- [ ] **Step 4：实现 `create_from_path()`。**

  它必须返回：

  ```python
  {
      "course_id": course_id,
      "total_steps": len(plan_steps),
      "steps": plan_steps,
      "title": payload["title"],
      "milestones": normalized_milestones,
      "estimated_days": payload["estimated_days"],
      "daily_capacity": payload["daily_capacity"],
      "concept_graph": payload["concept_graph"],
      "summary": payload["summary"],
  }
  ```

  当 Schedule 返回空步骤时，抛出 `PlanGenerationError("未能生成学习计划，请确认输入更具体")`。

- [ ] **Step 5：运行 Center 级回归。**

  ```powershell

  pytest tests/test_plan_center_api_contract.py tests/test_p1_agents.py::TestPlanCenterP1 -q
  ```

  预期：通过；不需要网络或真实 LLM。

- [ ] **Step 6：提交 Center 收口。**

## Task 3：让 API 只调用 PlanCenter

**文件：**

- 修改：`ai-service/internal_api.py`
- 测试：`ai-service/tests/test_plan_center_api_contract.py`

**接口：**

```python
def _get_plan_center() -> PlanCenter: ...
```

该惰性工厂使用 `_get_mock_flag()` 构造 Goal、Decompose、Schedule Agent，并创建单例 `PlanCenter`。它只负责依赖装配，不承担业务顺序。

- [ ] **Step 1：增加 `_get_plan_center()` 单例工厂。**

  在 `internal_api.py` 的既有 singleton 区域增加 `_plan_center_singleton` 和锁。第一次调用时按当前 mock 配置构造：

  ```python
  PlanCenter(
      goal_agent=GoalAgent(use_mock_llm=_get_mock_flag()),
      decompose_agent=DecomposeAgent(use_mock_llm=_get_mock_flag()),
      schedule_agent=ScheduleAgent(use_mock_llm=_get_mock_flag()),
  )
  ```

  仅在该工厂中允许为 PlanCenter 装配这些依赖。

- [ ] **Step 2：缩短 `create_plan_from_path()` 路由。**

  路由函数只执行：

  1. 从 `body` 读取 `topic`、`course_id`、`student_profile`；
  2. 调用 `await _get_plan_center().create_from_path(...)`；
  3. 用 `api_success(result)` 返回成功结果；
  4. 捕获 `PlanGenerationError` 并保持现有 HTTP 400 / `GENERATION_FAILED`；
  5. 捕获其他异常并保持现有 HTTP 500 / `INTERNAL_ERROR`。

  删除该路由函数中所有 Agent 构造、Goal/Decompose/Schedule 顺序、`_enrich_steps_with_nodes()` 调用和 `_normalize_milestones()` 调用。

- [ ] **Step 3：从 API 删除已迁出的私有计划生成辅助函数。**

  删除 `_enrich_steps_with_nodes()` 与 `_normalize_milestones()`；保留 `_compute_next_milestone()`，因为计划状态端点仍使用它。

## 完成条件

本方案完成的唯一判定是同时满足：

1. `PlanCenter` 是 Goal → Decompose → Schedule 的唯一业务编排位置；
2. `/internal/plans/create-from-path` 保持原有请求与响应契约；
3. API 路由不再包含计划步骤匹配、里程碑标准化和 Agent 执行顺序；
4. 离线契约测试通过；
5. 真实服务回归与手工请求均有可审计记录，或明确标注为未执行，不能以测试替代真实验证。

本方案不自动授权开始资源域、统一聊天、流式事件或 API 文件拆分的修改；它们必须在计划域验收完成后另立实施方案。
