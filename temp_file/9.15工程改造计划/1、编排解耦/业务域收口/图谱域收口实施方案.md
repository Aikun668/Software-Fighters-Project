# 图谱域收口实施方案

> 编写日期：2026-09-19
> 依据：`1、编排解耦` 路线图第 4 项「图谱接口收口（/graph/*，20 个端点）—— 纯搬运，独立好做」
> 前序轮次：聊天域 → 资源域 → 练习域 → 计划域（含剩余端点）均已收口
> 本轮目标：新增 `GraphCenter` 作为图谱域唯一业务入口，14 个图谱端点收窄为「校验 → 一个 Center 调用 → 序列化」，响应字节零变化（Java 是主要消费方）

## 零、现状摸底结论（先于方案）

### 0.1 端点数量：**14 个，不是路线图写的 20 个**

| 前缀 | 数量 | 端点 |

| `/graph/*` | 12 | `extract` / `nodes` / `masteries` / `reload` / `next-node` / `progress` / `check-prerequisites` / `nodes/{id}/delete` / `nodes/{id}/update` / `suggest-edges` / `export-mermaid` / `layered` |

### 0.2 代码现状：**已经比较薄，「纯搬运」基本成立**

- 14 个路由体合计 **138 行**（可执行体净行数），平均 ~10 行
- 全部已经在调 `internal_api._get_graph_service()`（`/graph/reload` 除外，见 0.6）
- 业务算法都在 `app/services/graph_service.py`（828 行），**图谱域没有 Center**，是 API → **Service 直连**

**但 14 个里有 4 个带真实内联逻辑**，不是零逻辑透传：

| 端点 | 行数 | 内联逻辑 |
| --- | --- | --- |
| `/graph/extract` | 16 | 调 LLM 抽取 `extract_knowledge_nodes` + 手工拼 `primary/related/broad/candidates` 四键 |
| `/graph/nodes` | 14 | `for update in body.updates` 循环 + `add_node`/`add_edge` 分支 dispatch |

其余 10 个是「调 service → 包一层信封 → `api_success`」，各 7~9 行。

### 0.3 `GraphService` 是**有状态单例**——这是与前四个域最大的不同

```python
class GraphService:
    def __init__(self):
        self._skeleton_cache = None              # 内存骨架缓存
        self._original_skeleton_node_ids = set() # 骨架节点白名单（不可删）
```

- `load_skeleton()` 首次读 `SKELETON_PATH`（JSON 文件）后**缓存进内存**
- `add_node` / `add_edge` / `delete_node` / `update_node` **只改 `_skeleton_cache`，没有任何写盘**
- 全文件搜索无 `save` / `write` / `json.dump` 回 `SKELETON_PATH`

**推论（现有行为，必须原样保住）**：
1. 运行时通过 `/graph/nodes` 加的节点，**进程重启即丢失**
2. 调一次 `/graph/reload`（`force_reload=True`）会把**所有运行时改动全部抹掉**
3. 前端看到的图谱是「骨架 + 本次进程内的临时改动」

前四个域的 Service 全是无状态纯函数，**这轮不是**。搬运时必须原样保住单例生命周期、`load_skeleton()` 调用时机、以及内存变异语义。

### 0.6 两个结构上的「暗坑」（收窄时必须原样保留）

**坑 1：双单例，`/graph/reload` 绕过内层**

```python
# internal_api.py:798
def _get_graph_service():          # 外层单例 _graph_service_singleton
    ...
    _graph_service_singleton = get_graph_service()   # 内层单例 _graph_service
    return _graph_service_singleton

# internal_api.py:894  /graph/reload
async def reload_graph(body):
    from app.services.graph_service import get_graph_service   # ← 直接调内层
    graph_service = get_graph_service()                        # ← 在 try 之外
    try:
        graph = graph_service.load_skeleton(force_reload=True)
```

两个工厂返回**同一个对象**，所以行为一致；但 `get_graph_service()` 这一行**在 `try` 之外**，搬运时若挪进 Center，异常路径会变。

**坑 2：`/graph/masteries` 没有 try/except，且它的 400 分支是死代码**

```python
async def update_masteries(body):
    if not body.events:                                    # ← 不可达
        return api_error(ErrorCode.INVALID_REQUEST, "events 不能为空", status_code=400)
    plan_service = get_plan_service()
    result = dict(body.masteries)
    for event in body.events:
        ...                                                # ← 裸跑，无 try
```

实测（本轮已验证）：

```text
POST /internal/graph/masteries  {"events": []}
→ 400 {"success":false,"error":"字段 'events' List should have at least 1 item after validation, not 0","error_code":"INVALID_REQUEST"}
```

`MasteryUpdateRequest.events` 带 `min_length=1`，`main.py:42` 注册了 `RequestValidationError` 处理器 —— 空列表在**进路由之前**就被 Pydantic 拦下。所以路由里那个 `if` 是**不可达的死代码**，且这个端点**任何内部异常都会以 FastAPI 默认 500 形式抛出**，body 形状与其它端点的 `api_error` 不同。

## 一、这次要解决什么

把图谱域收进与其它四域一致的形状：

```
现在：  HTTP → internal_api 路由（14 个，含 4 处内联逻辑）→ GraphService（直连）
目标：  HTTP → internal_api 路由（14 个，仅校验+序列化）→ GraphCenter → GraphService
```

**要解决的核心问题**：
1. 图谱域是唯一一个 **API 直连 Service、没有 Center** 的域，破坏了「API 只做协议适配」的统一边界
2. `/graph/extract`、`/graph/nodes`、`/graph/masteries`、`/graph/reload` 的编排逻辑长在路由里
3. 图谱域**没有 API 层契约测试**，14 个端点的字节契约无守护

**不解决**（不是本轮目标）：`GraphService` 的「不写盘 / reload 抹改动」行为、双单例、图谱数据模型、前端布局。

| # | 决策点 | 我的建议 | 理由 |
| --- | --- | --- | --- |
| 1 | `/knowledge-graph/*` 两个端点是否纳入本轮 | **纳入** | 与 `/graph/*` 共用同一个 `GraphService`，拆两轮会割裂同一个域；路线图说 20 个，实际 14 个，一并做完更干净 |
| 2 | 4 个零消费端点（reload / delete / update / suggest-edges）怎么办 | **同等收口 + 同等字节锁定，不删除** | 与计划域轮次同策略（`node-status-change`、legacy `/plans/status`）。删除会破坏 Java `PythonClient` 的潜在调用；但它们属**非用户可见改善**，验收记录里如实标注 |
| 3 | 双单例（`_get_graph_service()` 包 `get_graph_service()`）是否一并合并 | **不动，登记** | `/graph/reload` 绕过外层，合并会改变调用路径；且 `PlanCenter` / `PathAgent` / `VisualizationCenter` 也直连内层。本轮只登记为遗留项 |

| 5 | `update_masteries` 跨域调 `PlanService.update_mastery` 怎么处理 | **`GraphCenter` 持 `plan_service` 引用，默认 `get_plan_service()`** | 与 `PlanCenter(plan_service=None → PlanService)`、`PlanCenter(exercise_center=...)` 先例一致；`update_mastery` 是纯静态函数，无 I/O 风险 |
| 6 | `/graph/extract` 归 `GraphCenter` 还是已有聊天域的 `ChatCenter` | **归 `GraphCenter`** | 两者是**不同入口**：`/graph/extract` 是 Java 显式同步调用；`ChatCenter.stream_chat` 是聊天侧派生推荐事件。底层同一个 `extract_knowledge_nodes` 函数，互不冲突，不必合并 |
| 7 | 错误映射（400 / 404 / 500 分流）怎么摆 | **Center 原样抛 `ValueError`，API 按路由现有映射处理** | 同样是 `ValueError`，`/knowledge-graph/.../node/...` 映射 **404**，`/graph/nodes*` 映射 **400** —— 分流规则在 API，逐路由保持原样即可零风险。不引入新异常类，避免改变既有 `except ValueError` 的捕获范围 |

# internal_api.py 新增（与 _get_plan_center 同款双检锁）
_graph_center_singleton = None

### 5.5 测试隔离策略（**本方案最关键的一节**）

因为 `GraphService` 是有状态单例，隔离分三层：

**① `GraphCenter` 单测**：`GraphCenter(graph_service=GraphService())` —— 每例新实例，与 `test_graph_service.py` 既有做法一致，天然隔离。

**② HTTP 层契约测试 / ASGI 委派测试**：必须替换**模块级单例**，且要**同时覆盖两条路径**：

```python
fresh = GraphService()
mp.setattr(internal_api, "_graph_service_singleton", fresh)          # 13 个走 _get_graph_service() 的路由
mp.setattr("app.services.graph_service._graph_service", fresh)       # /graph/reload 直连的那条
```

> **只 patch 一处会漏**：`/graph/reload` 走 `app.services.graph_service.get_graph_service()` → 返回内层单例 `_graph_service`；其它 13 个走 `internal_api._get_graph_service()` → 若 `_graph_service_singleton` 已被前一个用例填充，patch 内层无效。**两处都要设**。

**③ 变更类用例的顺序约束**：`/graph/nodes`（add_node）、`/graph/nodes/{id}/delete`、`/graph/nodes/{id}/update`、`/graph/reload` 会**永久改变该实例的内存骨架**，进而改变同一实例后续 `/graph/layered`、`/graph/progress`、`/graph/export-mermaid` 的输出。所以：

- 每个测试用例用**自己的 fresh 实例**（fixture 级），用例之间零耦合
- 字节存证 harness 若共用一实例，**用例顺序必须固定**，且 before / after 两次运行**同序**

## 十、已知风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | **单例可变状态污染**（最高）：变更类端点永久改内存骨架，污染同进程后续用例 | 每例 fresh `GraphService()`；harness 用例顺序固定且 before/after 同序 |
| 2 | **双路径单例**：`/graph/reload` 绕过 `_get_graph_service()`，只 patch 一处会漏 | §5.5 明确两处都设；KG-C03 专门锁定 reload 语义 |
| 3 | **`/graph/masteries` 无 try/except**：收窄时若顺手补上，异常响应 body 形状从 FastAPI 默认 500 变成 `api_error` 信封 | 决策点 4 明确不补；KG-A12/A13 锁定现状 |
| 4 | **`if not body.events` 是死代码**：若误以为是活分支并为它写用例，会得到"永远不触发"的假通过 | 本轮已实测确认为 Pydantic 400；KG-A13 直接锁定实测事实 |
| 5 | **`/graph/reload` 的 `get_graph_service()` 在 try 之外**：挪进 Center 会改变异常路径 | Center 内统一在 `reload_skeleton()` 里调，异常由 API 的 `except Exception` 兜住；KG-A15 锁定 500 文案 |
| 6 | **键序漂移**：8 组信封键的插入顺序即 JSON 字节顺序 | Part A 断言完整响应体（`response.text` 级），非逐字段 |
| 7 | `extract_knowledge_nodes` 是 LLM 调用，harness / 用例触网会挂 | 全部注入替身；harness 绝不触网 |
| 8 | `delete_node` / `update_node` 依赖 `load_skeleton()` 初始化的 `_original_skeleton_node_ids`，搬运时改变调用时机会让「骨架节点不可删」失效 | Center 只转发参数，不改调用顺序；KG-A23 / KG-B11 锁定 |
| 9 | 14 端点一起改，回归面大 | 按 Task 2（读 8）/ Task 3（写 5 + 抽取 1）两批提交，每批提交前只跑受影响文件 |

## 十一、与路线图的偏差说明

路线图写「20 个端点，纯搬运，独立好做」，实际摸底结论是：

- **数量**：14 个（12 `/graph/*` + 2 `/knowledge-graph/*`），不是 20
- **「纯搬运」**：10 个是，4 个带内联编排逻辑（extract / nodes / masteries / reload）
- **「独立好做」**：端点确实独立（不依赖其它域），但 **`GraphService` 的有状态单例**是本轮特有的坑，比前面四个域更需要小心——前四域的 Service 都是无状态纯函数
