# 计划域收口 P1.1 终结行动计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 在不改变计划 API 对外契约、不进入资源域或聊天改造的前提下，消除 `PlanCenter` 内部重复的 Goal → Decompose → Schedule 编排，并保证图谱服务或分类器不可用时不丢失已生成的计划步骤。

**架构：** `PlanCenter` 只保留一个异步基础计划编排方法，负责调用三段 Agent 并产出未增强的标准计划 payload。`execute()` 将该 payload 包装为既有 `CenterResult`；`create_from_path()` 在同一 payload 上叠加步骤图谱匹配和里程碑标准化。图谱增强失败只能降级为“保留原步骤、节点 ID 为空”，不得把非空计划变成空计划。

**技术栈：** Python、FastAPI、pytest、现有 `PlanCenter`、GoalAgent、DecomposeAgent、ScheduleAgent、GraphService、`categorize_exercises`。

## 全局约束

- 本轮只修改计划域相关代码与测试。
- 保持 `/internal/plans/create-from-path` 的路径、请求字段、成功包装、400 `GENERATION_FAILED` 和 500 `INTERNAL_ERROR` 不变。
- 保持 `PlanCenter.execute(CenterTask)` 的 `CenterResult` 调用方式和聊天侧“不触发图谱增强”的现有行为不变。
- 不新增 Agent、Center、Workflow、接口、数据库字段或第三方依赖。
- 不修改 `_compute_next_milestone()`，它仍由计划状态、今日任务、进度更新和节点状态端点使用。
- 任何图谱、分类器或 LLM 分类失败都只能降低增强信息，不得删除原始 `ScheduleAgent` 步骤。

## 现存问题与完成定义

### 问题 1：Center 内仍重复三段式编排

当前 `PlanCenter._run_new_plan()` 与 `PlanCenter.create_from_path()` 分别包含 Goal → Decompose → Schedule 调用。虽然 API 已不再重复实现该流程，但 Center 内仍有两份相同的 Agent 编排，未来修改 Agent 输入、默认值、异常降级或 `existing_plan` 时仍可能分叉。

### 问题 2：图谱降级可能丢失步骤

`_enrich_steps_with_nodes()` 将未精确匹配的步骤收集为 `unknowns`。当前只有在 `unknowns and all_nodes` 成立时才将它们放回输出；当 GraphService 不可用、骨架为空或没有可分类静态节点时，`unknowns` 不会回填，非空原计划可能被错误变成空步骤列表。

### P1.1 完成定义

```text
Goal → Decompose → Schedule 在 PlanCenter 中只有一个异步编排实现；
execute() 与 create_from_path() 都复用它；
图谱增强失败时，返回步骤数量与 ScheduleAgent 原始步骤数量一致；
API 契约、现有聊天计划结果与真实 create-from-path 结果不退化。
```

## Task 1：抽出唯一的基础计划编排方法

**文件：**

- 修改：`ai-service/app/centers/plan_center.py`
- 修改：`ai-service/tests/test_plan_center_api_contract.py`
- 回归：`ai-service/tests/test_p1_agents.py`

**目标接口：**

```python
async def _generate_base_plan(
    self,
    *,
    user_input: str,
    topic: str,
    context: str,
    student_profile: dict,
) -> dict:
    """唯一执行 Goal → Decompose → Schedule 的位置，返回未增强 payload。"""
```

该方法负责：

1. 调用 GoalAgent，并将失败降级为当前 topic 的默认 goal；
2. 调用 DecomposeAgent，并将失败降级为空 decomposition；
3. 调用 ScheduleAgent；失败时抛出一个内部领域异常供调用者映射；
4. 通过已有 `_build_plan_payload()` 返回未增强 payload；
5. 不读取图谱、不调用分类器、不构造 `CenterResult`、不构造 HTTP 响应。

`_run_new_plan()` 与 `create_from_path()` 不再直接调用任一三段 Agent。

- [ ] **Step 1：先扩展离线测试，证明两个公共路径复用同一个编排方法。**

  在 `test_plan_center_api_contract.py` 中 patch `center._generate_base_plan` 为 `AsyncMock`，分别调用：

  ```python
  await center.execute(center_task)
  await center.create_from_path(
      topic="Transformer",
      course_id="ai_intro",
      student_profile={},
  )
  ```

  分别断言 `_generate_base_plan.assert_awaited_once()`。两条测试分别独立构造 Center，避免调用计数混淆。

- [ ] **Step 2：运行新增测试，确认当前实现失败。**

  ```powershell
  cd ai-service
  pytest tests/test_plan_center_api_contract.py -q
  ```

  预期：失败，因为当前没有 `_generate_base_plan()`，且两条公共路径各自直接调用三段 Agent。

- [ ] **Step 3：实现 `_generate_base_plan()`。**

  迁移当前两条路径中相同的 Agent 调用和默认值，使用以下输入差异：

  | 调用者 | `user_input` | `topic` | `context` |
  | --- | --- | --- | --- |
  | `_run_new_plan()` | `task.input` | 原 `topic` | `task.params.get("context", "")` |
  | `create_from_path()` | `topic` | 原 `topic` | `""` |

  方法返回 `_build_plan_payload()` 的结果；调用者不得再次组装同一 payload。

- [ ] **Step 4：改造 `_run_new_plan()`。**

  它只调用 `_generate_base_plan()`，然后以返回 payload 构造既有：

  ```python
  CenterResult(
      mode="plan",
      intent=task.intent,
      event_type="plan",
      payload=payload,
      agent="GoalAgent+DecomposeAgent+ScheduleAgent",
      sequence=task.sequence,
  )
  ```

  若基础编排失败，保持当前用户可见错误 `"计划编排失败"` 与 `CenterResult(event_type="error")`。

- [ ] **Step 5：改造 `create_from_path()`。**

  它只调用 `_generate_base_plan()`，再检查 `payload["steps"]`。步骤为空时保持抛出：

  ```python
  PlanGenerationError("未能生成学习计划，请确认输入更具体")
  ```

  非空步骤继续进入 Task 2 的图谱增强与里程碑标准化。

- [ ] **Step 6：执行结构搜索和离线回归。**

  ```powershell

  pytest tests/test_plan_center_api_contract.py tests/test_p1_agents.py::TestPlanCenterP1 -q
  ```

  预期：三类 `.run` 各只出现在 `_generate_base_plan()`；测试全部通过，允许既有 1 个 skip。

- [ ] **Step 7：提交。**

## Task 2：图谱增强失败时保留原始步骤

**文件：**

- 修改：`ai-service/app/centers/plan_center.py`
- 修改：`ai-service/tests/test_plan_center_api_contract.py`

**目标：** `_enrich_steps_with_nodes(steps, course_id)` 无论图谱是否可用，都返回与输入 `steps` 相同数量、相同顺序的步骤。增强失败只允许 `knowledge_node_id` 为空，不能丢步骤。

- [ ] **Step 1：写“图谱不可用”回归测试。**

  注入假的 `graph_service`，令 `load_skeleton()` 抛出 `RuntimeError("graph unavailable")`；输入两个原始步骤。断言：

  ```python
  result = await center._enrich_steps_with_nodes(steps, "ai_intro")
  assert len(result) == 2
  assert [step["topic"] for step in result] == ["注意力机制", "编码器"]
  assert all(step["knowledge_node_id"] == "" for step in result)
  assert all("suggested_resource_types" in step for step in result)
  ```

- [ ] **Step 2：写“静态节点为空”回归测试。**

  令 `load_skeleton()` 返回 `{"nodes": []}`、`_all_nodes()` 返回 `[]`。断言两个未知步骤仍全部返回；同时断言分类器未被调用。

- [ ] **Step 3：写“分类器失败”回归测试。**

  令静态节点非空、动态图谱无精确匹配，注入抛出 `RuntimeError("classifier unavailable")` 的 async classifier。断言输入的两个未知步骤仍全部返回、按 `step_order` 排序、节点 ID 为空。

- [ ] **Step 4：写“多个未知步骤分类结果映射”测试。**

  注入返回以下结果的分类器：

  ```python
  [
      {"index": 0, "knowledge_node_id": "node-a"},
      {"index": 1, "knowledge_node_id": "node-b"},
  ]
  ```

  输入两个未知步骤，断言第一个得到 `node-a`，第二个得到 `node-b`。这条测试不能通过从 `exercise` 字典读取不存在的 `index` 构造返回值。

- [ ] **Step 5：实现保守回填。**

  重构 `_enrich_steps_with_nodes()`：

  1. 精确命中步骤直接写入 `plan_steps`；
  2. 若静态节点可用，尝试分类器，为 `unknowns` 建立 `result_map`；分类失败时使用空 `result_map`；
  3. 无论静态节点是否可用、分类器是否成功，均遍历全部 `unknowns` 并写入 `plan_steps`；
  4. 未匹配时使用 `knowledge_node_id=""`，并保留默认资源类型建议；
  5. 最后按 `step_order` 排序。

- [ ] **Step 6：运行增强与 API 契约测试。**

  ```powershell

  pytest tests/test_plan_center_api_contract.py -q
  ```

  预期：全部通过；图谱失败、空图谱和分类失败不再产生空步骤结果。

- [ ] **Step 7：提交。**


## 关闭标准

只有同时满足以下条件，计划域 P1 才可标记为真正关闭：

1. `PlanCenter` 中三类 Agent 的 `.run()` 调用只存在于 `_generate_base_plan()`；
2. `execute()` 与 `create_from_path()` 都调用 `_generate_base_plan()`；
3. 图谱不可用、空图谱、分类器异常时，增强结果的步骤数等于原始 Schedule 步骤数；
4. API 仍仅委派 `PlanCenter.create_from_path()`，保持既有 200 / 400 / 500 契约；
5. 离线回归通过，真实 HTTP 结果有记录，未执行项与风险没有被伪装为通过；
6. 本轮没有引入资源域、聊天路由、流式事件或 API 文件拆分变更。

P1.1 关闭后，才进入 `ResourceCenter` / `ResourceGenWorkflow` 的独立收口方案。
