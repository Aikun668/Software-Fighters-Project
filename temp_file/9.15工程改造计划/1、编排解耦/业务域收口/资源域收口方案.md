# 资源域收口方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 在保持资源生成与追问解析的接口、SSE 事件契约和资源产物不变的前提下，让 `ResourceCenter` 成为 `ResourceGenWorkflow` 的唯一业务入口，消除 API 内重复的资源工作流运行、队列管理和终态 payload 组装。

**架构：** `ResourceCenter` 统一拥有资源工作流状态构造、一次 `workflow.run()`、终态 payload 组装和业务级 `StreamEvent` 流。`internal_api.py` 保留请求校验、追问答案解析、SSE 序列化和 HTTP 响应；`/resources/generate` 与 `/inquiry/resolve` 都委派给同一个 `ResourceCenter`。现有 `ResourceGenWorkflow → Director → 专项资源 Agent` 内部关系不变。

**技术栈：** Python、FastAPI、asyncio、SSE、现有 `StreamEvent` / `done_event`、`ResourceCenter`、`ResourceGenWorkflow`、`InquiryService`、pytest。

**方向约束：** [产品主线与业务编排约束.md](../0、产品方向与约束/产品主线与业务编排约束.md)

## 全局约束

- 不新增或修改公开路径：`/internal/resources/generate`、`/internal/inquiry/resolve` 保持可用。
- `ResourceGenWorkflow` 仍是资源域内部多阶段 Workflow；`Director` 仍只负责其内部专项资源 Agent 选择，不能升级为全局路由器。
- 本轮不修改资源内容生成 Prompt、质量门控、专项 Agent、导出端点、前端、Java、统一聊天路由或统一事件模型。
- 资源工作流每个请求只能运行一次；不得为 SSE 显示或结果汇总再次调用 `workflow.run()`。
- 成功 `done` 事件继续包含：`content_blocks`、`questions`、`response`、`error`、`review_status`、`repair_attempted`、`fallback_used`、`final_status`。
- 工作流异常继续以资源生成失败终态结束；不得让 API 抛出未序列化异常或漏发 `done`。
- 直接资源生成保持“不先做 InquiryService 追问”的现有语义；聊天内 `ResourceCenter.execute()` 的追问判断保持不变；`/inquiry/resolve` 继续使用已解析的答案，不再重复追问。

## 现状与目标调用链

### 当前调用链

```text
/resources/generate
  → API 校验 topic
  → API 取得 ResourceGenWorkflow
  → API 创建 Queue / 后台 task
  → API 调 workflow.run(..., event_queue)
  → API 组装 done payload / 输出 SSE

/inquiry/resolve
  → API 调 InquiryService.resolve(...)
  → API 取得 ResourceGenWorkflow
  → API 再次创建 Queue / 后台 task
  → API 调 workflow.run(..., event_queue)
  → API 再次组装 done payload / 输出 SSE

统一聊天资源请求
  → ChatCenter / ResultAgent
  → ResourceCenter.execute()
  → ResourceGenWorkflow
```

问题不在于 Workflow 存在，而在于 API 与 Center 同时拥有“如何运行资源生成流程”的权力，且两条 API 链路复制 SSE 业务逻辑。

### 迁移后调用链

```text
/resources/generate
  → ResourceCenter.stream_generate(...)
      → ResourceCenter._run_generation(...)
          → ResourceGenWorkflow.run(...)
              → Director → 专项资源 Agent
  → API 将 StreamEvent 序列化为 SSE

/inquiry/resolve
  → API 调 InquiryService.resolve(...)
  → ResourceCenter.stream_generate(...)
  → API 将 StreamEvent 序列化为 SSE

统一聊天资源请求
  → ResourceCenter.execute()
  → ResourceCenter._run_generation(...)
```

`ResourceCenter` 是资源域唯一业务入口；API 只拥有协议与传输职责。

## Task 2：让 ResourceCenter 成为唯一资源工作流入口

**文件：**

- 修改：`ai-service/app/centers/resource_center.py`
- 测试：`ai-service/tests/test_resource_center_api_contract.py`
- 回归：`ai-service/tests/test_result_agent.py`

**接口：**

```python
async def _run_generation(
    self,
    *,
    user_id: int,
    topic: str,
    student_profile: dict,
    resource_type: str,
    event_queue: asyncio.Queue | None = None,
) -> dict: ...

async def stream_generate(
    self,
    *,
    user_id: int,
    topic: str,
    student_profile: dict,
    resource_type: str,
) -> AsyncIterator[StreamEvent]: ...
```

`_run_generation()` 是 Center 内唯一允许调用 `ResourceGenWorkflow.run()` 的位置；它只运行一次并返回 Workflow 最终 state。`stream_generate()` 管理业务事件队列并在最后发出兼容的 `done_event`；它不生成第二份资源。

- [ ] **Step 1：实现 `_run_generation()`。**

  它构造并传入：

  ```python
  {
      "user_id": user_id,
      "topic": topic,
      "student_profile": student_profile,
      "resource_type": resource_type or "",
  }
  ```

  `event_queue` 非空时才加入该键。Workflow 依赖使用 `self.resource_workflow`；未注入时才创建 `ResourceGenWorkflow()`。不要在 API 中创建 Workflow。

- [ ] **Step 2：实现终态 payload 私有方法。**

  新增纯方法 `_done_payload(state: dict) -> dict`，固定返回：

  ```python
  {
      "content_blocks": state.get("content_blocks", []),
      "questions": state.get("questions", []),
      "response": state.get("response", ""),
      "error": state.get("error", ""),
      "review_status": state.get("review_status", "not_applicable"),
      "repair_attempted": state.get("repair_attempted", False),
      "fallback_used": state.get("fallback_used", False),
      "final_status": state.get("final_status", "success"),
  }
  ```

  这取代两条 API 端点中重复的 `done_event({...})` 载荷组装。

- [ ] **Step 3：实现 `stream_generate()`。**

  使用大小为 256 的 `asyncio.Queue`。创建一个后台 producer：调用一次 `_run_generation(..., event_queue=queue)`，成功后向队列放入 `done_event(_done_payload(state))`；异常后记录日志并放入：

  ```python
  done_event({"error": "资源生成失败，请稍后重试"})
  ```

  consumer 持续 `await queue.get()`，逐个 `yield StreamEvent`，遇到 `done` 后停止并 `await producer`。使用 `try/finally`：若调用方在 `done` 前取消消费，取消尚未完成的 producer 并等待其结束，避免孤儿 Workflow。

- [ ] **Step 4：让 `execute()` 复用 `_run_generation()`。**

  保留它的 `InquiryService.check()`、不清晰时返回既有 `CenterResult(event_type="inquiry")` 的行为。清晰后只调用 `_run_generation()`；用其 state 构造既有 `CenterResult(event_type="resource")`。`execute()` 不调用 `stream_generate()`，避免聊天路径因为不消费队列而卡住。

- [ ] **Step 5：运行 Center 和 ResultAgent 回归。**

  ```powershell

  pytest tests/test_resource_center_api_contract.py tests/test_result_agent.py -q
  ```

  预期：通过；每个直接资源请求只有一次 `workflow.run()`。

## 关闭标准

资源域收口可关闭，必须同时满足：

1. `ResourceGenWorkflow.run()` 在资源业务代码中仅由 `ResourceCenter._run_generation()` 调用；
2. `/resources/generate` 与 `/inquiry/resolve` 均只委派 `ResourceCenter.stream_generate()`；
3. `ResourceCenter.execute()` 复用 `_run_generation()`，保持聊天资源请求的 Inquiry 判断；
4. 两条 API 入口均保留原有 SSE `done` 字段，并且每次请求恰好一个 `done`；
5. Workflow、图谱或质量门控异常不会造成空流、双终态或无限等待；
6. 离线契约测试和既有 SSE 测试通过，两个入口均有真实 SSE 和资源内容证据；
7. 本轮未修改资源内容质量、聊天路由、全局事件模型或 API 文件拆分。

资源域关闭后，下一项才是统一聊天路由收口；流式事件模型和 API 文件拆分继续作为后续独立方案。
