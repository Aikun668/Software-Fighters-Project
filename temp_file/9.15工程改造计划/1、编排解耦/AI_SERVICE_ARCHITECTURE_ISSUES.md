# Python AI Service：当前架构问题说明（宏观诊断）

## 文档目的

本文件只说明当前结构中已经暴露的问题、影响和优先级，不提供具体代码改法。判断依据是已梳理出的真实调用链与模块职责，而不是对每一行源码的审计；因此它适合作为后续重构讨论的共同背景，不应被当作精确的代码清单。

## 当前系统的真实形态

项目同时存在三类请求链路：

| 代表请求 | 当前主链路 | 特征 |
| --- | --- | --- |
| `/tutor/chat` | HTTP Router → `TutorAgent` → LLM | 直接调用 Agent，绕过 Center、Workflow、Orchestration |
| `/resources/generate` | HTTP Router → `ResourceGenWorkflow` → `Director` → 专项 Agent → LLM | 直接调用 Workflow，资源 Agent 的选择发生在 Workflow 内 |
| 统一聊天/部分任务 | HTTP Router → Router/Result/Center → Agent 或 Workflow | 使用 Center 级分发和手写任务编排 |

同时，`internal_api.py` 约 2400 行、48 个端点，混合了路由、计划业务、Agent/Workflow 调用、SSE、多模态、安全校验、数据转换、单例管理和错误处理。

## 一句话结论

当前主要问题不是单纯“文件太大”，而是：

> 同一个业务能力存在多条进入路径，多个层同时拥有路由或编排权；`internal_api.py` 因此同时承担了接口层、业务层和编排层的职责。

大文件是这个问题最明显的外在表现；真正的风险来自职责边界和唯一入口不清楚。

## 问题一：业务编排入口不唯一

同一个系统内，HTTP 路由可以直接调用 Agent、直接调用 Workflow、调用 Center，甚至在自身内部手写业务顺序。于是“一个请求应该经过哪一层”没有统一答案。

这会造成：

- 调试时不能从固定入口追踪问题；不同端点的定位方式不同。
- 横切能力（日志、鉴权、画像、降级、埋点、限流、事件规范）容易漏接在某些直连链路上。
- 新功能更容易继续在 API 层直接拼接，形成新的旁路。
- 同一业务在不同入口下可能出现参数、返回、异常处理不一致。

这不是说所有请求都必须经过所有层。问题在于：每个业务域缺少一个**明确且唯一的主业务入口**。

## 问题二：编排职责分散，并且存在明确重复

当前执行顺序由多处控制：

- `ResultAgent` 负责多个 CenterTask 的顺序；
- `ResourceGenWorkflow` 负责资源生成的多阶段状态流；
- `PlanCenter` 负责 Goal → Decompose → Schedule；
- `internal_api.py` 的计划端点又复制了一遍 Goal → Decompose → Schedule。

其中“计划三段式”是同一逻辑的明确重复实现。资源生成也有 `ResourceCenter` 包装 Workflow 与端点直接调用 Workflow 两种入口。

后果是修改一处后另一处不一定同步，最终同一功能会逐步分叉。代码看似可运行，但长期会出现“为什么 A 接口正常、B 接口同样功能却不正常”的隐性成本。

## 问题三：路由、分类与命名语义混杂

当前至少有两套“决定下一步执行什么”的机制：

| 模块 | 实际职责 | 评价 |
| --- | --- | --- |
| `RouterAgent` + `intent_extractor` | 识别意图并选择 Center/任务 | 属于请求级分发 |
| `Director` | 为资源生成选择专项资源 Agent | 属于资源工作流内部选择 |
| `domain_router` | 判断内容属于 AI 领域还是通用领域 | 属于内容分类，不是执行路由 |

它们的作用域并不完全相同，因此不能粗暴合并成一个“万能路由器”。但现在名字、关键词规则和使用边界容易让人误以为它们可互相替代；其中请求级和资源级还各自维护一套关键词决策，缺少清晰的所有权。

特别是 `Director` 这一名称在不同位置指代不同逻辑，会增加理解和维护难度。

## 问题四：`internal_api.py` 是 Fat Controller

`internal_api.py` 的问题不只是端点数量多，而是其内部职责跨越了多个层次：

- HTTP 请求/响应与错误格式；
- SSE 事件生成和清洗；
- 模型白名单、SSRF、文件路径等安全校验；
- 多模态消息解析；
- Agent、Workflow、Service 的构造与调用；
- 计划、里程碑、任务状态、掌握度、图谱匹配等领域业务；
- 状态字典到接口/SSE 载荷的转换；
- 多个单例的懒加载与锁。

其中计划相关端点约占 800 行，是一个实际藏在接口文件里的“Plan 服务”。这导致：

- 业务规则无法脱离 HTTP 单独测试；
- 路由文件修改范围大，容易引入无关回归；
- SSE、错误处理和参数转换被复制到多个端点；
- 文件虽然能“拆开”，但若业务逻辑不先迁出，只会变成多个小型 Fat Controller。

## 问题五：状态机的层级边界尚未固定

Workflow 与部分 Agent 都使用 LangGraph：Workflow 维护跨阶段的业务状态，Agent 又维护自身的检索/回答等局部状态；Center 则使用手写 `if/else` 和任务循环。

这本身不必然错误。关键问题是系统没有明确规定：

- 什么任务必须使用 Workflow；
- Agent 内部 LangGraph 的状态允许覆盖到什么范围；
- Center 是否只做业务入口与委派，还是也能做多步骤编排；
- 手写顺序控制何时可以存在。

没有规则时，新功能会按开发者当时最方便的方式落在任意一层，层级会继续膨胀。

## 对系统造成的实际风险

| 风险 | 具体表现 |
| --- | --- |
| 行为分叉 | 两个入口实现同一计划/资源能力，修复或规则变更可能只生效一处 |
| 调试成本高 | 无法从“端点 → 固定业务入口”稳定追踪；每类端点走法不同 |
| 测试困难 | 业务逻辑嵌在 HTTP 与 SSE 中，难以做快速单元测试 |
| 可观测性不完整 | 直连链路可能绕过统一日志、画像、能力门控或事件规范 |
| 重构风险扩大 | 一次小修改会牵动 API、Center、Workflow、Agent 多处，难判断真实影响 |
| 认知负担 | 新成员需要先猜各层职责，目录名无法可靠反映实际职责 |

## 需要保留的事实与非问题

以下内容不应被误判为“必须删除”：

- 简单聊天直接形成“检索 → 回答”的局部流程是合理的；问题是它需要有统一的业务入口，而不是 API 任意直连。
- 请求级分发和资源工作流内部的专项 Agent 选择属于不同粒度，可以同时存在。
- Workflow 维护跨阶段状态、Agent 维护自身局部状态也可以共存，前提是边界写清楚。
- 不需要为了目录整齐而大规模推倒重写；当前更适合渐进式收敛。

## 本轮重构应优先解决的范围

1. 同一种业务能力只保留一个主业务入口。
2. API 层不再承担业务编排与领域规则。
3. 消除计划三段式的重复实现，并收敛资源生成的双入口。
4. 明确请求级路由、领域分类、资源 Agent 选择这三类决策的边界。
5. 在逻辑迁出后，再把 `internal_api.py` 拆成按业务域组织的内部接口包。

本轮不以“换框架”“全部改成 LangGraph”“删除所有 Center/Director”为目标。先让每种权力只由一层拥有，系统才会真正安静下来。
