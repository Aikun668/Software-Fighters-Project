# 聊天域编排验收方案

> **用途**：在《聊天域编排收口方案》实施完成后，验收统一聊天接口的业务入口、路由边界、流式事件、终态责任和真实用户可见结果。本文件是验收方案，不是测试结果；所有未执行项必须保留为“未执行”。

**对应实施方案：** [聊天域编排收口方案.md](聊天域编排收口方案.md)

**验收对象：** `/internal/api/chat`，以及它调用的 `ChatCenter → ResultAgent → 业务 Center` 链路。

**本轮不验收：** 资源 Prompt、资源质量门控、Java 联调、前端代码改造、全局事件基础设施、LangGraph 全量 streaming、数据库持久化和无关历史文件清理。

## 一、验收结论规则

聊天域编排只有在以下四类证据都满足时，才能标记为“收口通过”：

1. **结构证据**：API 不再拥有聊天业务编排和终态拼装权，`ChatCenter.stream_chat()` 是统一聊天唯一业务入口。
2. **离线行为证据**：普通聊天、能力路由、事件顺序、错误和取消行为通过不依赖真实 LLM 的测试。
3. **HTTP/SSE 证据**：真实 FastAPI/Starlette 请求可以收到正确的 SSE 事件、中文内容和唯一 done。
4. **人工结果证据**：至少检查普通中文对话和一个明确能力请求的用户可见结果；不能只凭 HTTP 200 或 pytest 通过结论。

证据状态必须使用以下三种之一：

| 状态 | 含义 |
| --- | --- |
| 通过 | 已执行并获得符合预期的证据 |
| 失败 | 已执行但不符合预期，必须记录现象和阻塞项 |
| 未执行 | 因环境、权限、真实 LLM、Java/前端不可用或超出范围而没有执行；不得写成通过 |

### 4.1 目标调用链

验收目标：

```text

  → API 校验与 sanitize

          → 对应业务 Center
```

### 5.2 流式事件与终态

成功普通聊天：

```text
center_start
→ token* 或 content*
→ center_end
→ recommendation? 
→ done
```

成功结构化能力：

```text
center_start
→ center_end / content
→ done.data 携带真实结构化产物
```

失败：

```text
已有事件*
→ error
→ done
```

逐项检查：

- [x] 最后一个业务事件始终是 `done`。
- [x] 每个请求的 `done` 恰好一个。
- [x] `error` 事件包含前端和 Java 可读取的 `content` 文本。
- [x] 业务 Center 已产生结构化产物时，即使没有 token，也不能补发“模型未返回有效内容”。
- [x] 追问事件是合法产出，不被误判为空回答。
- [x] 推荐事件如果出现，位置在最终 done 之前。
- [x] 推荐抽取超时后仍能在预算内收到 done。
- [x] 内部多 done 不会向外暴露多个 done。
- [x] 内部没有 done 时，聊天域只补发一个 done。

## 十、失败处理与遗留风险

### 10.1 任一关键项失败时

- 停止把聊天域标记为完成。
- 保存请求、原始 SSE、日志和最小复现步骤。
- 标明失败属于结构、离线行为、HTTP/SSE、真实 LLM、人工结果还是环境问题。
- 不通过修改测试断言或屏蔽异常来制造通过结果。
- 先修复唯一 owner 和终态责任，再扩大测试范围。

### 10.2 必须单独记录的未执行项

- [x] 真实 LLM 普通聊天。（LLM key 不可用）
- [x] 真实 LLM 明确能力请求。（同上）
- [x] Java → Python → 前端完整链路。（Java/前端不在本轮范围）
- [x] 浏览器人工检查。（需前端环境）
- [x] 真实网络断开后的后台取消。（离线取消测试已覆盖逻辑层，真实网络行为未测）
- [x] LangGraph 原生 streaming。（属下一阶段）
- [x] 高并发、背压、断线重连和事件回放。（不在本轮范围）

这些项目不属于本轮“聊天接口编排收口”的自动通过条件，但必须作为后续风险保留。
