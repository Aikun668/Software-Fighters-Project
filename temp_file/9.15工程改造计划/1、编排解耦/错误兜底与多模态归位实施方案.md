## 二、摸底结论

### 2.1 多模态：是一个**零调用的纯能力**，不是业务流程

`internal_api.py` L369–416，共三个符号 48 行：

| 符号 | 行 | 内部调用 | 外部调用 |
|---|---|---|---|
| `ALLOWED_IMAGE_MIMES` | L371 | 1 处（`_build_multimodal_message` 内） | 0 |
| `_extract_text_from_multimodal` | L374–380 | **0** | **0** |
| `_build_multimodal_message` | L383–415 | **0** | 2 处（均为测试资产） |

关键事实：

1. **`internal_api.py` 内 0 处调用。** 全文件搜 `images` 只命中这三个符号自身的函数体。没有任何端点调用它。
2. **`UnifiedChatRequest.images` 被声明但从未读取**（`app/api/models.py:113`，注释写「Java 传入，可选」）。即：Java 传图片进来会被 schema 收下、`sanitize_model` 放过、然后静默丢弃。
3. `app/` 全包搜 `multimodal` / `image_url` —— **0 命中**。多模态能力目前只存在于这一个函数里。
4. 唯一两个调用点都在测试侧：
   - `tests/test_sse_shared_facilities_contract.py:455–460`（A10/A11 SSRF 判定）
   - `_accept_sse_all_endpoints.py:186`（未跟踪字节探针）

**结论：这不是「搬一段业务逻辑」，是「把一个纯函数归位」。** 与 `_sse_sanitize` 同型 —— **归位不接线**。接线（让 `/api/chat` 真的把 `body.images` 喂进去）是另一件事，本轮不做，只在验收记录里登记。

> ⚠️ 上一轮 `test_sse_shared_facilities_contract.py` 的 docstring 写明：「注入点全部选在『抽取前后都存在』的符号上（…、`internal_api._build_multimodal_message`），因此抽取时断言一字不改」。本轮**就是要改它**——那是上一轮的承诺，本轮到期。该 docstring 需同步更新，且这属于**计划内**的注入点迁移，不是意外破裂。

### 2.2 统一错误：信封已经统一了，剩下的是三处漏网 + 一处真空白

全文件 `except Exception as e:` 共 **32 处**（另有 1 处 `except (ValueError, TypeError)`、7 处 `except ValueError`、3 处 `FileNotFoundError`、6 处 `PlanNotFoundError`、1 处 `PlanGenerationError`，这些是**收窄的**合理捕获，不动）。

32 处按形态分三类：

| 形态 | 数量 | 内容 | 现状 |
|---|---|---|---|
| **① JSON 端点兜底** | 28 | `logger.error(f"...: {e}")` + `return api_error(ErrorCode.X, "中文", status_code=500)` | 信封已统一；但 **26 处缺 `exc_info=True`**（仅 6 处有） |
| **② SSE 端点兜底** | 2 | 手写 `json.dumps({'type':'error','content':...})` + `json.dumps({'type':'done'})` | **绕过了 `app/events/types.py` 的事件工厂** |
| **③ 特殊** | 2 | `_unified_chat` L1317（预取首事件失败的 500 信封，合理保留）、`eval_judge` L1495 | `eval_judge` **把异常原文回给前端** |

②的明细：

- `profile_chat/event_stream` L454–457 → 手写错误帧 + done 帧
- `inquiry_resolve_plan/event_stream` L1433–1436 → 同上

③的明细（`eval_judge` L1495）：

```python
except Exception as e:
    logger.error(f"Eval judge failed: {e}")
    return api_error(ErrorCode.INTERNAL_ERROR, f"裁判调用失败: {e}", status_code=500)
                                              # ↑ 异常原文直接进响应体
```

这是信息泄露（内部路径、上游 API 报错、可能的 key 片段都会回给调用方）。端点由 `EVAL_JUDGE_ENABLED` 门控、默认关闭，所以风险不高，但**性质是缺陷不是风格**。

**④ 一处真空白：`main.py` 没有全局 500 兜底。**

`main.py` 只注册了 `RequestValidationError` handler。48 个端点里 **14 个完全没有 `try`**：

```
resources_generate  tutor_chat  exercise_generate  profile_workflow_status
solve_question  grade_exercise  get_evaluation_report  categorize_exercises
analyze_session  exercise_dashboard  enrich_profile  update_masteries
unified_chat  inquiry_resolve
```

其中 6 个是 SSE 端点（错误处理已下沉进各自 Center，属正常），但 `profile_workflow_status`、`categorize_exercises`、`analyze_session`、`exercise_dashboard`、`enrich_profile`、`update_masteries`、`grade_exercise`、`get_evaluation_report` 这 8 个是普通 JSON 端点 —— 一旦抛异常，响应体是 FastAPI 默认的 `{"detail": "Internal Server Error"}`，**不是 `api_error` 信封**。前端/Java 按 `success`/`errorCode` 解析会拿到空值。

**结论：所谓「统一错误」的真实工作量不是重写 32 处，而是①补日志纪律 ②让 2 处 SSE 走事件工厂 ③堵住 `eval_judge` 的泄露 ④补全局兜底。**

### 2.3 一个重要发现：两处 SSE 错误帧可以**零字节**改用事件工厂

实测（本机验证）：

```python
error_content_event("画像对话失败，请稍后重试").to_sse()
# == 'data: {"type": "error", "content": "画像对话失败，请稍后重试"}\n\n'   ← 与手写串逐字节相同

done_event().to_sse()
# == 'data: {"type": "done"}\n\n'                                        ← 逐字节相同
```

**但 `error_event(stage, message)` 不行**——它同时写 `message` 和 `content` 两个键：

```python
error_event("", msg).to_sse()
# 'data: {"type": "error", "message": "...", "content": "..."}\n\n'        ← 多一个 message 键，字节变了
```

这个坑必须写进代码注释和验收记录，否则后来者「顺手」换成 `error_event` 就会静默改协议。

## 三、关键决策

### D1. 多模态落点：`app/utils/multimodal.py`，公开名去掉下划线前缀

跟随 `sse_response.py` / `security_middleware.py` 的先例（`app/utils/` 放纯能力）。

| 旧名（`internal_api`） | 新名（`app.utils.multimodal`） |
|---|---|
| `ALLOWED_IMAGE_MIMES` | `ALLOWED_IMAGE_MIMES` |
| `_extract_text_from_multimodal` | `extract_text_from_multimodal` |
| `_build_multimodal_message` | `build_multimodal_message` |

**不留旧名别名。** 与 `_sse_sanitize` / `_is_internal_url` 的处理一致：迁移完成后加负向断言 `not hasattr(internal_api, "_build_multimodal_message")`，证明归位完成而非"两处并存"。

### D2. `extract_text_from_multimodal` 一并搬家，不删除

它当前 0 调用。GUIDE 原文写的是「多模态消息构建**与解析**」，删除属于擅自缩减能力范围。搬过去并在验收记录登记「零调用」，与 `sse_sanitize` 同一处理方式。

### D3. 2 处 SSE 错误帧改用 `error_content_event` / `done_event`，要求**字节零变化**

证据形态：契约测试内直接断言 `xxx.to_sse() == '<旧手写字面串>'`，字面串原样抄自改造前的代码。

### D4. `eval_judge` 停止回显异常 —— **这是本轮唯一的行为变更**

```python
# 前
return api_error(ErrorCode.INTERNAL_ERROR, f"裁判调用失败: {e}", status_code=500)
# 后
return api_error(ErrorCode.INTERNAL_ERROR, "裁判调用失败，请稍后重试", status_code=500)
```

异常详情仍进日志（`logger.error(..., exc_info=True)`），只是不出响应体。**需用户确认。**

### D5. 26 处补 `exc_info=True` —— 只改日志，不改响应

留痕用。`except Exception` 是 catch-all，兜到的一定是意料之外的错误，没有 traceback 无法定位。

### D6. `main.py` 加全局 `Exception` handler —— **新增安全网，需用户确认**

```python
@app.exception_handler(Exception)
async def unhandled_exception_handler(request: Request, exc: Exception):
    logger.error(f"Unhandled exception on {request.url.path}: {exc}", exc_info=True)
    return api_error(ErrorCode.INTERNAL_ERROR, "服务内部错误，请稍后重试")
```

**行为变更**：上列 8 个无兜底的 JSON 端点，未捕获异常的响应体从 `{"detail": "Internal Server Error"}` 变为标准信封。

**不影响**：`HTTPException`（404/405 等）有 Starlette 自己的 handler，不会被这个捕获；已带 `try` 的 28 处路径完全不变。

**⚠️ 实现坑（已探明）**：`TestClient` 默认 `raise_server_exceptions=True` 会把异常直接抛给测试而不是返回响应；同进程 ASGI 的 `ASGITransport` 同理。测试必须用 `TestClient(app, raise_server_exceptions=False)` 才能观测到兜底响应。

**⚠️ 边界如实说明**：全局 handler 对 **SSE 流已经发出 200 之后**的异常无效（响应头已发送，无法改状态码）。它只覆盖「响应发出前就炸」的情形。这一条要写进验收记录，不能宣称"所有异常都被兜住了"。
