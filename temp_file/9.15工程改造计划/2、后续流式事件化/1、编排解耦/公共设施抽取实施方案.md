### 0.3 安全校验现状

**① SSRF 判定**（`internal_api.py` L302-328）：4 条正则 + `_is_internal_url()`，**只有 1 个调用点**（L351，位于 `_build_multimodal_message` 内）。它是纯字符串判定函数，跟 HTTP 协议层无关。

**② 导出文件路径守卫**（3 处，逐字相同）：

```python

ext = os.path.splitext(safe_name)[1].lower()
if ext != ".pptx":                                     # ① 类型白名单 → 400
    return api_error(ErrorCode.INVALID_REQUEST, "不支持的文件类型", status_code=400)
file_path = os.path.join(_EXPORTS_DIR, safe_name)
if not os.path.realpath(file_path).startswith(os.path.realpath(_EXPORTS_DIR)):
    return api_error(ErrorCode.INVALID_REQUEST, "非法文件路径", status_code=400)   # ② 目录穿越 → 400
if not os.path.exists(file_path):
    return api_error(ErrorCode.NOT_FOUND, "文件不存在或已过期", status_code=404)   # ③ 不存在 → 404
return FileResponse(file_path, media_type=..., filename=safe_name)
```

出现在 `download_pptx`(L559) / `download_docx`(L600) / `download_pdf`(L640)，只有扩展名与 media_type 不同。**抄三遍的真实成本：加第四种格式时漏抄任一行就是一个安全洞，且不会有任何测试报错。**

**③ 输入消毒**：`sanitize_model` 已在共享模块 `app/utils/prompt_guard.py`（93 行）。全仓 AST 统计：**恰好 8 处调用，正好每个 SSE 端点各 1 处**（`profile_chat` / `resources_generate` / `tutor_chat` / `exercise_generate` / `solve_question` / `_unified_chat` / `inquiry_resolve` / `inquiry_resolve_plan`），别处没有。


**结论：SSE 输出的控制序列注入防护目前实际未生效。** 这是一处现存安全缺口，不是本轮造成的。本轮**不接线**（接线会改变输出字节，违反本轮硬约束），只做归位 + 如实登记，见 §二 决策点 3 与 §十 风险 4。

## 一、这次要解决什么

把「脚手架」从协议层文件里搬出去，并让调用方式由**共享模块**而不是**每个路由手写**来保证。

三件事：

1. **SSE 响应样板 → 一个 `sse_response()` 工厂**：8 个端点各改 1 行，行为与字节零变化。
2. **安全校验 → 共享模块**：SSRF 判定与导出路径守卫搬进 `app/utils/security_middleware.py`，路径守卫从「抄 3 遍」变成「调 1 次」。
3. **消毒保持显式**：`sanitize_model` 已在共享模块，**不改调用方式**（不做中间件/装饰器自动消毒），只加一道防退化锁。

**本轮不做业务逻辑改动**，与六域收口同性质：结构变化、行为与字节零变化。

## 五、技术方案

### 5.1 `app/utils/sse_response.py`（新增）

```python
"""SSE 响应的 FastAPI 适配器。

与 sse_heartbeat.py 的分工：那个模块只做「异步生成器 → 异步生成器」的
保活包装，不依赖 Web 框架；本模块是唯一把 SSE 文本流交给 FastAPI 的地方。
"""

from typing import AsyncIterator

from fastapi.responses import StreamingResponse

from app.utils.sse_heartbeat import sse_heartbeat_generator

SSE_MEDIA_TYPE = "text/event-stream"


def sse_response(event_stream: AsyncIterator[str]) -> StreamingResponse:
    """把 SSE 文本异步生成器包成流式响应（含心跳保活）。

    接收「已构造的生成器对象」而不是工厂函数：调用方在传参前调用
    event_stream()，与收窄前 `sse_heartbeat_generator(event_stream())` 的
    求值时序一致，生成器体内的业务调用仍延后到流开始时执行。
    """
    return StreamingResponse(
        sse_heartbeat_generator(event_stream),
        media_type=SSE_MEDIA_TYPE,
    )
```

**8 个端点的改动（各 1 行）**：

```diff
-    return StreamingResponse(sse_heartbeat_generator(event_stream()), media_type="text/event-stream")
+    return sse_response(event_stream())
```

**为什么字节零变化**：包装的生成器对象、`media_type`、`StreamingResponse` 的默认 headers 全部相同，只是把同一段构造代码搬进了函数体。

**同模块追加 `_sse_sanitize`（仅归位，不接线）**：

```python
def sse_sanitize(text: str) -> str:
    """移除用户文本中的 SSE 控制序列，防止伪造 SSE 帧。

    ⚠️ 当前**无调用方** —— 本轮只把实现从 internal_api.py 搬到它该在的位置，
    不改变任何运行时行为。接线方式待「SSE 输出清洗接线」独立小项决定
    （见 §二 用户补充）。函数名去掉前导下划线以便后续跨模块调用。
    """
    return text.replace("\n\n", "  ").replace("\ndata:", " data:").replace("\r", "")
```

**本轮它依然不被调用。** 契约测试只断言「实现可导入且行为与搬迁前一致」（SSE-B07），**不断言任何端点调用了它**，以防把「未接线」误写成「已修复」。sse_heartbeat.py 里的 `_sse_event_type` 保持不变——它只做"读"，不做"清洗"，职责不同。

**② 导出路径守卫**（把抄了 3 遍的 6 行收成 1 个函数）

```python
def safe_export_path(filename: str, *, allowed_ext: str, exports_dir: str) -> str:
    """校验导出文件名并返回绝对路径。

    异常语义与收窄前的三档 return 一一对应（顺序也是契约的一部分）：
      - 扩展名不在白名单      → ValueError("不支持的文件类型")      → 路由映射 400
      - realpath 逃出导出目录 → ValueError("非法文件路径")          → 路由映射 400
      - 文件不存在            → FileNotFoundError("文件不存在或已过期") → 路由映射 404
```
