## 步骤 ① 模型参数清洗（GUIDE P2 第 3 步收官）

### 摸底结论：这个概念在本项目里由两件事构成

| 组成 | 落地形态 | 之前状态 |
|---|---|---|
| **送入模型的文本要清洗** | `app/utils/prompt_guard.py::sanitize_model()` —— 递归清洗 Pydantic/dict/list 的所有 str 字段（截断 4000 字 + 过滤 8 类注入模式） | 只覆盖 8 个路由，**3 个入口漏网** |
| **客户端不得指定模型参数** | 请求模型里根本没有 `model`/`temperature`/`max_tokens` 字段 | 已有，但**无契约锁定** |

### 修了什么

| 入口 | 自由文本 | 去向 | 处置 |
|---|---|---|---|
| `POST /internal/graph/extract` | `user_message` / `assistant_reply` | LLM 抽取知识节点 | ✅ 接线 |
| `POST /internal/plans/create-from-path` | `topic` | LLM（Goal → Decompose → Schedule） | ✅ 接线 |
| `POST /internal/plans/{id}/complete-step` | `step.topic` | LLM 出题 | ✅ 接线 |
| `POST /internal/eval/judge` | `message` / `system_prompt` | 直连 LLM | ⛔ **按设计豁免**：它就是拿（可能含注入的）材料做裁判的评测旁路，清洗会洗掉评测能力 |

### `_get_mock_flag()` 环境化

```python
# 之前：return False（硬编码，离线无法构造 13 个工厂，只能靠测试 patch）
# 现在：AI_SERVICE_MOCK_LLM=1|true|yes|on → True；未设置 → False
```
未设置时与历史行为**逐字一致**（零行为变化）；离线测试/存证 harness 可用环境变量开关。
旧手法（`monkeypatch.setattr(internal_api, "_get_mock_flag", ...)`）仍有效。

### 契约 `tests/test_model_param_sanitize_contract.py`（13 例）

`MS-A01` 三个新入口必清洗（AST）｜`MS-A02` 全仓清洗调用点 ≥ 11（防退化）｜
`MS-A03` `/eval/judge` **不得**清洗｜`MS-B01` 请求模型不得暴露模型参数字段｜
`MS-C01..C03` 环境开关（默认 False / env 可开 / 仍可 patch）

## 步骤 ② 统一事件层（流式阶段 B）

依据《流式系统演进与改造指导》阶段 B 三条原则落地：

| 原则 | 落地 |
|---|---|
| §2.1 `on_token(chunk)` → `emit(event)` | 新增 `app/events/stream.py`：`ProgressEventType`（6 类最小集）+ `ProgressEvent(run_id, seq, ts, data)` + `StreamEmitter`（`on_token` 为兼容适配） |
| §2.2 一次生成、多方消费 | `ChatTaskDispatcher` 的 token 泵是唯一事件源：`_on_token` 先 `emit(message.delta)`，再进既有 SSE 队列 |
| §2.3 Transport 与 Event Model 分开 | 事件层**不 import 任何 web 框架**（由 `EM-C01` 锁定）；SSE 编码仍归 `app/events/types.py` |

**新消费者**：`MessageDeltaCollector` —— 把 `message.delta` 聚合回完整文本，用于
「前端逐字收到的文本 vs 后台收集的完整文本」对账（指导文档 §6-3），并按 `run_id` 打一行日志
（§6-5 可追溯）。

**零字节变化**：`emit()` 只通知订阅者，不参与 SSE 帧构造 —— 55 条存证逐条一致为证。
`emitter` 是**可选注入**参数（不传则内部新建，既有调用点零改动）。

### 契约 `tests/test_stream_event_layer_contract.py`（9 例）

`EM-A01..A05` 序号单调/`run_id` 恒定/Collector 聚合/订阅者异常隔离/轨迹封顶｜
**`EM-B01` 集成对账**（真实分发器下 `collector.text == SSE token 拼接 == 原文`）｜
`EM-B03` SSE 通路仍消费**原始** chunk（AST）｜`EM-C01` 无 web 依赖

## 步骤 ③ 补上「真实画像管线」存证缺口

**缺口**：`sse_all_endpoints.py` 的 `profile_chat` 用例把 `_get_profile_workflow` 换成了替身，
所以 P3-B3b 合并双层图时 55 条存证"全一致"其实**什么也没证明**。

**补法**：新增 `acceptance/harness/profile_pipeline.py` —— 走真实 `ProfileWorkflow`，
用 `AI_SERVICE_MOCK_LLM=1` 使其离线确定，正则归一化时间戳后取 sha256，3 个用例：

| 用例 | 覆盖 |
|---|---|
| `empty_profile_first_turn` | 空画像首轮 |
| `similar_weak_point_dedup` | 与已有 weak_points 高度相似 → 走 `semantic_judge` 候选预筛（**P3-B3b 激活的能力**） |
| `complete_profile_turn` | 6 维全满 → 走 `complete` 分支 |

**敏感性验证**：`similar_weak_point_dedup` 的响应里含 `profile_update` 载荷（合并后的画像，
如 `knowledge_base: 44`、`learning_goal`、`weak_points`），即 **merge/judge 的结果进入哈希** ——
该管线再改动，存证会变。
**确定性**：同日连跑两次 identical=True。
基准：`acceptance/snapshots/profile/_accept_profile_pipeline_after.txt`（snapshots 已 ignore）。
