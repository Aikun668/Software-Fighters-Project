# 阶段 D（最小切片）：执行进度对用户可见

- **日期**：2026-09-26 · **基线**：`9196b6a`
- **依据**：《流式系统演进与改造指导》阶段 D ——
  > 用户侧并不需要暴露全部内部思考，但可以展示可信、简洁的进度，例如"正在检索课程资料""正在组织解释"。
- **定性**：⚠️ **用户可见变更轮**（本流式改造首次真正改变前端可见信息）。既有帧逐帧不变，只**新增** `progress` 帧。

## 一、切片边界（做了什么 / 明确没做什么）

**做**：把**已经产生**的内部事件（`node.started` / `node.completed`）搬到 SSE 线上，前端最简展示。

**没做（刻意推迟）**：
- 「节点/事件 → 用户可见文案」**映射表** —— 本切片 `message` 是**占位文案**（`正在执行 <节点名>`），
  内部节点名先直接露出；等你定文案口径后再补表（本轮不改协议、只改文案来源）。
- 取消 / 背压 / 断线重连 / 持久化（阶段 E）。
- 其他页面与 `conversations.ts` 的另一份 `parseSSEStream`。

## 二、动手前的三项侦察（先取证再改）

| 侦察 | 结论 | 影响 |
|---|---|---|
| **Java 网关会不会吃掉新事件类型** | `PythonClient.createSseEmitter` 用 `emitter.send(SseEmitter.event().data(eventData))` **原样透传**原始 JSON；下面的 `type` 分支只用于**收集入库**（`collectedData` / `responseText`），**不参与过滤** | ✅ 新增 `progress` 帧能到浏览器；这是本切片最大的风险点，已排除 |
| **前端现在认哪些类型** | `parseSSEStream` 只处理 `content` / `token` / `inquiry` / `done` / `error`，其余落 `default`（`center_start`/`center_end` 今天就在发，但前端**一直忽略**） | 需要给解析器加 `progress` 分支 + 回调 |
| **`node.started` 怎么拿** | 探针实测（`SP-07`，生产同款配置 `stream_mode=["updates","values","debug"]` + `subgraphs=True` + 手工嵌套）：`debug` 流的 `type == "task"` 事件 = **节点开始**，且带与 `updates` **同形**的 namespace，顺序正确（外层 `wrapped` 先于其内层 `inner_a/inner_b`） | 不必逐节点改 `custom` writer（那要动 4 个 Workflow 的所有节点） |

## 七、收口（同日补做）：端到端 harness 补上盲区

### 7.1 为什么必须单独一个 harness

`sse_all_endpoints.py` 的聊天用例把 `_get_chat_center` 换成了 `_StubCenter`（只回放预置事件），
所以它**永远不产生图节点事件** —— 阶段 D 新增的 `progress` 帧在那个 harness 里**一条都测不到**。
这与 P3-D 当时"画像管线被 stub 掩盖"是同类缺口，故新增独立 harness（同法：独立文件、不 stub 业务）。

### 7.2 跑了什么（全真链路）

```text
POST /internal/api/chat  →  ChatCenter.stream_chat
                         →  真 ChatTaskDispatcher（token 泵 + progress 转发）
                         →  真 TutorAgent 图（retrieve / respond 等）
```

### 7.3 实测结果

| 项 | 值 |
|---|---|
| 帧数 / token / progress | **79 / 69 / 6** |
| `progress_stages` | `['analyze', 'respond', 'retrieve']` |
| 断言（`problems`） | **空** —— started/completed 成对、token 正文非空、`done` 唯一且最后 |
| 可复现 | 同日两次运行 sha256 **完全一致** |
| 基准 | `acceptance/snapshots/chat/_accept_chat_progress_after.txt` |

### 7.4 过程中发现的真问题（本轮最大收获）

**聊天链路不认 `AI_SERVICE_MOCK_LLM`**：

1. `ChatCenter._get_dispatcher()` 直接 `DecomposeAgent()` / `TutorAgent()` 等构造 —— **不传** mock 旗标
   （`internal_api` 的工厂则会传 `_get_mock_flag()`），于是 Agent 内部 `use_mock_llm=False`；
2. `ProfileAgent.judge_llm`、`TutorAgent._get_clarity_llm` 走**直接实例化** `OpenAILLM(...)`（不经 `create_llm`），
   吃的同样是实例旗标。

结果：**没有 API Key 的环境下，整条聊天链路在"构造期"就抛 `ValueError`** —— 任何离线端到端测/CI 都跑不起来。
本次 harness 只能对 `create_llm` 与 `OpenAILLM` 做**全覆盖 patch**（只跳过 flag 判断本身），
并把"mock 旗标本应生效"登记为待统一项（遗留 6）。

> 这与 P3-D 的"`_get_mock_flag` 环境化"是同一件事没做完：环境化只覆盖了 `internal_api` 工厂那一条路径。
