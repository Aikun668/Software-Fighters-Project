# 学习闭环化五优先级技术路线与实施总纲

> **定位**：这是 `9.15工程改造计划` 在“业务域收口、统一事件、执行进度可见”之后的下一阶段总纲。它回答的是：项目不再继续横向堆叠功能时，如何把已有的对话、计划、练习、资源、图谱和画像，逐步收成一个真正能带学生学习的系统。
>
> **本文不是代码改动单，也不是立即执行全部事项的授权。** 每个优先级进入开发前，仍须另立本阶段实施方案和验收记录；未被该阶段点名的模块不随手重构。

---

## 一、先把这条路线说清楚

目前系统已经不缺单项能力：

- AI 服务已有聊天、学习计划、练习、资源、知识图谱、画像等业务域；
- Java 侧已有学习活动、学习记录、节点掌握度、计划等业务入口；
- 前端已有对话、计划、练习、资源、图谱、学情分析等页面；
- 流式系统已能把 token 和最小执行进度交给对话页。

但学生现在仍可能面对的是一组功能入口：想做题点练习，想看资料点资源，想问问题点聊天。系统未必能稳定回答这一句最重要的话：

> **“你现在应该做什么，为什么是这一步；做完以后，系统会怎样调整？”**

本路线的目标就是把这句话做成可靠的产品能力。最终不是“系统替学生偷偷连续调用多个 Agent”，而是：

```text
学生目标 + 已有学习记录
          ↓
系统整理当前学习状态
          ↓
给出一件可解释、可拒绝的下一步行动
          ↓
学生明确点击开始，进入一个已有业务域
          ↓
结果形成学习证据，更新下一次的学习状态
```

这五块必须按顺序推进：

```text
P0 真实链路可信
  → P1 学习状态有统一口径
  → P2 单课程闭环跑通
  → P3 页面收成学习入口
  → P4 按真实需求补生产保障
```

P0–P3 是当前主要投入；P4 只预留方向，不抢占产品主线。

## 二、全局边界：以后每个阶段都不能突破的线

### 2.1 不把学习闭环做成“后台自动串多个 Center”

现有产品约束仍然有效：一次自然语言请求只进入一个主业务域；专项能力结束后只能给出下一步建议，不能自行启动下一个 Center。

因此，学习闭环的正确形态是：

```text
系统给出“建议练习 / 建议复习 / 建议提问 / 建议看资源”
→ 学生确认
→ 前端带着明确 action 进入 ExerciseCenter / PlanCenter / TutorCenter / ResourceCenter
→ 原业务域独立完成本次任务
→ 结果回写为证据
```

错误形态是：

```text
聊天结束 → 后台自动生成资源 → 自动出题 → 自动改计划 → 自动推送
```

后者会重新制造一个跨域总调度器，既违背已经完成的编排收口，也会让学生失去控制感。

### 2.2 三层各自只承担一类责任

| 层 | 应承担什么 | 不应承担什么 |
| --- | --- | --- |
| 前端 | 展示“当前该做什么”、说明理由、接收学生确认、渲染结果 | 计算掌握度、复制判题/计划规则、猜测下一步 |
| Java 后端 | 用户、课程、长期学习记录、权限和持久化事务；向前端提供稳定业务读模型 | 编排 AI 内部多阶段流程、复制 Agent 规则 |
| Python AI 服务 | 解释、出题、批改、生成资源、计划计算、推荐所需的智能/算法能力 | 直接成为长期学习事实的第二套真源 |

这里的“长期学习事实”包括：用户是谁、课程是什么、做过什么、一次练习得了什么结果、节点掌握度当前值、计划当前状态。P1 的第一项工作不是迁数据，而是逐项写清这些事实现在由谁保存、将来由谁最终负责。

### 2.3 学习证据强弱必须分级

不能把所有行为都等价地当作“学会了”。建议采用以下产品口径，具体数值留给 P1 的小方案决定：

| 证据 | 能说明什么 | 对掌握度的影响原则 |
| --- | --- | --- |
| 完成一次资源浏览 | 学生接触过内容 | 只能给很弱的接触信号，不能证明掌握 |
| 主动提问 / 阅读讲解 | 学生在尝试理解 | 可记录困难点或兴趣点，不直接大幅加分 |
| 客观题正确 | 某个知识点有一次正确表现 | 中等强度，需结合题目归属、难度和历史 |
| 主观/代码题通过批改 | 有较强的理解或应用表现 | 较强证据，必须保留评分依据 |
| 连续复习后仍正确 | 长期保持 | 强证据，可用于提升稳定掌握度 |
| 错题、跳过、长时间中断 | 需要补救或复习 | 不能简单扣成“不会”，应触发解释、回顾或前置检查 |
| 学生手动纠正系统判断 | 学生明确反馈 | 作为高优先级反馈，但保留来源和时间 |

### 2.4 每次交付都必须区分四类证据

任何阶段验收记录必须明确标注：

1. 离线单元/契约测试；
2. 本地 ASGI 或前端模拟联调；
3. 真实 HTTP（前端 → Java → Python → 持久化）的结果；
4. 人工可见结果及未执行项。

其中任意一类没有完成，都如实登记，不能用前一类替代后一类。

## 三、P0：先把“这条学习路真的能走通”做可信

### 3.1 P0 的一句话目标

在不新增学习产品功能的前提下，建立一条可重复验证的真实链路：学生发起动作，前端、Java、Python 和持久化各自做对自己的事，发生异常时能知道断在哪里。

### 3.2 为什么 P0 必须排在最前面

当前已经确认过三个现实风险：

- 真实聊天链路没有完整继承 `AI_SERVICE_MOCK_LLM`；无 Key 时，部分 Agent 在构造期就会失败，导致“离线端到端可跑”并不成立；
- `docs/AI服务-后端对接文档.md` 的后端 TODO 是早期文档，不能直接当作现状；必须逐端点核对已有 Controller、PythonClient 和前端调用；
- 部分学习页面仍有演示性静态数据。它们适合作为视觉样稿，但不能被误判为真实闭环已经接通。

这三个问题不处理，后续即使做出“下一步建议”，也无法确定它是正确的产品链路还是只在局部样例里好看。

### 3.3 P0 的工作包

#### P0-A：做一张“真实链路台账”

以一个学生动作作为单位，而不是按仓库目录统计。优先登记以下动作：

| 学生动作 | 前端入口 | Java 入口/持久化 | Python 业务入口 | 结果去向 | 当前证据 |
| --- | --- | --- | --- | --- | --- |
| 发起普通答疑 | 对话页 | 会话/消息转发 | `ChatCenter → TutorCenter` | 对话与学习记录 | 待逐条复核 |
| 完成计划任务 | 学习计划页 | 计划/活动记录 | `PlanCenter.update_progress` 等 | 掌握度、计划状态 | 待逐条复核 |
| 完成练习 | 练习页 | 作答/成绩记录 | `ExerciseCenter.grade` | 错因、掌握度、画像 | 待逐条复核 |
| 使用学习资源 | 资源页 | 资源/活动记录 | `ResourceCenter` | 资源记录、弱学习证据 | 待逐条复核 |

台账必须写“已实测 / 只读到代码 / 未接通”三种状态，禁止凭目录或接口名推断已经实现。

#### P0-B：统一“可离线构造”的模型配置

目标不是把真实模型替换为 mock，而是让所有创建模型的路径遵守同一开关口径：

- 经工厂创建的 Agent；
- `ChatCenter._get_dispatcher()` 直接构造的 Agent；
- Agent 内部直接创建 `OpenAILLM` 的辅助模型；
- 测试、验收 harness 和本地开发环境。

完成标准是：在明确设置 mock 环境时，真实聊天链路能在**不 patch 业务对象**的情况下完成可重复的离线验收；未设置 mock 且无 Key 时，返回的是清楚、统一、可定位的配置错误，而不是构造期散落的异常。

#### P0-C：建立“最小真实闭环 harness”

只选择一条已经存在的业务路径，不新建学习功能。harness 至少应验证：

```text
前端请求格式 / Java 转发或持久化边界 / Python 业务响应 / SSE 终态
```

首批场景建议是：普通答疑、一次计划进度更新、一次练习评分。它们分别覆盖“流式对话”“状态更新”“学习效果输入”三种基础形态。

#### P0-D：冻结本阶段不做项

- 不新建“学习闭环总调度 Agent”；
- 不迁移全部历史数据；
- 不为所有页面补完真实接口；
- 不因流式功能再做 Kafka、Redis Streams 或新的 EventBus；
- 不把旧对接文档的 TODO 直接当实现任务，必须先以台账核准。

### 3.4 P0 退出条件

只有满足以下条件，才进入 P1：

- 有一张由实际代码和一次运行验证过的链路台账；
- mock/无 Key/有 Key 三种模型配置的行为写清楚，并至少让真实聊天链路的离线运行可重复；
- 三条最小业务路径有明确的离线、真实 HTTP、人工结果和未执行项记录；
- 本轮没有顺手新增学习业务逻辑。

## 四、P1：让系统有一本可信的“学生学习账本”

### 4.1 P1 的一句话目标

先不急着让系统替学生做决定；先让系统能在任意时刻用同一套口径回答：这个学生、这门课、这个知识点，现在处于什么状态。

### 4.2 P1 的核心产物：学习状态读模型

P1 建议定义一个面向产品的读模型，暂称 `LearningSnapshot`。它不是为了再复制一份数据，而是把散落的计划、掌握度、活动、画像和图谱信息整理成前端可用的一张“当前学习状态卡”。

```text
LearningSnapshot
├─ student_id / course_id / generated_at
├─ active_plan：当前计划、当前步骤、是否中断
├─ current_node：当前或最需要处理的知识节点
├─ mastery：当前值、来源、最后一次有效证据时间
├─ recent_evidence：最近若干条可解释的学习证据
├─ profile_context：只保留本次推荐真正需要的偏好/困难信息
├─ freshness：数据是否过期、是否缺少关键来源
└─ next_action：可为空；只是一条建议，不是后台命令
```

关键要求：`LearningSnapshot` 只读、可追溯、带来源。它不能悄悄修改计划或掌握度；修改必须由明确的学习动作和对应的业务域完成。

### 4.3 P1 的工作包

#### P1-A：完成“学习事实归属表”

逐项确认下列事实的最终真源、写入者和读取者：

| 学习事实 | 建议最终真源 | 典型写入动作 | 主要读取者 |
| --- | --- | --- |
| 用户/课程身份 | Java 业务数据 | 登录、选课 | 全部页面和 AI 请求上下文 |
| 计划及步骤状态 | 计划数据域 | 创建计划、完成步骤、调整计划 | 计划页、学习状态读模型 |
| 节点掌握度 | 节点掌握度数据域 | 练习评分、计划进度、人工修正 | 图谱、计划、推荐 |
| 学习活动/证据 | 学习活动或记录数据域 | 浏览、作答、完成、跳过、纠正 | 学情分析、读模型、审计 |
| 画像偏好与困难点 | 画像数据域 | 画像对话、学生纠正、练习分析 | AI 请求的辅助上下文 |

若现有 Python 服务临时保存了某项长期状态，P1 只记录兼容策略和迁移方向，不允许在未核对调用方前大搬家。

#### P1-B：定义学习证据合同

每条 `LearningEvidence` 至少要能表达：

```text
evidence_id, student_id, course_id, node_id,
type, occurred_at, source_action, source_record_id,
score_or_result, confidence, effect_hint, explanation
```

其中：

- `source_action` 表示它来自练习、计划、资源、答疑或人工修正；
- `source_record_id` 用于防止同一次作答、同一个按钮重试被重复计入；
- `effect_hint` 是“建议怎样影响学习状态”，不是前端自己计算的最终值；
- `explanation` 必须能向学生或教师解释“为什么有这条记录”。

P1 必须先固定事件类型和幂等规则，再决定数据库表、DTO 或 Python 返回字段如何增量适配。

#### P1-C：确定掌握度更新的统一口径

现有计划服务已经有练习、资源、遗忘和复习相关的计算。P1 不另起一套公式，而是要统一回答：

1. 哪些事件允许改变掌握度；
2. 每次改变由哪个服务计算、哪个服务最终落库；
3. 当前掌握度缺数据时默认如何展示；
4. 同一作答重放、网络重试、前端重复提交如何不重复加分；
5. 学生主动纠正画像时，哪些字段可改、哪些历史事实不可被覆盖。

这一步的成果是口径和契约测试，不是追求一次性把算法调到“最聪明”。

#### P1-D：给下一步建议限定输入和输出

P1 中的 `next_action` 只能从已定义的动作集合中选择，例如：

```text
review_current_node
practice_targeted_questions
ask_for_explanation
study_assigned_resource
resume_plan
check_prerequisite
```

每条建议必须同时返回：

- `action_kind`：学生要做什么；
- `target`：知识点、计划步骤或资源主题；
- `reason`：来自哪几条证据；
- `expected_minutes`：预估耗时，可为空；
- `entry`：学生确认后应进入哪个既有业务域；
- `dismiss_policy`：学生拒绝后是暂不推荐、换替代动作还是请求手动选择。

它绝不能返回“立刻调用 ResourceCenter 后再调用 ExerciseCenter”这种跨域执行指令。

### 4.4 P1 退出条件

- 每项长期学习事实有明确真源和写入边界；
- `LearningSnapshot` 与 `LearningEvidence` 的字段、来源和空值策略冻结为 V1；
- 至少覆盖“练习正确、练习错误、计划完成、仅浏览资源、长期未学习、学生纠正”六类状态样例；
- 证明同一证据重复提交不会被重复记账；
- 尚未要求前端大面积改版，也尚未自动串 Center。

## 五、P2：挑一门课，把一条学习闭环真正跑出来

### 5.1 P2 的一句话目标

不是把所有课程都接入，而是让一个真实课程中的一个学生，从“系统建议”走到“完成动作、产生证据、下一步变化”，全过程可演示、可解释、可回归。

### 5.2 试点课程与范围选择标准

试点课程应满足：

- 已有稳定的知识图谱节点和前置关系；
- 有可用的计划步骤；
- 至少有练习生成/评分能力；
- 能提供一小批课程资料或图解；
- 团队能准备固定测试账号和演示数据。

优先选择“节点关系清楚、错题可明确归属”的课程。不要一上来选覆盖面最大但资料最杂的课程。

### 5.3 试点必须覆盖的五种学生状态

| 学生状态 | 系统应建议什么 | 目的 |
| --- | --- | --- |
| 新进入课程 | 创建或确认学习计划 | 验证起点不是空白页 |
| 正在按计划学习 | 做当前计划步骤 | 验证计划和当前行动一致 |
| 练习连续错误 | 针对性讲解、图解或前置检查 | 验证系统不会只重复出题 |
| 中断一段时间 | 恢复、热身或回归检查 | 验证遗忘/软着陆能力真正进入产品 |
| 完成当前节点 | 解锁下一节点或安排复习 | 验证结果能影响下一步 |

### 5.4 闭环交互流程

以“某知识点连续错题”为例：

```text
练习评分完成
→ 写入本次作答及其知识点证据
→ 读取 LearningSnapshot
→ 给出“先看图解，再做 3 道针对题”的建议卡
→ 学生选择“开始”或“换一个方式”
→ “开始”后进入一个明确的已有业务域
→ 新结果再形成证据
→ 下一次刷新时，建议/掌握度/计划状态发生可解释变化
```

“建议卡”只做引导和跳转。资源生成、答疑、出题、改计划仍由各自 Center 自己执行。

### 5.5 P2 的技术约束

- 用课程白名单或功能开关限制试点，不能一上线影响所有课程；
- 每次建议必须带证据来源，开发和演示时都能追到原始活动；
- 建议失效时（计划被删除、节点不存在、数据很旧）必须降级成“请从学习计划中选择下一项”，而不是发送无效跳转；
- 不让 LLM 直接写掌握度数值；LLM 可以帮助解释或生成内容，状态计算必须走确定性业务规则；
- 试点中的学生可以拒绝建议，拒绝本身也要有轻量记录，避免系统一直重复推同一动作。

### 5.6 P2 退出条件

至少完成一条真实演示链路，并能提供：

1. 起始学习状态截图/接口响应；
2. 建议卡及其理由；
3. 学生确认进入已有能力后的真实结果；
4. 证据记录与掌握度/计划状态变化；
5. 下一次建议变化或明确不变的理由；
6. 对“错题、拒绝建议、网络重试、计划已失效”四种边界的测试结果。

## 六、P3：把页面从“工具大厅”收成“学习入口”

### 6.1 P3 的一句话目标

学生打开系统后，先看到的不是一排功能，而是自己当前最值得做的一件学习任务；计划、图谱、资源、练习和对话成为完成这件事的不同入口。

### 6.2 页面职责重新划分

| 页面/区域 | P3 后的第一职责 | 与闭环的关系 |
| --- | --- | --- |
| 首页/学情分析 | 当前行动、理由、最近变化 | `LearningSnapshot` 的主视图 |
| 学习计划 | 今天任务、计划步骤、恢复状态 | 承接 `resume_plan` / `review_current_node` |
| 练习中心 | 针对指定节点的真实练习会话与评分结果 | 承接 `practice_targeted_questions` |
| 资源中心 | 与当前节点关联的真实资源列表、生成和使用记录 | 承接 `study_assigned_resource` |
| 对话页 | 围绕当前节点的解释、追问与澄清 | 承接 `ask_for_explanation` |
| 知识图谱 | 解释当前位置、前置与解锁关系 | 不替代“下一步行动” |

### 6.3 前端改造顺序

1. **先做只读当前行动卡**：只读取 `LearningSnapshot`，展示推荐、理由、数据更新时间和“开始学习/暂不处理”。
2. **再做明确跳转**：点击“开始”进入一个既有页面，并携带 `course_id`、`node_id`、`action_kind` 等明确上下文。
3. **再替换一条演示数据链路**：优先替换 P2 所选课程的练习或资源页，禁止同时把所有静态页面翻新。
4. **最后串回结果**：动作完成后刷新当前行动卡，让学生看见“我刚刚做的事产生了什么变化”。

当前资源页和练习中心页存在演示性 `resources` / `questions` / 分数数据。P3 应按“一个页面、一条真实链路”的方式替换，不能把展示层的模拟结果误作学习事实。

### 6.4 P3 体验要求

- 文案必须用学生语言，例如“先复习注意力机制，再做 3 道题”，不能直接显示内部节点名或 Agent 名；
- 每条建议有“为什么推荐给我”和“换一个方式”入口；
- 没有数据时显示诚实的起步引导，不用假进度填满页面；
- 进度流只展示学生有用的阶段，例如“正在查找课程资料”“正在组织讲解”，不暴露内部推理或原始节点名；
- 前端不复制掌握度和推荐规则；它只消费后端稳定合同。

### 6.5 P3 退出条件

- 试点学生首次进入时，能在一个入口找到当前行动；
- 一个建议能跳到真实计划、练习、资源或对话能力；
- 完成动作后，主入口能显示与真实数据一致的变化；
- 演示数据和真实数据在页面上有明确隔离，不存在“看似真实、实际本地写死”的混淆；
- 至少有一次人工录屏或端到端手测，验证学生视角能完成闭环。

## 七、P4：把它做得像稳定产品（后置、按需）

P4 不是当前主线的前置条件。只有当 P0–P3 已经证明学生会稳定使用闭环，且实际出现长任务、网络中断、并发或排障需求时，再按问题选择建设：

- 用户取消后真正中断模型/工作流，避免后台继续消耗；
- `run_id + seq` 进入前端协议，支持事件去重、排序和有限重连；
- 长连接/长任务的背压和超时策略；
- 跨 Java、Python 的请求关联、耗时和错误观测；
- 资源、练习、建议和学习证据的持久化回放；
- 基于真实用户量再考虑限流、队列或分布式基础设施。

不把 Kafka、Redis Streams、全面 WebSocket 化或“所有 Agent 全异步生成器化”列为默认任务。它们只能由真实问题触发并单独立项。

## 八、阶段依赖、风险与不做事项

### 8.1 阶段依赖

| 阶段 | 依赖 | 交付给下一阶段的东西 |
| --- | --- | --- |
| P0 | 现有业务域与流式基础 | 可信链路台账、可复现验收环境 |
| P1 | P0 的真实链路结论 | 学习状态/证据 V1 合同、事实归属表 |
| P2 | P1 合同 | 单课程真实闭环与边界用例 |
| P3 | P2 可用接口与行为 | 学生可见的统一学习入口 |
| P4 | P0–P3 的实际运行数据 | 有针对性的稳定性能力 |

### 8.2 最大风险与对应做法

| 风险 | 后果 | 处理原则 |
| --- | --- | --- |
| 把学习闭环做成跨 Center 自动链 | 重新出现万能调度、难测且失控 | 建议与执行分离，学生确认后只进一个 Center |
| 用页面静态数据冒充闭环 | 演示好看但没有真实价值 | 页面标明演示/真实；P3 每次只替换一条真链路 |
| LLM 直接决定或写入掌握度 | 状态不可解释、难回归 | LLM 只做生成和解释；状态更新走确定性规则 |
| 一次迁移所有学习数据 | 高风险且难回滚 | P1 先建读模型和事实表，逐域兼容迁移 |
| 先做大规模基础设施 | 花费大但学生价值未验证 | P4 必须由真实问题触发 |

### 8.3 明确不做

- 不新增全局“学习超级 Agent”；
- 不把 `LearningSnapshot` 变成第二套持久化真源；
- 不在前端复制判题、掌握度、遗忘或推荐算法；
- 不在没有真实课程闭环前扩展更多炫技功能；
- 不将离线 mock、ASGI 测试或旧截图当作真实 HTTP/人工结果。

## 九、推荐的文档拆分与执行顺序

本总纲批准后，建议只按以下顺序立文件，不提前创建后续阶段的代码任务：

1. `P0-真实链路与模型配置一致性实施方案.md` + 对应验收记录；
2. `P1-学习状态与学习证据V1设计方案.md`（先出数据/接口合同，再讨论实现）；
3. `P2-单课程学习闭环试点实施方案.md` + 对应验收记录；
4. `P3-学习入口页面与真实数据接线方案.md`；
5. P4 只有在出现具体运行问题后再建方案。

每个文件都必须回答同样的四个问题：

```text
学生在这一阶段获得什么？
哪些已有业务域和接口会变？
哪些数据是真源、怎样回滚？
如何分别证明离线、真实 HTTP、人工体验与未执行项？
```
