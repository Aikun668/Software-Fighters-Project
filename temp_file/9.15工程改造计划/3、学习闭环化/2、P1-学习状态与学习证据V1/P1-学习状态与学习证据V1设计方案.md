## 〇、四个强制问题（总纲 §9 要求，逐条先答）

### 问题 1：学生在这一阶段获得什么？

**直接可见变化 = 0。** P1 不改前端、不新增学生可点的按钮。这一点必须如实登记，不能包装成"体验升级"。

P1 交付的是一份**地基承诺**：此后任何页面读到的"这个学生、这门课、这个知识点，现在处于什么状态"，**数字同源、可解释、可追溯**。当前系统做不到这一点 —— 同一份掌握度在三个地方被显示成三个不同等级（见 §三·缺口③），且学完一节刷新即失忆（缺口①）。

学生真正受益发生在 P2/P3：没有 P1 冻结的口径，P2 跑通的闭环会把"同一个知识点在图上已掌握、在计划里还在学、在统计卡里算薄弱"这种自相矛盾带给学生。

### 问题 2：哪些已有业务域和接口会变？

**P1 内：代码零变更。** 仅冻结契约。变更清单如下，**均在 P2 实施**：

| 变更项 | 现状 | P1 冻结的契约 | 实施阶段 |
| --- | --- | --- | --- |
| 掌握度落库 | **无人落库**（缺口①） | Java 在 `POST /api/plans/{planId}/progress` 与 `POST /graph/masteries` 收到 Python 计算结果后**必须**写 `node_masteries` | P2 |
| 阈值口径 | 三端三套（缺口③） | **统一 0.85 / 0.6 / 0.3 / 0**（队长已裁决） | P2 |
| `plan_steps.mastery_*` | 死字段，Java 零写入（缺口②） | 裁决为**冗余快照**：只读展示用，**不作任何计算输入**，不要求 Java 回写 | P2（或直接废弃，见 §三·②） |
| 缺失数据默认值 | 两套（缺口④） | **统一为「无记录 = 未学习 = 0.0」**，全链一致 | P2 |
| 辅导域事件 | 算法支持、零调用（缺口⑤） | 保留 `tutor_question_asked` 在事件表中；**本阶段不接线** | P2 起按需 |
| 新增读端点 | 无 | `LearningSnapshot` 的对外形状（§二） | P2 |
| 新增事件契约 | 无 | `LearningEvidence` 八字段 + 幂等键（§四） | P2 |

### 问题 3：哪些数据是真源、怎样回滚？

**P1 只出文档，因此回滚 = 不合并本文件、删除本目录。** 无任何代码或数据结构变更，无数据迁移，回滚成本为零。

P1 **冻结**的真源归属（P2 起生效）：

- **掌握度唯一真源 = `node_masteries` 表（Java 拥有）**。现有表，`UNIQUE KEY uk_user_node(user_id, node_id)`。不新增掌握度表、不做双写。
- **学习证据真源 = 现有落库记录**（`learning_records` / `learning_activities` / `messages` / `resources` 等，Java 拥有）+ 未来按 §四 契约补的幂等键列。**不新建"证据大表"**，P2 先以读模型聚合现有记录。
- **计划真源 = `learning_plans` + `plan_steps`（Java 拥有）**。
- Python 侧**继续保持零状态**：`ai-service` 不落任何长期状态，`LearningSnapshot` 由 Python 现算现返，Java 可缓存但不得作为真源。

若未来必须新增表/列，回滚策略 = **停写新列 + 保留旧读写路径**（加法式变更，不做破坏性迁移）。

### 问题 4：如何分别证明离线、真实 HTTP、人工体验与未执行项？

**P1 是设计阶段，四类证据中的后两类在本阶段必然为「未执行」** —— 这是事实，不掩饰。

| 证据类别 | P1 本阶段提供什么 | 状态 |
| --- | --- | --- |
| **① 离线单元/契约测试** | 无新代码 → 无新测试。但本文件的每条契约都**标注了可验证的断言点**（§六 验收清单），P2 实现时逐条落测 | **未执行**（待 P2） |
| **② 本地 ASGI / 前端模拟联调** | 无新端点 → 无 harness 可打 | **未执行**（待 P2） |
| **③ 真实 HTTP（前端→Java→Python→持久化）** | 无实现 → 无链路 | **未执行**（待 P2） |
| **④ 人工可见结果** | 无前端改造（总纲 §4.4 明确要求） | **未执行**（设计使然） |

> **P0-A 的既有结论必须继承**：前端目前**不产生任何真实学习证据**（计划/练习/资源三个动作的第一跳是断的）。因此 §六 的六类状态样例，**P2 只能先用后端/harness 造数据**，**不得假装已有真实证据**。这一条是 P1→P2 交接的硬约束。

## 二、核心产物 1：`LearningSnapshot`（只读读模型）V1

**性质**：面向产品的**读模型**。只读、可追溯、带来源。**不得静默修改计划或掌握度** —— 修改只能由明确的学习动作和对应业务域完成。

```
LearningSnapshot
├─ student_id        : Long          必填
├─ course_id         : String        必填
├─ generated_at      : ISO8601       必填，生成时刻
├─ active_plan       : object|null   见 2.1
├─ current_node      : object|null   见 2.2
├─ mastery           : object        见 2.3
├─ recent_evidence   : array         见 2.4
├─ profile_context   : object|null   见 2.5
├─ freshness         : object        见 2.6
└─ next_action       : object|null   见 §五，可为空
```

### 2.1 `active_plan`

| 字段 | 类型 | 空值策略 |
| --- | --- | --- |
| `plan_id` | Long | — |
| `title` | String | — |
| `status` | enum(`in_progress`/`paused`/`completed`) | — |
| `current_step` | object\|null | 无未完成步骤 → `null` |
| `interrupted` | bool | 判定依据：`status == paused` **或** 当前步骤 `last_activity_at` 距今超阈值（阈值待 P2 定，登记为待裁决项） |

`current_step` 子字段：`step_id`、`order`、`topic`、`node_id`(nullable)、`status`。

### 2.2 `current_node`

「当前或最需要处理的知识节点」。`node_id: null` 表示本课程无可推荐节点（图谱为空或全部已掌握）。

| 字段 | 类型 | 来源 |
| --- | --- | --- |
| `node_id` | String | 图谱域 |
| `name` | String | 图谱域 |
| `reason` | enum(`current_step_node`/`weakest`/`next_ready`/`review_due`) | 见下 |

**`reason` 的取值顺序（V1 冻结优先级）**：
1. `current_step_node` —— 计划当前步骤绑定的 `node_id`（最优先，因为学生在计划里）；
2. `review_due` —— 存在 `last_review_at` 已过复习窗口的节点；
3. `weakest` —— 掌握度最低且 > 0 的节点；
4. `next_ready` —— 先修已满足、排序最靠前的未学节点（复用 `recommend_next_node`）。

### 2.3 `mastery`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `node_id` | String | 与 §2.2 一致 |
| `value` | float\|null | **`null` = 无记录 = 未学习**（与 0.0 语义合并，见 §三·④） |
| `level` | enum(`not_started`/`beginner`/`learning`/`proficient`/`mastered`) | 按 §三·③ 阈值映射 |
| `source` | enum(`node_masteries`/`plan_step_snapshot`/`none`) | **V1 主源 = `node_masteries`**；`plan_step_snapshot` 仅当主源缺失且计划内有快照时降级使用，并如实标注 |
| `last_evidence_at` | ISO8601\|null | 最后一次**有效证据**时间 |

### 2.4 `recent_evidence`

固定取最近 **N=5** 条（N 为 V1 冻结值）。每条即一条 `LearningEvidence`（字段见 §四），**只含已落库、可追溯的记录**；不得包含前端内存态或演示数据。

### 2.5 `profile_context`

**只保留本次推荐真正需要的偏好/困难信息**（总纲 §4.2 明确要求）。V1 允许字段：

- `weak_points`：String[]，最多 3 条（来源：`exercise_profile_service.enrich_profile`）
- `preferred_style`：String\|null（来源：画像域）
- `skill_level`：enum(`beginner`/`developing`/`proficient`)\|null

**禁止**把完整画像塞进来（越权、且与只读读模型定位冲突）。

### 2.6 `freshness`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `stale` | bool | 有任一来源数据超过各自时效 |
| `missing_sources` | String[] | 缺失的来源清单，取值：`active_plan`/`mastery`/`profile`/`graph` |
| `computed_from` | String[] | 本次实际参与计算的来源（可审计：哪些是真读到、哪些是缺省） |

**`computed_from` 是 P1 可解释性的核心** —— 它让"这个数字怎么来的"可被回答，而不是一个黑盒百分比。

## 三、P1-A 学习事实归属表（含本轮新发现的 5 个缺口）

### 3.1 归属表（总纲 §4.3 P1-A 要求）

| 学习事实 | 最终真源 | 唯一写入者 | 主要读取者 | 本次结论 |
| --- | --- | --- | --- | --- |
| 用户/课程身份 | Java `users`/`course` | 登录、选课（Java） | 全部页面 + AI 请求上下文 | ✅ 清晰 |
| 计划及步骤状态 | Java `learning_plans`+`plan_steps` | 计划域（Java） | 计划页、读模型 | ✅ 清晰 |
| **节点掌握度** | Java `node_masteries` | **⚠️ 当前无人写入** | 图谱、计划、推荐、统计卡 | ❌ **缺口①** |
| 学习活动/证据 | Java `learning_records` 等 | 练习/资源/计划（Java） | 学情分析、读模型、审计 | ⚠️ 前端第一跳断（P0-A 已登记） |
| 画像偏好与困难点 | Java `student_profiles` | 画像对话、练习分析（Java） | AI 辅助上下文 | ✅ 清晰 |

### 3.2 缺口① 掌握度落库缺失（**P1 最重要的一项裁决**）

**事实链**（逐个核对，非推断）：

| 计算掌握度的端点 | 位置 | 结尾动作 | 是否落库 |
| --- | --- | --- | --- |
| `POST /graph/masteries` | `GraphController.java:61-72` | `return Result.ok(result)` | ❌ 只回显 |
| `POST /api/plans/{planId}/progress` | `LearningPlanController.java:290-312` | 转发 Python 后 `Result.ok` | ❌ 只回显 |
| `POST /exercise/session/analyze` | 同上模式 | 只回显 | ❌ 只回显 |

**唯一落库入口**：`PUT /api/node-masteries/{nodeId}` → `NodeMasteryController.upsert`（`NodeMasteryController.java:38`）→ `NodeMasteryServiceImpl.upsert`（`NodeMasteryServiceImpl.java:42`，含 `@Transactional`，写 `mastery`/`review_count`/`last_review_at`）。

**前端接线状态**：`frontend/src/api/nodeMasteries.ts:33` 有 upsert 封装，**零页面引用**（P0-A 已登记）。

**三处 docstring 均声明"Java 自行持久化结果"**（`internal_api/graph.py:97`、`internal_api/plans.py`、`graph_center.py:100`），但 Java 侧无任何代码接过该责任。**净效果：掌握度算得出、响应里看得见、存不下去。**

**P1 裁决（队长已定：只定归属，代码放 P2）**：

> **归属**：`node_masteries` 是掌握度唯一真源，写入责任在 **Java**。
> **落库点（P2 实施）**：`POST /api/plans/{planId}/progress` 与 `POST /graph/masteries` 在拿到 Python 的 `mastery_updates` / `masteries` 后，**必须**调 `INodeMasteryService.upsert` 落库；`review_count` 递增规则见 §3.4。
> **幂等**：落库以 `(user_id, node_id)` 为键 upsert（现有唯一约束已保证），但**"是否应重算"由 §四 的证据幂等键决定** —— 重复提交同一证据不得再次推进掌握度。

### 3.3 缺口② `plan_steps.mastery_*` 是死字段

**事实**：
- **Java 写入点 = 0**（全仓 `mastery_current|mastery_after` 在 `*.java` 无匹配）。
- **Python 读取点 = 6 处**：`plan_center.py:433,446,450,549,713,721`（均作**计算输入或回退值**）。
- **Python 写入点 = 2 处**：`plan_center.py:517,533`，仅回填**响应体**，不落库。

**P1 裁决**：

> `plan_steps.mastery_current` / `mastery_after` 定位为**计划内冗余快照**：
> - **只用于展示**（"这一步进来时 0.5、出去时 0.62"），**不得作为任何掌握度计算的输入**；
> - **不要求 Java 回写**（回写只增复杂度、且与 `node_masteries` 形成双真源）；
> - P2 实现时，§三·④ 的默认值裁决必须**同时改掉 `plan_center._old_mastery` 的回退链**（见下）。
> - **备选**：若 P2 发现它连展示都不需要，可整体废弃（删列/删读写），本文件登记为**待 P2 裁决项**。

### 3.4 缺口③ 阈值三套口径（队长已裁决统一）→ **统一为 0.85 / 0.6 / 0.3 / 0**

**现状三套**：

| 场所 | 阈值 | 位置 |
| --- | --- | --- |
| Python 图谱状态 | 0.85 掌握 / 0.6 / 0.3 / 0 | `graph_service._mastery_to_status` |
| Python 图谱颜色 | 0.85 / 0.6 / 0.3 / 0 | `graph_service._mastery_to_color` |
| Python 图谱标签 | 同上 | `graph_service._mastery_to_tag` |
| **Java 统计卡** | **0.8 / 0.4** | `NodeMasteryServiceImpl.java:78-85` `getDistribution` |
| Python 技能分级 | **≥0.8 / ≥0.6** | `exercise_profile_service.enrich_profile` `skill_levels` |

**P1 冻结口径（V1）**：

| 掌握度区间 | `level` | 图谱状态 | 图谱颜色区段 | 标签 |
| --- | --- | --- | --- | --- |
| `null` / `0.0`（无记录） | `not_started` | 锁定 | 未开始 | 未学 |
| `(0, 0.3)` | `beginner` | 学习中 | 初步接触 | 初学 |
| `[0.3, 0.6)` | `learning` | 学习中 | 学习中 | 学习中 |
| `[0.6, 0.85)` | `proficient` | 学习中 | 基本掌握 | 基本掌握 |
| `[0.85, 1.0]` | `mastered` | 已掌握 | 熟练掌握 | 已掌握 |

**P2 需改动的两处**：
1. `NodeMasteryServiceImpl.getDistribution` 的 `0.8f` / `0.4f` → 按上表重算分桶（`mastered` = `>=0.85`，`proficient+learning` 合并为 `in_progress` 的口径需同步登记）；
2. `exercise_profile_service` 的 `skill_levels` 阈值 `0.8/0.6` → 对齐 `mastered`/`proficient` 边界 0.85/0.6。

> **注意**：图谱的 `_mastery_to_status` 是 `<=0.0 → 锁定`，即 **0.0 视为未开始**；与上表一致。`0.0` 与 `null` 在 `level` 上合并为 `not_started`，但 `value` 字段保留区分（`null` = 真的没记录，`0.0` = 有记录且值为 0），便于审计。

### 3.5 缺口④ 缺失数据默认值不一致 → **统一为 0.0**

**现状**：

| 入口 | 默认值 | 位置 |
| --- | --- | --- |
| 图谱入口 | `0.0` | `graph_center.py:105` `result.get(node_id, 0.0)` |
| 计划入口（主） | `0.5` | `plan_center.py:549` `masteries.get(node_id, step.get("mastery_current", 0.5))` |
| 计划入口（回归） | `0`（经 `or 0`） | `plan_center.py:721` `step.get("mastery_current") or 0` |
| 计划服务内部 | `0.5` / `0` 混用 | `plan_service.py:390` / `:54,:72,:214` |

**P1 冻结**：

> **无记录 = 未学习 = `0.0`。** 全链一致。
> - **理由**：`0.5` 会让"完全没学过"与"学过一半"无法区分，且使学生首次练习的得分变化失真（从 0.5 起算的 `+40%` 会虚高）；
> - **P2 改动点**：`plan_center._old_mastery` 的 `0.5` 兜底 → `0.0`；`plan_service.py:390` 的 `0.5` 兜底同步改 `0.0`；
> - **例外**：`plan_steps.mastery_current` 缺失时（历史数据），`0.0` 同样适用，但因 §3.3 已裁决它不作计算输入，影响面收窄。

### 3.6 缺口⑤ 辅导域完全不参与掌握度

**事实**：`plan_service.update_mastery` 支持 `tutor_question_asked`（`plan_service.py:195`，`min(current + 0.05, 1.0)`），但**全仓无生产调用点**（仅测试 `test_graph_endpoints_api_contract.py` 与 acceptance harness 构造过）。

**P1 裁决**：

> 保留 `tutor_question_asked` 在事件表内（算法已就位，属"答疑"类 `source_action`）。
> **本阶段不接线**。P2 若要接线，必须同时定义"什么算一次有效提问"（防刷分：同一会话重复提问不重复加分），该规则登记为 **P2 待裁决项**。

## 四、P1-B 学习证据合同（`LearningEvidence` V1）

### 4.1 字段（八字段 + 幂等键，总纲 §4.3 P1-B）

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `evidence_id` | String | ✅ | 证据唯一标识（UUID 或 `{source_action}:{source_record_id}:{node_id}`） |
| `student_id` | Long | ✅ | |
| `course_id` | String | ✅ | |
| `node_id` | String | ✅ | 无节点归属时使用保留值 `__none__`，不得为 `null`（便于索引与统计） |
| `type` | enum | ✅ | 见 4.2 |
| `occurred_at` | ISO8601 | ✅ | 学生动作发生时刻（非入库时刻） |
| `source_action` | enum | ✅ | 见 4.3 |
| `source_record_id` | String | ✅ | **幂等键的一半**，见 4.4 |
| `score_or_result` | float\|bool\|String\|null | ⭕ | 分数/对错/结果摘要 |
| `confidence` | float `[0,1]`\|null | ⭕ | 对这条证据的置信度（人工纠正 = 1.0） |
| `effect_hint` | enum\|null | ⭕ | **建议**怎样影响状态，**不是前端最终值** |
| `explanation` | String | ✅ | 必须能向学生/教师解释"为什么有这条记录" |

### 4.2 `type` 枚举（与现有算法对齐）

**V1 冻结 = 现有 4 个 + 人工纠正 1 个**：

| `type` | 现有算法支持 | 位置 |
| --- | --- | --- |
| `resource_viewed` | ✅ `min(current+0.1, 0.6)` | `plan_service.py:188` |
| `exercise_done` | ✅ `current + (score-current)*0.4` | `plan_service.py:191` |
| `exercise_failed` | ✅ `max(current-0.2, 0.0)` | `plan_service.py:193` |
| `tutor_question_asked` | ✅ `min(current+0.05, 1.0)` | `plan_service.py:195` |
| `manual_correction` | ❌ 需新增（P2） | —— |

**现有枚举定义处**：`app/api/models.py:160` 的 `Literal["resource_viewed","exercise_done","exercise_failed","tutor_question_asked"]`。P2 需扩展此 `Literal` 并同步 `MasteryUpdateRequest`。

### 4.3 `source_action` 枚举（总纲 §4.3 指定 5 类）

`exercise`（练习）｜`plan`（计划）｜`resource`（资源）｜`tutor`（辅导）｜`manual`（人工纠正）

**映射矩阵（V1 冻结）**：

| `source_action` | 允许的 `type` |
| --- | --- |
| `exercise` | `exercise_done`, `exercise_failed` |
| `plan` | `exercise_done`, `exercise_failed`, `resource_viewed` |
| `resource` | `resource_viewed` |
| `tutor` | `tutor_question_asked` |
| `manual` | `manual_correction` |

不合法的组合必须被拒绝（P2 在边界校验，快速失败）。

### 4.4 幂等规则（总纲 §4.3 强制要求）

**幂等键 = `(student_id, course_id, node_id, source_action, source_record_id)`**。

规则：
1. 同一幂等键的重复提交 → **丢弃，不重复记账**（不报错，幂等返回首次结果）；
2. `source_record_id` 由**产生记录的业务域**提供（练习 = `learning_records.id`、计划 = `plan_steps.id`、资源 = `resources.id`、辅导 = `messages.id`、人工 = 纠正记录 id）；
3. **无自然记录 id 的动作**（如 `resource_viewed` 的浏览）→ 由**客户端生成一次性 token** 作 `source_record_id`；服务端按幂等键去重；
4. **时间窗口辅助**：若客户端无法提供 token，服务端可用 `(student_id, node_id, type, occurred_at 取分钟) ` 作退化键，**但必须在 `explanation` 标注为退化判定**，且该退化路径登记为 **P2 待裁决项**（可能误合并）。

### 4.5 证据强度分级（总纲 §2.3 要求）

| 强度 | 证据类型 | 是否可改掌握度 |
| --- | --- | --- |
| **强** | `exercise_done`, `exercise_failed`, `manual_correction` | ✅ 可改 |
| **弱** | `resource_viewed`, `tutor_question_asked` | ✅ 可改，但增幅极小（现有算法已体现：+0.1 上限 0.6 / +0.05 上限 1.0） |
| **不可用** | 前端内存态、静态演示数据 | ❌ **严禁进入证据流** |

## 五、P1-D `next_action` 契约（总纲 §4.3 P1-D）

### 5.1 动作集合（V1 冻结 = 6 个，不得扩展）

```
review_current_node          复习当前节点
practice_targeted_questions  做针对性练习
ask_for_explanation          请求讲解
study_assigned_resource      学习指定资源
resume_plan                  恢复计划
check_prerequisite           检查前置知识
```

### 5.2 输出形状（V1 冻结 = 5 字段，总纲 §4.3 指定）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `action_kind` | enum(上表 6 值) | 学生要做什么 |
| `target` | object | `{node_id?, step_id?, resource_topic?}` —— 按 `action_kind` 填对应项 |
| `reason` | String[] | 来自哪几条证据（引用 `evidence_id`） |
| `expected_minutes` | int\|null | 预估耗时，可为空 |
| `entry` | String | 学生确认后进入的**既有业务域**（路由路径，如 `/learning-path`、`/exercise`） |
| `dismiss_policy` | enum(`snooze`/`alternative`/`manual_pick`) | 拒绝后：暂不推荐 / 换替代动作 / 请求手动选择 |

**硬红线（总纲 §4.3 末句）**：

> `next_action` **绝不能**返回"立刻调用 ResourceCenter 后再调用 ExerciseCenter"这种跨域执行指令。
> 一条建议 = 一个 `action_kind` + 一个 `entry`。**执行由学生点进去、由既有业务域完成。**

### 5.3 V1 推荐生成规则（可解释、确定）

| `action_kind` | 触发条件（V1） |
| --- | --- |
| `resume_plan` | `active_plan.interrupted == true` |
| `review_current_node` | `review_due` 或 `mastery.level ∈ {beginner, learning}` 且 `current_node.reason == current_step_node` |
| `practice_targeted_questions` | 最近 5 条证据含 `exercise_failed`，或 `mastery.level == learning` |
| `check_prerequisite` | `current_node` 存在未满足先修（复用 `check_prerequisites`） |
| `study_assigned_resource` | 计划当前步骤有绑定资源且未浏览 |
| `ask_for_explanation` | `mastery.level ∈ {not_started, beginner}` 且无 `exercise_*` 证据（纯陌生节点） |

**同时只返回 1 条**（V1 冻结）。多条建议排序剪枝登记为 **P2 待裁决项**。
