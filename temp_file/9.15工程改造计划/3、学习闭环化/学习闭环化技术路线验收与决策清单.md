# 学习闭环化技术路线验收与决策清单

> **用途**：配合《学习闭环化五优先级技术路线与实施总纲》使用。它不替代各阶段的实施测试；用于在进入下一优先级前判断：上一阶段是否真的结束，还是只完成了局部代码或展示。

---

## 一、全阶段通用检查

每次阶段交付必须分别留下下面四类证据；缺少任何一类只能标为“未执行”，不能用其他证据代替。

| 证据层 | 要证明什么 | 可接受例子 | 不能替代它的东西 |
| --- | --- | --- | --- |
| 离线测试 | 规则、DTO、幂等、异常分支 | pytest / JUnit / Vitest / 契约测试 | 手工截图 |
| 本地联调 | 同进程或受控环境的协议行为 | ASGI harness、前端 mock 流 | 真实跨服务运行 |
| 真实 HTTP | 前端、Java、Python、持久化的实际接口链 | 固定账号下的请求/响应/SSE 记录 | AsyncMock、旧快照 |
| 人工结果 | 学生能否理解并完成动作 | 截图、录屏、人工检查步骤 | HTTP 200、测试通过 |

每份验收记录还必须有：改动范围、未改范围、回退方式、遗留风险和下一动作。

---

## 二、P0 通过门：真实链路可信

- [ ] 已完成“学生动作 → 前端 → Java → Python → 持久化/响应”的台账，且每行标明证据级别。
- [ ] 已确认早期后端 TODO 与当前 Controller/Client/前端调用的实际差异；没有把旧文档直接视为当前状态。
- [ ] `AI_SERVICE_MOCK_LLM` 的真实聊天构造路径可离线运行，或配置缺失时能返回统一、可定位错误。
- [ ] 普通答疑、计划进度更新、练习评分各有至少一条可重复验证链路。
- [ ] 已区分真实页面数据和演示数据。

**进入 P1 的决策问题**：团队能否明确说出“当前学习事实写到哪里、哪条链路尚未真实跑通”？若不能，停在 P0。

---

## 三、P1 通过门：学习状态可信

- [ ] `LearningSnapshot V1` 字段、来源、更新时间和空值策略已冻结。
- [ ] 计划、节点掌握度、学习活动、记录、画像等长期事实都有唯一真源和写入边界。
- [ ] `LearningEvidence V1` 有唯一 ID、来源动作、来源记录 ID、节点归属、发生时间和解释字段。
- [ ] 同一作答/活动重复提交不会重复改变学习状态。
- [ ] 至少覆盖正确、错误、完成、仅浏览、中断、学生纠正六类样例。
- [ ] “下一步建议”被限定为学生可选择的动作卡，而不是跨 Center 执行命令。

**进入 P2 的决策问题**：面对一个固定学生和课程，系统能否不靠人工拼凑而给出可追溯的当前学习状态？若不能，停在 P1。

---

## 四、P2 通过门：单课程闭环真实发生

- [ ] 试点课程、节点集、测试账号和课程资料范围已固定。
- [ ] 新进入、正常学习、连续错题、中断恢复、完成节点五种状态至少各有一条场景。
- [ ] 建议卡说明“做什么、为什么、从哪里开始”，学生可以拒绝或更换方式。
- [ ] 学生确认后只进入一个已有业务域；没有后台自动连调多个 Center。
- [ ] 动作完成后形成带来源的学习证据，并能改变或解释为何不改变下一次建议。
- [ ] 覆盖重复提交、计划失效、建议拒绝、网络重试四种边界。
- [ ] 有一份从初始状态到下一次建议的完整真实 HTTP + 人工演示证据。

**进入 P3 的决策问题**：学生是否能在不理解系统内部模块的情况下完成一次“建议 → 学习 → 结果 → 新建议”？若不能，先修 P2，不进入页面扩展。

---

## 五、P3 通过门：学生面对的是学习入口，而非功能堆

- [ ] 首页或学情入口可展示真实的当前行动、理由和数据更新时间。
- [ ] 点击行动可带明确上下文进入真实计划、练习、资源或对话页。
- [ ] 至少一个试点页面已从静态演示数据替换为真实数据链路。
- [ ] 完成一次动作后，入口页能反映真实变化。
- [ ] 没有数据、数据过期、建议失效时有诚实且可用的降级展示。
- [ ] 用户可见进度文案不暴露内部 Agent、节点名或推理内容。

**进入 P4 的决策问题**：是否已有真实用户/演示场景暴露出取消、断线、长任务、并发或排障痛点？没有就不提前做 P4。

---

## 六、P4 的最小决策门（不作为当前硬目标）

只有下列问题真实出现时才分别立项：

| 真实问题 | 才考虑的能力 |
| --- | --- |
| 用户取消后模型仍继续运行 | 取消传播与工作流终止 |
| 弱网下重复显示/丢失进度 | `run_id`、`seq`、重连和去重 |
| 生成快于浏览器消费 | 背压、队列上限、超时 |
| 无法定位一次请求卡在哪 | 跨服务追踪、耗时、错误关联 |
| 真实并发压力出现 | 限流、任务执行器、再评估队列/分布式方案 |

不因“看起来企业级”而默认引入 Kafka、Redis Streams 或全面 WebSocket 改造。
