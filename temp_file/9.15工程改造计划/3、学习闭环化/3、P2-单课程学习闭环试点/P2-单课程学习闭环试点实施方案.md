## 〇、四个强制问题（总纲 §九 要求，逐条先答）

### 问题 1：学生在这一阶段获得什么？

**首次出现真正可见、可解释、可回归的变化。**

P1 交付的是"地基承诺"（数字同源），学生看不见。P2 不同：学生第一次会看到一个**建议卡**，卡上写明"做什么、为什么、从哪里开始"，点"开始"进入一个**已有业务域**，做完之后**掌握度、计划状态、下一条建议会真的变** —— 而且变得可解释（每条建议带证据来源）。

**必须如实登记的边界**：本轮**不新建前端业务能力**，建议卡只做引导与跳转（总纲 §5.4 硬红线）；资源生成、答疑、出题、改计划仍由各自 Center 自己执行。且 P0-A 已确认前端计划/练习/资源三个动作的第一跳是断的 —— **P2 的闭环证据以"后端/harness 造数据 + 真实 HTTP"为主，不得假装已有真实前端证据**（P1 §6.2 硬约束）。

### 问题 3：哪些数据是真源、怎样回滚？

**真源（P1 已冻结，P2 起生效）**：
- 掌握度唯一真源 = `node_masteries`（Java 拥有，`UNIQUE KEY uk_user_node(user_id,node_id)`）
- 学习证据真源 = 现有落库记录（`learning_records` / `learning_activities` / `messages` / `resources`，Java 拥有）
- 计划真源 = `learning_plans` + `plan_steps`（Java 拥有）
- Python 侧**保持零状态**：`LearningSnapshot` 现算现返，Java 可缓存但不得作为真源

**回滚**：
- **纯 Python 改动**（阈值、默认值、读模型、证据契约、`next_action`）= `git revert` 单个 commit，无数据结构变更，成本为零。
- **Java 落库接线**（缺口①）是唯一有写入副作用的变更 → 回滚 = revert commit；已写入的 `node_masteries` 行**不删**（P1 已定它本就是真源，回滚只停"新的自动写入"，不停读写路径）。
- **若未来必须新增表/列** → 加法式变更（停写新列 + 保留旧读写路径），不做破坏性迁移。

### 问题 4：如何分别证明离线、真实 HTTP、人工体验与未执行项？

四类证据**分级登记，任何一类缺失都必须标注"未执行"，不得互相替代**：

| 证据类别 | P2 提供什么 | 状态 |
| --- | --- | --- |
| **① 离线单元/契约测试** | P1 §6.3 的 A1–A6、A8 落为契约测试；阈值边界、默认值、幂等、非法组合 | 计划执行 |
| **② 本地 ASGI / 前端模拟联调** | 新增 harness：`acceptance/harness/learning_snapshot.py`、`plan_closure.py`，用 `httpx.ASGITransport` 打读模型与进度端点 | 计划执行 |
| **③ 真实 HTTP（前端→Java→Python→持久化）** | A7：`POST /api/plans/{id}/progress` 后 `node_masteries` 确有写入（需 Java 侧就绪） | **取决于 Java 落地**；未就绪则标注"未执行" |
| **④ 人工可见结果** | 建议卡人工演示截图/响应 | **若建议卡不做前端，则标注"未执行（设计使然）"** |

## 二、现状摸底结论（本轮逐文件复核，非推断）

### 2.1 缺口① 掌握度落库缺失 —— 复核确认仍在

| 端点 | 位置 | 结尾动作 | 落库 |
| --- | --- | --- | --- |
| Java `POST /api/plans/{planId}/progress` | `LearningPlanController.java:290-312` | `:308 return Result.ok(result)` | ❌ |
| Java `POST /graph/masteries` | `GraphController.java:61-72` | `:68 return Result.ok(result)` | ❌ |
| Python `POST /plans/{plan_id}/progress` | `internal_api/plans.py:124` | 返回 `{"mastery_updates": {...}}` | ❌（设计如此，Python 零状态） |
| Python `POST /graph/masteries` | `internal_api/graph.py:95` | 返回 `{"masteries": {...}}` | ❌（同上） |

**唯一落库入口**：`NodeMasteryController.upsert`（`NodeMasteryController.java:38-47`）→ `NodeMasteryServiceImpl.upsert`（`:42`，`@Transactional`，写 `mastery`/`review_count`/`last_review_at`）。**零自动调用方。**

**Python 返回体形状（落库时按此取值）**：
- `POST /plans/{id}/progress` → `mastery_updates: {node_id: {old_mastery, new_mastery, delta, event_type}}`（`plan_center.py:504-509`）
- `POST /graph/masteries` → `masteries: {node_id: float}`（`graph_center.py:109`）

> ⚠️ **落库只写 `new_mastery`，不写 `old_mastery`/`delta`**（后两者是响应体展示用）。

### 2.2 缺口③ 阈值口径 —— 复核确认

| 场所 | 现状 | 目标 |
| --- | --- | --- |
| Python 图谱状态/颜色/标签 | `0.85/0.6/0.3/0`（`graph_service.py`） | **已是目标值，不动** |
| Python 技能分级 | **百分制** `acc>=80` / `acc>=60`（`exercise_profile_service.py:77-82`） | `80 → 85` |
| Java 统计卡 | `0.8f` / `0.4f`（`NodeMasteryServiceImpl.java:82-83`） | `0.85f` / `0.6f` |

> **重要澄清（P1 §3.4 表述需修正）**：`exercise_profile_service` 的阈值是**准确率百分数**，不是掌握度小数。P1 写的"`0.8/0.6`"实为 `80/60`。因此 Python 侧改动是 `80 → 85`，`60` 不动。

### 2.3 缺口④ 默认值 —— 复核确认

| 入口 | 现状 | 目标 |
| --- | --- | --- |
| 图谱入口 | `0.0`（`graph_center.py:105`） | **已是目标值** |
| 计划入口 | `0.5`（`plan_center.py:549`） | `0.0` |
| 计划入口（无 node） | `0.5`（`plan_center.py:548`） | `0.0` |
| 计划服务内部 | `0.5`（`plan_service.py:390`） | `0.0` |

### 2.4 关于 `GraphController` vs `KnowledgeGraphController` —— 澄清（重要）

前序会话曾误记"P1 引用的 `GraphController` 应改为 `KnowledgeGraphController`"。**本轮复核证明这是两个并存的、不同的类**：

- `GraphController.java:61` = `POST /graph/masteries` → `pythonClient.updateMasteries(...)` ← **P1 的引用正确**
- `KnowledgeGraphController.java:50` = `GET /masteries/{courseId}` → `masteryService.getDistribution(...)`（**统计卡**，是缺口③ Java 侧的落点）

**结论：P1 锚点无需修正，此澄清不得再作为"纠错"带入后续。**

### 2.5 试点课程

`ai_intro`（`ai-service/data/knowledge_graph_skeleton.json`）：**10 节点 / 15 边**，覆盖 `depends_on`/`extends`/`parallel` 三种关系，难度 1–5 齐备，含 `skill` 类型节点。它同时是全仓默认 `course_id`。满足总纲 §5.2 五条标准（节点关系清楚、有难度梯度、可明确归属错题）。

### 决策点 4：证据幂等键的落库位置

`LearningEvidence` 的幂等键 = `(student_id, course_id, node_id, source_action, source_record_id)`。

- P1 定"证据真源 = 现有落库记录 + 未来按契约补的幂等键列" → 意味着 **Java 侧需新增列/索引**。

```
┌─────────────────────────────────────────────────────────────┐
│ 前端（P2 不动）                                              │
│   建议卡 = JSON 响应（本轮由 harness/人工演示消费）           │

│   ★ P2 新增：收到 Python 结果后调 INodeMasteryService.upsert  │
└──────────────────────────┬──────────────────────────────────┘
                           │ 请求体带全部上下文（零状态）
┌──────────────────────────▼──────────────────────────────────┐
```

4. 建议失效（计划被删/节点不存在/数据很旧）→ 降级为"请从学习计划中选择下一项"（总纲 §5.5 第 3 条）

## 十、回滚方式

| 变更 | 回滚 |
| --- | --- |
| Task 1（阈值/默认值） | `git revert` 单 commit，零结构变更 |
| Task 2–5（契约/读模型/建议/白名单） | `git revert` 单 commit，新增端点不影响旧链路 |

## 十二、一句话收口

> **P2 不是把闭环做大，而是把闭环做真一次。** 一个课程、一个学生、五种状态、四条边界 —— 从"系统建议"到"动作产生证据"到"下一次建议变化"，每一步都能指出来源、都能回滚。
