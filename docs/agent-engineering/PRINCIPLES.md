# AI Agent 工程化改造原则

> 状态：持续维护的决策基线。
> 目标：将“智学云 DeepTutor”整理为可真实展示、可验证、可面试深挖的 AI Agent 工程项目。

## 1. 项目定位

- **主定位**：AI Agent 工程师。
- **辅助定位**：AI 应用开发能力。
- **主叙事**：面向个性化学习场景的多 Agent / Workflow 工程系统。
- **展示主线**：资源生成（Resource Generation）Workflow。

前端与 Java 后端是完整产品的集成层；简历中应如实说明其历史分工与后期接手维护情况。个人主责叙事聚焦 Python AI 服务、Agent、Workflow、上下文、质量控制与评测。

## 2. 以现有代码为事实起点

当前资源生成链路为：

```text
RouterAgent → ResultAgent → ResourceCenter → ResourceGenWorkflow
→ Director 路由 → 单个 Specialist Agent → Finalize
```

其中 `ResourceGenWorkflow` 目前是“模块化单 Specialist Workflow”：Director 从内容、代码、项目、思维导图、闪卡、交互式图解等 Agent 中选取一个执行。

因此，在完成本轮改造和验证前，**不将这条链路表述为严格的多 Agent 协作系统**。

## 3. 改造目标：有界多 Agent Workflow

在保留现有外层路由、Center 和 SSE 机制的前提下，将资源生成主链路演进为：

```text
Planner / Director
        ↓
Specialist Generator
        ↓
Reviewer / Validator
   ├── 通过 → Finalizer → 结构化结果
   └── 不通过 → Repair（最多一次）→ 再校验
```

这不是为了增加 Agent 数量，而是为每个角色建立明确职责、输入、输出和失败边界。

## 4. 状态与记忆原则

每次资源生成使用独立的 Workflow State，至少分为四类：

1. **请求上下文**：运行 ID、主题、资源类型、学生画像快照。
2. **路由计划**：目标 Agent、子类型、规划大纲、路由依据。
3. **生成产物**：草稿内容块、质量报告、最终内容块。
4. **执行控制**：阶段耗时、错误、重试次数、SSE 事件。

学生画像与对话历史属于跨会话的长期数据；Workflow State 只保存本次运行所需的快照和中间产物。二者不能混用。

## 5. Agent 协议原则

- Planner 只负责选择执行策略和准备上下文。
- Specialist 只负责生成指定类型的资源，并输出结构化内容块。
- Reviewer 采用轻量 LLM-as-Judge 门控，输出固定格式：`pass` 或 `repair`、一句原因、最多 3 条可执行修复建议；不使用多维百分制评分。
- Repair 只根据质量报告修复当前草稿，最多执行一次。
- Finalizer 负责确定性聚合和对外响应，不额外引入无必要的 LLM 调用。

每个角色都应能独立测试；不得依赖隐式的全局上下文或“上一个 Agent 好像说过什么”。

## 6. 可靠性与成本原则

- 优先规则路由，LLM 只作为无法判断时的兜底。
- 先由确定性 Validator 检查内容块、必填字段和类型/基础格式；LLM Judge 只判断是否值得修复。
- 所有循环必须有上限；默认最多一次修复。
- 生成失败时优先降级到现有内容生成能力，而不是让整条请求失败。
- Judge 不可用时不阻塞主请求，返回已通过基础校验的草稿，并记录未评审状态。
- 记录每个阶段的耗时、模型调用、重试和失败原因。
- 不为展示而引入无收益的多 Agent、Memory、RAG 或微服务复杂度。

## 7. 评测与证据原则

每次重要改造都要留下可复现证据：

- 覆盖典型资源请求的固定样例集；
- 路由正确性、结构化输出有效率、修复触发率、端到端耗时等指标；
- 失败与回退案例；
- 改造前后的结果对比。

没有验证结果的“能力提升”不写入简历亮点。

## 8. 失败、回退与 SSE 原则

- 输入不合法时在 API 层直接返回明确的 4xx 响应，不进入 Workflow。
- 路由不确定时依次使用规则、LLM 兜底和默认 `content` 路由。
- Specialist 生成失败或超时时，优先使用现有内容生成能力降级；若仍无法形成合法结构，返回统一错误结果。
- Validator 或 Judge 要求修复时，最多修复一次；Judge 的主观判断不能吞掉已经通过确定性校验的可用结果。
- SSE 复用现有事件协议，以 `plan → generate → review → repair（可选）→ finalize → done` 表达进度。
- 所有运行都应以一个 `done` 事件结束；非致命的 Judge 跳过、质量不足或降级不作为前端请求失败处理。

## 9. 简历与面试原则

项目资产不只有代码，还包括可解释的工程故事：

```text
Problem → Constraints → Options → Decision → Trade-off → Result
```

每项关键改造都应能回答：为什么需要它、为何不采用其他方案、失败如何处理、如何验证收益。

不夸大个人贡献，不把队友历史实现直接写成个人从零开发；以提交记录、代码、测试和文档作为事实依据。

## 10. 范围约束

- 首先只深挖资源生成主链路，不同时重写所有 Center 和全部 Agent。
- 第一版的轻量 Judge 仅正式覆盖 `content`（课程文档/学习资源）与 `interactive_diagram`（交互图解）；其他资源类型保留现有生成能力。
- 现有产品功能保持可用，避免为重构破坏比赛项目已有能力。
- 先完成一条能讲透、能评测、能演示的 Workflow，再扩展到其他链路。

## 11. 后续工作方式

每一轮改造开始前，先明确：目标、现状、候选方案、验收标准和风险；完成后补充验证结果与面试问题。

本文档只记录已确认的长期原则。具体状态字段、Reviewer 规则、评测样例和实施步骤，将在后续设计文档中单独确认。
