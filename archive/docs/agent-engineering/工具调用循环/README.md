## 〇、一分钟版本

| 问题 | 答案 |
|---|---|
| 工具循环是什么 | "模型说要调工具 → 系统执行 → 结果塞回对话 → 再问模型"的 while 循环 |
| 我们现在有吗 | **没有**。我们有多步协作，但"下一步走哪"由**代码**决定，不由**模型**决定 |
| 差在哪 | 我们发给模型的请求体里**没有 `tools` 字段**（`llm_service.py:393-400`），模型根本不知道世上有工具 |
| 为什么需要 | 模型不能"临时喊一声我要查资料/算个数/搜实时信息"，检索关键词错就只能错着答，算数靠脑补、实时事实靠旧记忆（幻觉来源之一） |
| 怎么补 | 不推翻现有架构：**在 LangGraph 图的某个节点内部，加一个模型主导的工具循环**。图管大流程，节点内跑循环 |
| 分几步走 | 三阶段：① Tutor 试点 → ② 治理（圈数/超时/审计/mock）→ ③ 按域推广 |

## 一、术语表（先对齐词汇）

| 术语 | 意思 |
|---|---|
| **工具（Tool）** | 系统里一个可被调用的函数：联网搜索、向量检索、算数、查库…… |
| **工具说明书（Tool Spec）** | 一段 JSON，描述"工具叫什么、要什么参数、干什么用"，随请求发给模型 |
| **原生工具调用（Native FC）** | 模型自带的能力：按固定格式输出"我要调 X 工具、参数是 Y" |
| **工具调用循环** | 说→做→喂回→再说的 while 循环；每转一圈对话包长一节 |
| **ReAct** | 上述循环的思想模型：Reason（想）+ Act（做）交替，观察结果再想 |
| **LangGraph** | 我们在用的"流程图画图工具"：把多个步骤连成图、按图执行。**它不自带工具循环** |
| **条件边（conditional edge）** | LangGraph 里"满足什么条件走哪条线"的连线，**判断函数是我们写的代码** |
| **反思（Reflection）** | 生成后由专门环节检查、不合格打回重做。我们有工程化版本（质量门 repair） |

## 二、现状架构（2026-10-15 基准）

### 2.1 总体形态：流程图，不是循环

我们的多步调用是 **LangGraph 状态图**（StateGraph，作用：把多步操作连成一张图、按图执行），特征是：

- **节点（node）= 一个 Agent 干一次活**：一次 LLM 调用 + 该角色的后处理
- **连线写死或由代码函数判断**，模型无权改变流程
- **节点间传的是结构化 state**（带类型的 Python 字典），不是对话消息列表

代表例子（真实连线，全部已验证）：

```
TutorAgent（app/agents/tutor_agent.py:76-81）：
    retrieve ──固定──→ respond ──→ END

DeepSolve（app/workflows/deep_solve.py:46-48）：
    plan → investigate → solve → verify    （四步全固定）

ResourceGen（app/workflows/resource_gen.py:177-191）：
    plan → generate → validate ─┬ 通过 → review → finalize
                                └ 不过 → repair ──→ 回 validate
                                  （唯一会"转圈"的地方，但圈数与条件由代码定）

ProfileAgent（app/agents/profile_agent.py:112-115）：
    extract → semantic_judge → merge → audit → response
```

### 2.2 LLM 调用层：请求体里没有工具

`app/services/llm_service.py` 的 `chat()`（:366）/ `chat_stream()`（:452）发出的请求体只有六个键：

```python
{
    "model": ..., "messages": ..., "temperature": ...,
    "max_tokens": ..., "thinking": {...}, "stream": ...
}
```

（证据：`llm_service.py:393-400`）

**没有 `tools`、没有 `tool_choice`。**这意味着：

1. 模型**不知道**系统里有任何工具
2. 模型**不可能**输出"帮我调 X"的指令
3. 即使模型在正文里"求"我们查什么，调用层也没有解析与执行的机制

### 2.3 "检索"现在由谁决定：代码，不是模型

以 TutorAgent 为例，知识库检索是否发生、用什么查询词，**全是代码说了算**：

- 图里固定先走 `retrieve` 节点（`tutor_agent.py:81`）
- 节点内部用确定性逻辑判断"要不要注入知识库"（`should_inject_kb`，按 kb_top_score 阈值，:291 附近）
- 检索查询词来自**用户原话**（ContextBuilder 的 relevance query），模型无权改写、无权追加

**后果**：用户问"那线程呢？"这种指代型追问，检索词可能根本搜不到东西；模型明知缺资料，也只能硬答。

### 2.4 我们已有的"伪循环"：质量门 repair

`ResourceGen` 的 `validate → repair → validate` 是**目前全项目唯一会转圈的结构**（`resource_gen.py:179-190`）。但它和工具循环有本质区别：

| | 质量门 repair | 工具循环 |
|---|---|---|
| 谁发现"不行" | **代码**（质量门评分） | **模型**（看着工具结果自己判断） |
| 转圈做什么 | **重做同一件事**（重新生成） | **获取新信息**（调新工具、拿到新事实） |
| 圈数上限 | 代码定死 | 循环运行时由模型收敛 |

两者互补：repair 管"质量"，工具循环管"信息"。**目标架构是两者并存。**

### 2.5 现状能力小结

| 能力 | 状态 | 证据 |
|---|---|---|
| 多步协作（多角色串行） | ✅ 有，成熟 | 全项目 8+ 张图（agents/、workflows/） |
| 条件分支 | ✅ 有，代码判断 | `add_conditional_edges`（resource_gen.py:179、profile_workflow.py:79 等） |
| 结构化状态传递 | ✅ 有，比"纯消息列表"更稳 | 各 Agent 的 State TypedDict |
| 质量门 + 打回重做 | ✅ 有 | resource_gen validate/repair |
| **模型自主调工具** | ❌ **没有** | 请求体无 tools 字段（llm_service.py:393-400） |
| **模型改写/追加检索词** | ❌ 没有 | 查询词来自用户原话 |
| **模型算数/验证** | ❌ 没有 | 无执行类工具 |

## 三、目标架构（期望的工具循环）

### 3.1 设计总纲

> **图管大流程，节点内跑工具循环。**

- **LangGraph 图继续当骨架**：域路由、阶段划分、质量门这些"必须确定性"的东西不动
- **工具循环作为图的一种新节点类型**嵌入：在该节点内部，模型获得"自己决定下一步"的权力
- **决定权分级**：该交给模型的交给模型（要不要再查、查什么词），该留给代码的绝不放（能不能联网、调哪些工具、最多转几圈）

### 3.2 目标形态（以 TutorAgent 为例）

```
【现状】
    retrieve ──固定──→ respond ──→ END
   （代码检索）      （模型一次作答）

【目标】
    retrieve ──→ respond(工具循环节点) ──条件──→ END
                     ↑        │
                     │        ├─ 模型说"够了" → 出正文 → END
                     └────────┤
                              └─ 模型说"我要查 XX / 算 XX"
                                    → 执行工具 → 结果进 state
                                    → 回到本节点再问模型
```

变化清单（**只有三处**）：

1. **`respond` 节点挂上工具说明书**：LLM 请求体新增 `tools` 字段（`bind_tools` 等价物），首批工具建议只开三个——`kb_search`（改写检索词并重查）、`calculator`（精确计算）、`web_search`（联网检索实时信息，如最新价格/版本/新闻；只查不改、结果标注来源）
2. **节点内部加循环**：模型返回工具调用 → 执行 → 结果作为一条 `tool` 角色消息追加进 messages → 再调模型；返回纯正文 → 出循环
3. **state 扩一个字段**：`tool_trace: list[dict]`（每次调用记 `{tool, args, result_digest, ms}`），供审计与前端"执行过程"展示

### 3.3 循环节点的运行时规则（必须全部满足）

| # | 规则 | 为什么 |
|---|---|---|
| R1 | **圈数上限**（建议 4，可配 `TOOL_LOOP_MAX_ITERATIONS`） | 防模型无限要工具；open-webui 同款防线（其 `middleware.py:5904-5908, 6386-6393`） |
| R2 | **整环节点级超时**（并入现有 Center 超时预算，不新开体系） | 直接回应 review §3.6"活跃 LLM 任务无超时"的 P0 |
| R3 | **工具白名单按 Agent/域分配**，不是全局一套 | 教学场景不需要 40 个内置工具；Exercise 域开 calculator，Tutor 域开 kb_search + web_search，各管各的 |
| R4 | **工具结果不直接给用户**：只进模型上下文；用户看到的仍是正文 token 流 | 前端契约（token 帧 = 正文）不变，SSE 协议零改动 |
| R5 | **工具执行期间不发 token**：进入工具调用分支后，本轮 token 流暂停，循环结束后一次性流式吐最终正文 | 避免前端收到"正文一半 → 中断 → 又一段"的拼接灾难 |
| R6 | **每次工具调用过 `routing_audit`**：记 trace_id / tool / args 摘要 / 耗时 / 结果是否为空 | 与现有观测体系对齐；顺带补上 review §3.14"审计是死代码"的接线 |
| R7 | **mock 模式必须可用**：`use_mock_llm=True` 时，mock LLM 返回预设的工具调用序列与正文，全链路可离线测试 | 现有测试体系的硬约束（无 Key 环境要能跑） |
| R8 | **断连即全链取消**：工具循环所在的协程必须能被 cancel 且清理干净（aclose 生成器、cancel 子任务） | 直接回应 review §3.1/§3.2 的孤儿任务 P0——**加了循环后这个 P0 的后果会被放大**（多圈 = 多次 LLM 调用 = 并发额度被占更久） |
| R9 | **工具失败降级不致命**：单个工具报错 → 把错误信息作为工具结果喂回模型（让它自己决定换路或直答），不抛异常打断整轮 | 工具循环的价值就在于模型能对失败做出反应 |
| R10 | **幻觉护栏不跳过**：现有 `kb_verify` / `response_sanity` 在循环出口处照常生效 | 循环给了模型更多信息，但输出仍须过同一道门 |
| R11 | **联网工具专属安全**：`web_search` 只允许传**搜索词**（query），不开放任意 URL 抓取（防 SSRF）；后端只走白名单搜索服务；结果条数设上限（建议 top 5）；单次超时（建议 5s）；回答引用搜索结果时标注来源与「信息可能过时」 | 联网结果不可信、可能违规或过期；把抓取面收敛到「搜索词 → 白名单 API → 摘要」最小闭环，同时守住教育场景的内容安全 |

### 3.4 目标能力对照

| 能力 | 现状 | 目标 |
|---|---|---|
| 检索词是否贴合指代型追问 | ❌ 用户原话直搜 | ✅ 模型改写（"那线程呢" → 结合上文生成"线程 thread 概念"） |
| 缺资料时模型能否自救 | ❌ 硬答 | ✅ 主动追加检索 |
| 精确计算 | ❌ 脑补 | ✅ calculator 工具 |
| 实时事实（价格/版本/新闻） | ❌ 用过时记忆硬答（幻觉） | ✅ web_search 工具 + 来源标注 |
| 决定权 | 100% 代码 | 代码定边界（工具清单/圈数/超时），模型定路线（调不调、调哪个） |
| 可预测性 | ✅ 完全确定 | ⚠️ 边界内不确定——由 R1/R3/R6 兜住 |
| 可测试性 | ✅ 1595 测试锁行为 | ✅ R7 保证离线全链路可测 |

## 四、演进路线（三阶段，每阶段可独立交付）

### Phase 1 · Tutor 试点（最小闭环）

- [ ] `llm_service` 请求体支持可选 `tools` 参数（`chat()` / `chat_stream()` 各加一个形参，默认 None = 现状零变化）
- [ ] 写三个首批工具：`kb_search(query)`、`calculator(expr)`、`web_search(query)`（kb_search/calculator 各 ~30 行；web_search 接白名单搜索后端，含超时/结果截断/来源标注/mock 实现）
- [ ] `TutorAgent.respond` 节点改造为循环节点（实现 R1/R4/R5/R7/R9）
- [ ] `TutorState` 加 `tool_trace` 字段
- [ ] 契约测试：mock 模式下验证"模型要工具 → 执行 → 收敛 → done 唯一"四件事
- **验收**：指代型追问（"那线程呢？"）的检索命中率，改写前后对比；calculator 消除 1 类算数幻觉；web_search 让「实时价格/最新版本」类提问从"旧记忆硬答"变为"检索后作答并标来源"
- **状态**：`未开始（2026-10-15）`

### Phase 2 · 治理（把 R2/R6/R8/R10 钉死）

- [ ] 循环节点纳入 Center 超时预算
- [ ] 工具调用接入 `routing_audit`（同时把审计从 `execute` 迁到 `stream_chat`，顺手修 §3.14）
- [ ] 断连取消契约测试：断言 `asyncio.all_tasks()` 不残留循环协程（同时修 §3.1/§3.2）
- [ ] 工具结果消化进 `ContextBuilder` 的固定顺序（工具结果属于"相关知识库证据"段，不另立门户）
- **验收**：工具调用 100% 有审计记录；断连后零孤儿任务
- **状态**：`未开始（2026-10-15）`

### Phase 3 · 按域推广（只推有明确收益的域）

| 域 | 是否引入循环 | 首批工具 | 理由 |
|---|---|---|---|
| Exercise（出题） | 建议引入 | `calculator`、`kb_search` | 题干数值需要精确；题目需贴知识点 |
| Plan（规划） | 暂缓 | — | 现有 Goal→Decompose→Schedule 分工已够，强行加循环反而破坏确定性 |
| Visualization | 暂缓 | — | 已有独立 pipeline 与质量门 |
| 资源生成 | 暂缓 | — | validate/repair 已是"代码版反思"，先看 Tutor 试点效果 |
- **状态**：`未开始（2026-10-15）`

### 明确不做的

- ❌ 不引入 LangChain Agent / create_react_agent 全家桶（我们要的是**一个节点内 ~50 行的手写循环**，不是一套框架）
- ❌ 不开放"用户自定义工具"（教学场景没有这个需求，且是权限大坑）
- ❌ 不给 Planning/编排层放权（CapabilityGate 与 Dispatcher 的决定权**永远在代码**——这是本项目的差异化，不学 open-webui 的"全放给模型"）

## 五、与参考项目的对照（决策依据存档）

| | open-webui（参考） | 我们（现状） | 我们（目标） |
|---|---|---|---|
| 谁决定下一步 | 模型（纯工具循环，无图） | 代码（纯图，无循环） | **图定边界 + 模型定路线**（图内嵌循环） |
| 工具数量 | ~40 内置 + MCP + 用户自定义 | 0 | 每域 2-3 个白名单（Tutor：kb_search / web_search / calculator） |
| 圈数防护 | 有（迭代上限） | —（无循环） | 有（R1，默认 4） |
| 结果回传形态 | 追加进 messages | — | 追加进 messages + `tool_trace` 审计 |
| 检索词生成 | LLM 改写（`generate_queries`） | 用户原话直搜 | LLM 改写（作为 kb_search 工具的入参） |

> 对照结论：open-webui 的工具循环证明了"模型主导"路线的工程形态与防线设计（圈数、增量拼接、错误兜底）；我们吸收其**防线**，不照搬其**放权范围**——因为它的场景是通用助手（无法预知用户要什么），我们的场景是教学（必须保证"出题就出题、答疑就答疑"）。
