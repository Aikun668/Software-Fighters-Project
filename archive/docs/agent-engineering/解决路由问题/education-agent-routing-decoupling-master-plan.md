# 教育多智能体系统｜路由与 Agent 架构解耦总执行计划

> **文档性质**：实施路线与阶段验收约定（架构级，不是代码任务书）  
> **版本**：V1.0 · 2026-10-13  
> **当前进度**：T0 重构前基线已完成；**T1 尚未开始，尚未授权生产代码改造**。  
> **适用范围**：Vue 前端、Java Spring Boot 中台、Python FastAPI AI 服务之间的对话路由与 Agent 编排。  
> **约束**：本文件不假定具体代码实现；需要确认类、接口、依赖或修改范围时，由 Coding Agent 提供源码证据，之后再制定单阶段编码任务书。

## 0. 改造目标、约束与工作方式

### 0.1 为什么改造

当前系统以对话为唯一入口，由规则路由选择业务 Center，再调度专业 Agent 产出答疑、练习、资源、计划、可视化、画像等结果。已有调查表明，系统中存在能力映射分散、意图判断与计划构建混杂、复合请求可能漏执行、上下文与结果处理职责交叉等问题。

**目标不是推倒现有多 Agent 体系，也不是增加更多 Agent；而是统一能力语言、减少重复决策，让路由更懂用户，让各 Center/Agent 只负责明确的业务。**

### 0.2 最终约定的逻辑链

**用户消息 + 必要上下文 → 意图决策 → 执行计划构建/执行前裁决 → Dispatcher → 业务 Center / Agent / Workflow → 标准化结果与 SSE → Java 持久化。**

其中：

- **意图决策**回答“用户想完成什么”，允许多意图；先尝试高精度确定性判断，不确定时再按需语义判断。
- **能力映射**定义“系统能做什么、谁来执行、预期交付什么”，区分 *意图 / 业务能力 / 执行动作 / 产物类型*；不得默认一一对应。
- **执行计划**回答“本次执行什么、先后顺序是什么、哪些任务真正依赖前一任务结果”；它不是静态能力清单。
- **执行层**负责完成已确定的工作流，允许 Center 内部调度专业 Agent，但不重新决定全局用户意图。
- **状态与协议层**保留 Java 为权威落库方，维持既有 SSE 对外契约，不因内部结构调整改变用户可见结果。

以上是**逻辑职责**，不要求每项都新建类、进程或服务。

### 0.3 所有阶段共同遵守的规则

1. **逐阶段授权**：每次只批准一个阶段；完成小块验收后才能进入下一步。T1–T3 以保留旧行为为原则；T4 允许经过审核的行为改善；T5 以基础设施稳定为原则。
2. **先看证据再定改法**：本文仅规定目标与方向。涉及真实代码边界、能力是否可用、跨服务契约时，先让 Coding Agent 给出最小必要证据，不由架构师凭空推断。
3. **保护已有工作**：改动前确认 Git 工作区、未提交内容、可回滚边界；不擅自提交、覆盖、删除其他工作的修改。每阶段形成独立可追溯变更。
4. **新旧行为分开评估**：T0 旧路由快照只证明可复现，不代表旧结果正确。结构改造应与快照一致；T4 修复旧错误必须依据审核后的 Gold Labels。
5. **不破坏权威系统**：不擅自改变 Java 数据所有权、会话/产物落库职责、前端协议和 SSE 终态规则。
6. **交付从简**：默认由 Coding Agent 在对话里给一段简短交接摘要，并在仓库保留一份阶段报告；仅当审查必要时额外上传一份关键数据或 diff。不要为每个子任务增加多个报告文件。

### 0.4 阶段衔接总览

| 阶段 | 性质 | 要解决的问题 | 验收后才解锁 |
|---|---|---|---|
| T0 · 已完成 | 只读基线 | 固定旧行为与 SSE 契约 | T1 |
| **T1 · 统一能力映射** | 结构改造 | 能力定义分散、重复维护 | T2 |
| **T2 · 拆分决策与计划** | 结构改造 | 谁理解意图、谁构造计划不清晰 | T3 |
| **T3 · 整理执行边界** | 结构改造 | Dispatcher、Center、Agent 职责交叉 | T4-A |
| **T4-A · 三态路由与语义判断** | 行为优化 | 规则无法理解隐式/上下文需求 | T4-B |
| **T4-B · 复合任务和上下文依赖** | 行为优化 | 多诉求遗漏、任务顺序与依赖混淆 | T4-C |
| **T4-C · 能力产物闭环** | 行为优化 | 命中意图却无法交付正确产物 | T5 |
| **T5 · SSE / Context / 跨域收口** | 结构改造 | 上下文、输出和跨域调用耦合 | FINAL |
| **FINAL · 集成、性能和灰度验收** | 最终验证 | 端到端正确、可用、可回滚 | 正式切换 |

## T1 · 统一能力映射（结构改造）

**目标**：建立统一的能力定义依据，使“用户意图—业务能力—具体动作—产物类型—执行者”的关系能被一致查询和解释，消除相同映射在多处各自维护的问题。

**执行步骤**

1. 以 T0 已冻结的旧映射为起点，核对所有已注册意图、实际执行能力与历史兼容关系；标出仅注册、仅能执行或产物未闭环的项目。
2. 明确四层概念的归属及多对多关系，不让“一个意图对应一个 Center”成为硬性约束。
3. 形成统一能力映射设计，并逐步让原有路由、计划、分发环节读取同一权威定义；必要的旧接口可暂时保留兼容。
4. 检查新增能力、变更执行者、调整产物类型时，哪些位置应维护、哪些位置只读；排除循环依赖或重复真源。
5. 对照 T0，确认本轮没有顺手改变用户路由、执行顺序或 SSE 行为。`flashcard_gen`、`adjust_plan` 等能力问题只记录，留待行为阶段裁决。

**小块验收 T1-Gate**

- 所有现存主要业务能力都有明确映射与负责人；意图、能力、动作、产物不再被混为同一个字段。
- 原来多处维护的**同一项映射**只剩一处权威来源，其他环节不再自行定义竞争版本。
- 旧版路由快照和代表性 SSE 契约与 T0 对齐；偏差必须解释，不允许静默接受。
- 交付一份简短说明：统一了什么、哪些能力尚未闭环、是否可以安全进入 T2。

**本阶段不做**：调整关键词、引入 LLM 路由、修复复合请求、重写专业 Agent。

## T2 · 拆分意图决策与执行计划（结构改造）

**目标**：确立唯一、清楚的责任链：意图识别产生 **RouteDecision**，计划构建产生 **ExecutionPlan**，执行前裁决决定“追问 / 确认 / 放行”。

**执行步骤**

1. 明确意图决策需要输出的信息：候选意图、必要参数、上下文关联、判定依据；区分规则评分与经过校准的概率。
2. 将“识别用户诉求”和“选择执行能力、排列任务、决定依赖”分为独立逻辑职责；统一执行计划的生成与校验归属。
3. 让计划能够分别表达**任务集合、执行顺序、数据依赖**；顺序在前不自动意味着结果必须传给下一任务。
4. 为追问、确认、放行明确唯一执行前裁决点；本轮先明确和连接契约，对已有用户交互保持兼容，改变追问时机或行为须另行批准。
5. 用旧路由案例检验职责迁移后的结果稳定性，并单独测试各契约可以被隔离验证。

**小块验收 T2-Gate**

- 意图判断组件不直接派发业务、不自行创建最终执行计划；计划构建不重新猜用户意图。
- 能够从明确的路由决策稳定形成可验证计划，包括单任务与多任务结构。
- 追问、确认状态有明确消费方，不再只有标记却不知道谁执行；行为变化项已被隔离。
- T0 路由快照与 SSE 核心行为保持兼容；现存错误保留到 T4 有计划地修复。

**本阶段不做**：用新模型替换旧判定算法、扩展 Agent 业务能力、改变持久化协议。

## T3 · 整理 Center / Agent 执行边界（结构改造）

**目标**：形成稳定的业务执行关系：Dispatcher 根据计划分发；Center 拥有本领域工作流；Agent 完成专业步骤，避免执行层重新解释全局意图。

**执行步骤**

1. 针对主要能力确认执行所有权：答疑、解题、练习、资源、计划、可视化、诊断、画像等分别由哪个业务域交付。
2. 将 Dispatcher 的职责限定在接收合法计划、调度任务、收集执行结果；不让它决定用户究竟想做什么。
3. 保留 AutoCenter 作为 `auto` 业务域内的执行分发者；允许它按**已确定的任务类型**选择 Agent，但不能擅自改变全局意图。
4. 明确 Center 与专业 Agent 的输入、输出、失败结果、可追踪信息的边界；优先兼容旧 Agent，不强制统一内部工作流的技术实现。
5. 对跨 Center 和 Agent 的直接调用列出保留、封装或后移清单；只有存在真实耦合问题时才改，避免为了形式整齐大范围调整。

**小块验收 T3-Gate**

- 任一执行任务都能清楚定位“谁调度、谁负责产物、谁处理失败”。
- 没有执行层擅自覆盖上游全局意图；域内 Agent 选择与全局路由的界限明确。
- 主要能力输出与原有 Java / SSE 契约兼容；关键工作流仍可独立执行。
- 不因拆层而增加不必要的调用环节或重复编排。

**本阶段不做**：强制合并/删除 Agent、全面重写跨域依赖、修改旧路由语义。

## T4-A · 三态路由与语义判断（行为优化）

**目标**：实现最初选定的混合方案：**明确普通聊天 / 明确专用能力 / 无法可靠判断**；只让第三种情况进入按需语义理解，避免所有请求额外调用一次 LLM。

**执行步骤**

1. 基于人工审核后的 Gold Labels 及真实对话边界，定义哪些表达可由高精度规则直通，哪些必须进入“不确定”。
2. 建立三态决策路径；特别禁止把“没有命中关键词”直接等同于“明确普通聊天”。
3. 对不确定请求使用可替换的语义判定能力，结合必要历史与产物上下文，输出结构化候选意图及参数，不让模型直接执行 Center。
4. 将语义结果交给 T2 的统一计划环节验证；无效结果、超时和模型不可用均进入明确的安全兜底，不可凭空生成高成本产物。
5. 先旁路对照新旧决策，再小范围开启新判断；记录路由来源、错误类别、额外时延和成本。

**小块验收 T4-A-Gate**

- 明确请求仍能走低延迟直通；语义模型仅在有价值的请求上触发。
- 隐式意图、多轮指代和否定表达等场景相对旧版确有改善，且普通答疑误触发没有不可接受的增加。
- 每次路由可解释“规则直通、语义判断还是兜底”，并能回溯版本和输入依据。
- 模型失败不会造成错乱执行；路由时延与费用处于**事先由产品方批准的预算**内。

**本阶段不做**：把全部路由交给 LLM、让语义模型直接修改画像/数据库、连带改写底层 SSE。

## T4-B · 复合任务与上下文依赖（行为优化）

**目标**：让系统完整处理用户在一句话或多轮中提出的多个诉求，准确区分**任务先后顺序**与**真正的数据依赖**。

**执行步骤**

1. 将“先讲解，再出题”“解完这题，再给类似练习”等明确复合表达识别为多个任务，避免静默丢弃第二诉求。
2. 在计划中尊重用户明确指定的执行顺序；没有明确顺序时按业务约束安全安排，不盲目使用固定中心优先级。
3. 仅当下游确实需要上游内容时，建立结果依赖；传递必要、结构化、可追踪的数据，不依靠无边界的长文本拼接。
4. 支持“再来五道”“把刚才的图改详细些”等跨轮指代，引用可用的历史、产物标识与当前上下文；证据不足时澄清。
5. 对执行中间失败、部分完成和用户确认情形，明确后续任务是继续、阻断还是询问，避免重复生成和错误复用。

**小块验收 T4-B-Gate**

- 单条复合请求的主要诉求不再被吞掉；执行顺序符合用户表达。
- 无依赖时任务可独立执行；有依赖时下游确实获得需要的上游结果。
- 多轮指代能找到正确对象；找不到时安全追问，不误改其他产物。
- 部分失败、追问、确认有一致结果，用户可以理解实际完成了哪些任务。

**本阶段不做**：引入复杂通用工作流平台、一次实现任意并行图、把所有历史全文交给每一个 Agent。

## T4-C · 能力产物闭环（行为优化）

**目标**：从“识别到意图”进一步走到“真正交付用户要的产物”，消除路由可达、执行可达、产物可用三者之间的断层。

**执行步骤**

1. 对主要能力建立“请求 → 所需动作 → 业务 Center → 预期产物 → 结果状态”的交付路径，并标记不足之处。
2. 优先核实并闭环：闪卡是否真的产生闪卡；计划调整是否针对已有计划；解答已有题目是否区别于新题生成。
3. 对诊断明确证据要求：有已有学习记录时如何诊断，缺乏依据时如何先测评或澄清；不凭空宣称掌握程度。
4. 对画像明确主任务与辅助更新的边界、用户授权与 Java 持久化归属；不能让背景自述直接覆盖用户真正的答疑需求。
5. 建立产物交付状态与失败反馈的一致语义，并通过业务场景检查从输入到交付的完整链路。

**小块验收 T4-C-Gate**

- 已对外宣称可用的核心能力，能够交付正确类型的实际产物，而不只是命中某个意图名。
- 对暂未完成的能力有明确产品状态，不误导用户为“已生成成功”。
- 计划、诊断、画像等涉及既有学习状态的功能，不越过授权、证据与落库边界。
- 各能力均能区分路由正确、执行成功、产物可用三种不同结果。

**本阶段不做**：以路由重构为由新增大量教育产品功能；对暂未授权的用户资料自动持久化。

---

## T5 · SSE / Context / 跨域收口（结构改造）

**目标**：在新路由与业务流程稳定后，收敛执行基础设施的剩余交叉职责，降低后续维护成本。

**执行步骤**

1. 明确统一上下文的入口、裁剪与作用范围；区分路由需要的简要上下文与业务 Agent 需要的专业上下文。
2. 将 SSE 事件契约及终态语义作为统一约束，减少 Dispatcher 中与业务正文合成混在一起的职责，但保证对外协议不变化。
3. 对跨 Center / Agent 的调用建立稳定契约和依赖边界，保留真正有价值的内部工作流，避免创建新一层机械代理。
4. 检查取消、超时、异常、重复结果、重复 done，以及多任务阶段性内容的输出一致性。
5. 与 Java 的消息、资源、计划、画像落库边界做接口核对，保持 Python 纯编排的既定责任。

**小块验收 T5-Gate**

- 路由上下文、业务上下文的获取和更新职责明确，没有明显重复构建或相互覆盖。
- SSE 主链路及终态契约与外部消费者兼容，消息可持续流式接收，不丢最终状态。
- 跨域调用具备可解释的输入输出与失败边界，避免隐式循环依赖。
- 若某项清理风险大且收益有限，可以标记延期，不阻塞已稳定的新路由上线。

**本阶段不做**：重写 Java 数据层、无差别消灭所有跨域调用、为了拆分而拆分。

## FINAL · 集成、性能和灰度验收

**目标**：从“单阶段通过”升级为“真实产品可稳定使用”，确认用户体验、业务正确性、成本、数据安全、上线回滚都达标。

**执行步骤**

1. **架构总验收**：回看统一能力映射、决策/计划分离、执行责任边界。确认原本发现的重复定义与越权决策已得到处理。
2. **路由语义总验收**：使用已人工确认的 Gold Labels，对比旧路由与新路由；按明确产物、普通答疑、否定、复合任务、多轮指代、需要澄清分别分析误触发与漏判。140 条合成案例不能替代真实对话验证，应在授权条件下补充脱敏样本。
3. **跨服务真实链路验收**：覆盖主要能力从 Vue 发起、Java 会话及上下文准备、Python 路由和 Agent 执行、SSE 返回、Java 落库与前端展示的闭环。测试替身通过不能替代真实集成测试。
4. **稳定性与安全验收**：覆盖异常、超时、取消、重试、重复请求、确认未完成、部分产物失败，以及画像/计划更新的授权与一致性。
5. **性能与费用验收**：对比首个有效 SSE 事件时间、路由 p95、按需语义调用比例、模型成本、失败回退；具体预算在上线评审前明确，不在本文虚构阈值。
6. **灰度与回滚验收**：先旁路观测，再小范围启用，再扩大；保留返回旧路由的可控开关。发现明显误触发、产物错误、SSE 或持久化异常时立即回退并留存证据。
7. **完成签收**：汇总已解决问题、保留的历史限制、延期优化事项、风险和下一轮维护责任，最终由产品决策者批准切换。

**最终验收 FINAL-Gate**

- **正确性**：用户主要诉求得到正确路由，明确多任务不漏执行，产物种类与请求一致。
- **稳定性**：核心业务完整闭环；SSE、Java 落库及前端展示没有不可接受的回归。
- **性能成本**：满足上线前批准的热路径延迟与模型费用预算。
- **可控性**：审计可追溯、策略可回滚、灰度结果有对照证据。
- **范围说明**：清楚注明已上线能力、未上线能力和已知限制，避免把待完善能力标成已完成。
