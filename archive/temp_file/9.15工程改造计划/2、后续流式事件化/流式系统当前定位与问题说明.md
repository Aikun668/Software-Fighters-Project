# 流式系统当前定位与问题说明（宏观版）

> 说明：本文**没有基于完整源代码逐行审计**，仅根据目前已确认的调用链、现象与设计描述，做宏观层面的客观归纳。因此它用于统一问题认识、确定后续方向；具体类、方法、节点及改动范围仍应在阅读代码后确认。

## 1. 当前现象

用户发起聊天后，底层 LLM 虽已能够持续产出 chunk/token，但前端通常要等模型完整回答生成完，才一次性看到整段文本，而不是逐字/逐段出现。

已知调用链大致可概括为：

```text
LLM.chat_stream()
  → TutorAgent：循环接收 chunk 并拼成完整 response
  → BaseAgent / LangGraph：等待图执行完成并返回最终 state
  → AutoCenter：等待 Agent 完整结果并封装 CenterResult
  → ResultAgent：等待任务完整结束后再 yield
  → SSE / 前端
```

关键事实不是“底层没有流式能力”，而是：**流在中间层被聚合成完整字符串，后续链路主要只认识最终结果。**

## 2. 核心问题的宏观判断

### 2.1 真正的断点：系统抽象仍是“函数 → 结果”

当前主链路的接口语义更接近：

```text
输入 → 等待执行完成 → 返回最终 Result / State
```

这类结果型（Result-oriented）抽象适合最终答案、状态持久化、质量检查和业务编排；但它无法天然表达：

```text
任务尚未结束，但现在先产生一小段文本 / 一个工具进度 / 一个节点状态。
```

所以问题不是简单某一层漏写了 `yield`。只要中间某层先把 chunk 聚合为 string，再向外 `return` 完整结果，token 的时间顺序就已经丢失，后面无法“重新恢复”为真实 token 流。

### 2.2 当前 callback + Queue + SSE 修法的性质

现有修法大意是：在 Agent 消费 `chat_stream()` 时，一边继续把 chunk 拼成完整答案，保证原有 sanity check、最终状态与后续业务不变；另一边通过 callback/queue 把同一份 chunk 实时送到 SSE 与前端。

```text
一次 LLM generation
       ├─ chunk → 完整 response → 原业务链路
       └─ chunk → Queue / SSE → 前端
```

这是合理的**过渡方案**，不是错误方案。它以较小改动恢复了聊天体验，并且坚持“只调用一次 `chat_stream()`”是必要约束：二次生成不只是浪费 token，还会导致前端看到的答案与后台检查、保存的答案不同，产生状态分裂。

但它的本质是：**在结果型架构外补出一条 token 旁路。** 它能解决 Demo 或单一聊天链路的流式展示，却还没有把 streaming 变成系统的原生能力。

### 2.3 `ResultAgent` 的 yield 不等于 token streaming

如果它是在 `await _execute_task()` 获得完整结果后再 `yield result`，那么它流出的单位是“完整任务结果”，不是 token。它属于任务级流式（task-level streaming），不能替代聊天所需的 token/事件级流式。

## 3. 当前所处阶段与定位（重点）

可以将 AI Agent 的流式成熟度粗略划为五级：

| 阶段 | 定义 | 当前状态 |
|---|---|---|
| L0 | 完全非流式：等待完整回答 | 已跨过 |
| L1 | LLM SDK 能逐 chunk 输出 | 已跨过 |
| **L2** | 用 callback / Queue / SSE 将 token 旁路推到前端 | **当前所在阶段** |
| L3 | 统一事件流：文本、工具、节点、状态、错误均可被表达与消费 | 下一阶段 |
| L4/L5 | Agent-native Runtime 与生产保障：取消、重连、背压、追踪、持久化、分布式等 | 中长期 |

因此，当前系统的定位应是：

> **已经具备 LLM 级与体验补偿级流式能力，正处于从“结果型多 Agent 系统”向“事件驱动 Agent 执行系统”迁移的起点。**

这个定位很重要：现在不应因追求“企业级”而贸然引入 Kafka、Redis Streams、微服务或复杂 EventBus；也不该把 callback 方案当作最终架构。眼下最有价值的升级，是先让系统内部拥有一致的事件表达。

## 4. 为什么要把 LangGraph streaming 用起来，而不是绕开它（重点）

当前如果主要通过 TutorAgent 自己开 callback 旁路拿 token，Graph 对外仍然是：

```text
graph.ainvoke(input) → 等整个图结束 → final state
```

这意味着：Graph 仍被当作一个黑盒函数，外部只能知道最终结果，难以自然看到“检索开始/结束、回答节点开始、模型正在输出、工具调用完成、状态已更新”等过程。

LangGraph 原生的流式执行能力（例如 `astream` 及其相关事件/状态流能力）提供的方向是：

```text
Graph 执行中
  → 节点执行事件
  → 状态更新事件
  → 模型输出事件
  → 工具调用事件
  → 完成 / 错误事件
```

这里的价值不在于把 `ainvoke` 机械替换成 `astream`，而在于让 **Graph 本身可被观察、可被持续消费**。这样可逐步形成：

```text
LangGraph execution stream
  → 统一 StreamEvent
  → 前端 SSE、结果聚合、日志/追踪等多个消费者
```

相比 Agent 私有 callback，这种方向更符合项目未来的多 Agent 目标：

- Agent 不需要知道“前端是否在线”，只负责报告发生了什么；
- token 不再是唯一可流出的内容，工具、检索、节点进度、重试、错误也可以统一呈现；
- 最终 `CenterResult` 仍然保留，但它变成事件被聚合后的最终结果，而不是唯一的系统语言；
- 后续增加 Planner、Retriever、Reviewer 等角色时，不会把各处回调参数堆成难维护的 callback hell。

## 5. 当前阶段需要明确的边界

1. **流式先发、完整校验后做存在天然取舍。** 如果完整 sanity check 失败时“绝不能让用户看原文”，就不能无缓冲地实时推全部 token；需要后续选择小缓冲、句子级/片段级守卫，或把 sanity 定位为生成后的记录与重试机制。
2. **SSE 不是当前主要矛盾。** 聊天场景中 SSE 仍然合适；是否换 WebSocket 是以后有实时中断、暂停、双向控制、语音等需求时再评估的传输层问题。
3. **不要追求一步到位的企业基础设施。** 现在应先建立 Event Model 和稳定的单链路流式语义；复杂消息队列、分布式执行等应在真实并发、重连、可观测性需求出现后再引入。

## 6. 一句话结论

当前不是“流式功能没有修好”，而是：

> **已经用旁路完成了 L2 级体验修复；下一步应以 LangGraph 原生 streaming 为核心，把系统从“最终结果驱动”逐步升级为“执行事件驱动”。**
