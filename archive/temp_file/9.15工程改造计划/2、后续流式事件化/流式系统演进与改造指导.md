# 流式系统演进与改造指导（宏观版）

> 说明：本文给出架构演进方向与决策原则，不规定具体类名、接口签名、LangGraph 参数或代码实现。实际落地前需以现有代码、LangGraph 版本、前后端协议和测试结果为准。

## 1. 改造目标

目标不是“让文字一个个出现”本身，而是让一次 Agent 请求可以被描述为一段持续发生的执行过程：

```text
执行开始
→ Agent / 节点开始
→ 检索或工具执行
→ 文本增量输出
→ 状态更新
→ 质量检查 / 重试（如有）
→ 执行完成或失败
```

最终结果仍然需要保留，用于存储、回放、评估与后续业务；但它应由执行过程中的事件汇总而来，而不再是唯一对外语义。

## 2. 总体原则

### 2.1 先统一事件，再扩展基础设施

优先把 `on_token(chunk)` 的单一语义，升级为统一的 `emit(event)` 思维。这里不要求立即做复杂 EventBus，而是先确立一种稳定、可扩展的事件结构。

建议概念上至少能表达：

```text
run.started / run.completed
agent.started / agent.completed
node.started / node.completed
message.delta
tool.started / tool.progress / tool.completed
state.updated
error / retry
```

每个事件应在概念上具备 `run_id`、递增序号、事件类型、发生时间、数据载荷等基础信息。这样以后才能支持前端排序、日志关联、去重、追踪和重连恢复。

### 2.2 只生成一次，多个消费者复用同一事件源

对于一次 LLM generation，模型 chunk 必须只来自一次 `chat_stream()` 调用：

```text
同一 chunk source
  ├─ 前端消费者：展示 message.delta
  ├─ Collector：聚合完整 response / final state
  ├─ 校验与记录消费者：质量、日志、指标
  └─ 追踪消费者：节点与耗时
```

不要为“前端流式”和“后台最终答案”各发一次模型请求。一次生成、多方消费，是保证成本、顺序和状态一致性的基本原则。

### 2.3 Transport 与 Event Model 分开

SSE 只是把事件推到浏览器的一种方式，不应成为 Agent 或 Graph 内部逻辑的一部分。

```text
Agent / LangGraph → StreamEvent → SSE adapter → Frontend
```

以后即使替换为 WebSocket、命令行输出、日志、评测回放，也应消费同一种事件，而不是重写 Agent。

## 3. 推荐演进路线

### 阶段 A：稳定当前 L2 方案

保留 callback + Queue + SSE 作为短期兼容层，重点确认：

- 一次请求只生成一次模型流；
- token 顺序稳定，完成、异常、取消均能正确收尾；
- 队列不能无限堆积；
- 前端清楚区分“生成中、完成、失败”；
- 完整答案与前端展示内容可对账。

这一阶段的目标是：**可靠地修好单聊天链路，而不是扩张能力。**

### 阶段 B：定义最小统一 `StreamEvent`

将 `on_token` 抽象为“发出事件”，先从最少几类开始：运行开始、文本增量、节点/Agent 开始结束、错误、运行完成。

同时保留一个 Collector，将 `message.delta` 聚合回当前系统仍需要的完整 response、`CenterResult` 或最终 state。这样可以避免大面积重写既有业务。

```text
事件流 → Collector / Reducer → Final Result
```

这一阶段完成后，系统从“主路 + 特殊 token 旁路”开始变为“一个事件源 + 多个消费者”。

### 阶段 C：接入 LangGraph 原生 streaming

这是下一次真正的架构升级重点。

先调研并以最小实验验证当前 LangGraph 版本能提供哪些流：节点更新、状态更新、LLM token、工具调用、子图或自定义事件。然后选择能覆盖项目需求的流模式，让图执行本身向外产生事件，而不是只在 TutorAgent 内部私自开洞。

迁移时应遵循：

1. 先选择一条最稳定、最简单的聊天链路做试点；
2. 保持 `ainvoke` 的旧路径作为非流式兼容/回退；
3. 将 Graph 流转换为内部统一 `StreamEvent`，避免前端直接依赖 LangGraph 的事件格式；
4. 验证 token、节点、状态事件与最终结果的一致性；
5. 再逐步扩展到检索、工具与更多 Agent。

这样使用 LangGraph streaming 的目的不是“框架炫技”，而是让 Graph 成为一个可观测的执行运行时。

### 阶段 D：Agent execution stream

当多 Agent 逐渐接入后，前端和日志系统应能消费完整执行过程：

```text
Router 识别请求
→ Retriever 检索
→ Tutor 组织回答
→ Reviewer 检查
→ 必要时重试
→ 完成
```

用户侧并不需要暴露全部内部思考，但可以展示可信、简洁的进度，例如“正在检索课程资料”“正在组织解释”。系统侧则应保留更细的事件用于调试和观测。

### 阶段 E：按真实需求补齐生产能力

以下能力暂不应抢跑，但应预留事件语义：

| 能力 | 解决的问题 |
|---|---|
| 取消（cancel） | 用户停止后，后台真正中断 Agent/模型，避免继续烧钱 |
| 背压（backpressure） | 生产速度快于网络/前端消费速度时，防止队列无限增长 |
| 断线重连与恢复 | 网络中断后可按 run_id/seq 续接或明确告知无法续接 |
| 幂等与去重 | 重连后不重复渲染已收到的事件 |
| 可观测性 | 能定位一次请求卡在 Router、检索、LLM、工具还是检查阶段 |
| 持久化与回放 | 能复盘一次执行过程、排查异常、做效果评估 |

只有在用户量、任务时长、并发或实际线上故障提出需求时，再评估 Redis Streams、消息队列、任务执行器或更复杂的分布式架构。

## 4. 校验与流式的处理原则

完整答案生成后才进行的 sanity check，无法撤回已经实时发送给用户的 token。因此必须先产品化地明确它的角色：

- 若 sanity 仅用于记录、评分、提示或决定下一轮重试：实时流式可继续；
- 若 sanity 是“未通过就绝不能展示”的硬门禁：不能无缓冲直出，需要小缓冲、片段/句子级安全检查，或先生成后展示；
- 不要把“流式展示”和“最终质量控制”误当成没有取舍的同一件事。

## 5. 当前不建议做的事

- 不要为了“企业级”立刻上 Kafka、Redis Streams、微服务或分布式 EventBus；
- 不要立刻把全项目所有 `run()` 改成 async generator；
- 不要让前端直接绑定框架内部事件格式；
- 不要只盯 WebSocket；SSE 在当前单向聊天流式里依然合适；
- 不要把模型的隐性推理过程直接暴露为用户进度。

## 6. 建议的近期验收标准

在进入下一阶段前，至少确认：

1. 首个可见文本到达时间（TTFT）明显降低；
2. token/chunk 的前端顺序稳定，结束事件与错误事件不混乱；
3. 前端最终文本与后台收集到的完整文本一致；
4. 用户取消、网络断开、模型异常时任务能收尾，不遗留无限等待；
5. 一次请求能够追溯到统一的 `run_id`，并知道各关键节点的大致耗时；
6. 非流式旧路径仍可作为安全回退，直到新路径稳定。

## 7. 一句话路线

> **先用旁路把体验救回来；再用统一 Event Model 把语义立起来；随后接入 LangGraph 原生 streaming，让 Graph 自己成为事件源；最后再按真实规模补取消、重连、背压与观测。**
