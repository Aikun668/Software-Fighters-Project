# 练习域收口实施方案

> **用途**：计划域、资源域、聊天域收口完成后，处理练习域（出题、解题、批改、错因分析、练习分析）的编排边界。本方案用于锁定范围、唯一入口、兼容红线和验收条件；经用户确认后方可开始改代码。

**目标：** 在不改变 `/exercise/*`、`/solve`、`/evaluation/report` 对外请求/响应契约（含 SSE 事件字节形状与 Java 消费字段）的前提下，让 `ExerciseCenter` 成为练习域唯一业务入口，API 收窄为协议适配。

**推荐架构：** API 只做请求校验、调用一个业务 Center、SSE 序列化与 HTTP 响应；`ExerciseCenter` 负责出题、解题、错因分析、批改与分析类业务的入口与编排；专用 Agent 与 Service 保持现状。

**技术栈：** Python、FastAPI、asyncio、现有 `StreamEvent`、`ExerciseCenter`、`ExerciseAgent`、`SolveAgent`、各练习 Service、pytest。

**方向约束：**
- [产品主线与业务编排约束.md](../../0、产品方向与约束/产品主线与业务编排约束.md)（练习评估 = 出题、解题、批改、错因分析 → `ExerciseCenter`）

## 一、这次要解决什么

练习域目前有 10 个对外端点，其中 4 类旁路直接违反指导文件：

| 违反类型 | 端点 | 现状 |
| --- | --- | --- |
| API 直连 Agent + 手写 SSE | `/exercise/generate` | 路由内 `_get_exercise_agent()` + 手写 progress/done/error 编排 |
| API 直连 Agent + 手写 SSE | `/solve` | 路由内 `_get_solve_agent()` + 手写 steps/token/confidence/done 编排 |
| API 内含完整业务逻辑 | `/exercise/error-analysis` | 路由内加载 prompt、拼模板、调 `llm.chat()`、解析 JSON |
| API 内构造 Agent + 业务文案 | `/plans/{plan_id}/complete-step` | 路由内直接实例化 `ExerciseAgent` 并 run，组装推荐动作与文案 |

另 6 个端点为"API 直调一个 Service"的薄透传（grade / evaluation-report / categorize / session-analyze / dashboard / profile-enrich），没有跨层编排，但按"每域唯一入口"原则仍应经 `ExerciseCenter` 转发。

**核心判断**：`/exercise/generate` 与 `/solve` 的业务编排（发什么阶段事件、什么文案、什么终态）在两个路由函数里各手写一份，这正是 ISSUES 问题一"业务编排入口不唯一"在练习域的表现。

### 当前调用链

```text
/exercise/generate
  → internal_api.exercise_generate()
  → _get_exercise_agent().run(...)
  → API 手写 progress(plan) → progress(generate) → done(questions)

/solve
  → internal_api.solve_question()
  → _get_solve_agent().run(...)
  → API 手写 steps → token* → confidence → done
```

### 迁移后调用链

```text
/exercise/generate
  → API 校验
  → _get_exercise_center().generate_stream(...)
      → ExerciseAgent.run(...)
      → yield StreamEvent（progress / done）
  → event.to_sse()（协议序列化，含本题型字节兼容规则）

/solve
  → API 校验
  → _get_exercise_center().solve_stream(...)
      → SolveAgent.run(...)
      → yield StreamEvent（steps / token / confidence / done）
  → event.to_sse()
```

## 三、兼容红线（先于技术方案，最高优先级）

真实消费方调查结论：

- **Java 是唯一消费方**：`PythonClient.createSseEmitter()` 逐事件透传给前端，并对 `done` 事件调用 `onDone` 回调。
- **前端未接这两个端点**：`frontend/src/api/exercise.ts` 定义了 `generateExercise` 但无组件消费，无 `/solve` 引用。（仍按"前端已消费"的标准对待，不拿"前端没接"当随便改的理由。）
- **Java 读 done 顶层字段**：`ExerciseController.saveExercisesToDb()` 读 `doneData.get("questions")` 与 `doneData.get("topic")` —— questions 必须在 done 事件**顶层**，不能在 `data` 嵌套里。

必须保持的字节形状（收口前后逐字节一致）：

**`/exercise/generate` 成功路径**

```json
{"type": "progress", "stage": "plan", "content": "正在规划「{topic}」的练习题..."}
{"type": "progress", "stage": "generate", "content": "已生成 {n} 道题目"}
{"type": "done", "questions": [...]}
```

**`/exercise/generate` 失败路径**

```json
{"type": "error", "content": "题目生成失败，请稍后重试"}
{"type": "done"}
```

**`/solve` 成功路径**（Java 注释：steps → token → confidence → done）

```json
{"type": "steps", "content": [...]}
{"type": "token", "content": "..."}          // 多次，4 字一片
{"type": "confidence", "score": 0.9}
{"type": "done"}
```

**`/solve` 失败路径**

```json
{"type": "error", "content": "解题功能暂时不可用，请稍后重试"}
{"type": "done"}
```

**两条失败路径的形状不同，必须分别保持**：

- `/exercise/generate`：现状先发 `progress(plan)` 再调 agent，agent 失败时消费方看到的是
  `progress(plan)` → `error` → `done`（三段）。
- `/solve`：现状先调 agent，失败时没有前置事件，只有 `error` → `done`（两段）。

**`/plans/{plan_id}/complete-step`**（JSON，保持现有响应字段）
`step_order` / `step_completed` / `recommended_action` / `questions` / `message`。

## 五、技术方案

### 5.1 事件序列化（`app/events/types.py`）

现状缺口：`steps` / `confidence` 不是 `StreamEventType` 成员；exercise 的 `progress` 用 `content` 键，而标准 `progress_event` 输出 `message` 键；exercise 的 `done` 需要顶层 `questions`（标准 `done_event` 输出 `data` 嵌套）。

方案：扩展 `events/types.py`，**只新增，不改动现有类型的现有输出**（聊天域、资源域行为零影响）。

1. 新增类型：`StreamEventType.STEPS = "steps"`、`StreamEventType.CONFIDENCE = "confidence"`。
2. 新增工厂：
   - `steps_event(steps: list) -> StreamEvent`（`data=steps`）
   - `confidence_event(score: float) -> StreamEvent`
   - `progress_content_event(stage, content)`：`PROGRESS` + `data={"content": ...}`，供练习域 progress 保持 `content` 键
   - 顶层字段平铺：为上述三类事件的 `data` 在 `to_sse()` 中平铺到 payload（与 TOKEN 平铺同一模式），使输出与兼容红线逐字节一致。
3. `to_sse()` 新增规则（互不影响现有分支）：
   - `STEPS` → `payload["content"] = self.data`
   - `CONFIDENCE`、练习域 `PROGRESS`（`data` 含 `content`）→ 平铺 `data` 键到顶层
   - `DONE` 需要顶层平铺时，使用专用工厂 `flat_done_event(data)`（打平 data 到顶层），不改标准 `done_event`

**验收方法**：新增字节对照测试 —— 对同一事件序列断言 `to_sse()` 输出与兼容红线中的 JSON 逐字节一致。

### 5.2 `ExerciseCenter` 新增方法

```python
class ExerciseCenter:
    async def execute(self, task: CenterTask) -> CenterResult: ...   # 现有，保持

    async def generate_stream(
        self, *, topic: str, knowledge_node_id: str | None, strategy: str,
        count: int, difficulty: str, student_profile: dict,
    ) -> AsyncIterator[StreamEvent]: ...
        # progress(plan) → ExerciseAgent.run → progress(generate, n) → flat done(questions)
        # 异常 → error(content) + flat done（无 payload，与现状一致）

    async def solve_stream(
        self, *, question: str, context: str,
    ) -> AsyncIterator[StreamEvent]: ...
        # SolveAgent.run → steps → token*(4 字分片, 0.03s) → confidence → done
        # 异常 → error + done

    async def analyze_errors(self, *, errors: list, level: str) -> dict: ...
        # 迁移 API 内的 prompt 加载/模板插值/sanitize/llm.chat/parse_llm_json

    async def grade(self, *, question_type: str, user_answer: str | None,
                    correct_answer: str | None = None, choices: list | None = None,
                    multi: bool = False, points: int = 1,
                    reference_answer: str = "", rubric: str = "") -> dict: ...
    async def evaluation_report(self, *, evaluation_results: dict) -> dict: ...
    async def categorize(self, *, exercises: list, knowledge_nodes: list, course_id: str) -> dict: ...
    async def analyze_session(self, *, records: list, masteries: dict, course_id: str) -> dict: ...
    async def dashboard(self, *, user_id, masteries: dict, recent_records: list, course_id: str) -> dict: ...
    async def enrich_profile(self, *, user_id, student_profile: dict,
                             recent_records: list, session_analysis: dict) -> dict: ...

    async def generate_consolidation(
        self, *, topic: str, knowledge_node_id: str | None,
        is_near_end: bool,
    ) -> dict: ...
        # complete-step 的题目生成：purpose=consolidation、review 策略、count 2/3
```

依赖可注入（离线测试用）：`exercise_agent`、`solve_agent`、`llm_service`；节流参数可覆盖：
`plan_progress_delay`（默认 0.3s）、`generate_progress_delay`（默认 0.5s）、`token_delay`（默认 0.03s）、
`chunk_size`（默认 4）。未注入时保持现有惰性默认构造。

### 5.3 `internal_api.py` 收窄

- 新增 `_get_exercise_center()` 惰性单例工厂（示例：`ExerciseAgent(use_mock_llm=...)` + `SolveAgent(use_mock_llm=...)`）。
- 10 个端点收窄为"校验 → 调用 Center → 序列化"：

```python
@router.post("/exercise/generate")
async def exercise_generate(body: ExerciseGenRequest):
    body = sanitize_model(body)
    if not body.topic.strip() and not body.knowledge_node_id:
        return api_error(ErrorCode.INVALID_REQUEST, "topic 和 knowledge_node_id 至少提供一个", status_code=400)
    center = _get_exercise_center()

    async def event_stream():
        async for event in center.generate_stream(...):
            yield event.to_sse()

    return StreamingResponse(sse_heartbeat_generator(event_stream()), media_type="text/event-stream")
```

- 删除 API 内的：`_sse_stream_chunks` 的 solve 调用点、error-analysis 的 prompt/LLM 代码、complete-step 的 `ExerciseAgent` 构造。
- `_sse_stream_chunks` 若收口后无调用方则删除（`/tutor/chat` 仍在用，须搜索确认后决定）。
