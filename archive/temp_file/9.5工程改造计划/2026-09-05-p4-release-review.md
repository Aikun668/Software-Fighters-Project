## 3. HOLD 的三个精确原因与回指

### 3.1 能力产物不以 content 形态流出（主阻塞，回 **Task 2/3**）

诊断（cap-05 实测事件流）：plan 中心**有** content 事件，但 payload 形状为
`{type, title, topic, total_steps, steps, milestones, estimated_days, daily_capacity}`——
没有 `response`/`content` 键。前端 `chat.ts` 的 content 处理器与 `internal_api` 的正文累积
都只认 `response/content` → **用户在统一聊天里看到空回答**（cap-01/05/06，3 条，触发一票否决）。

→ 回 **Task 2**（前端 content 渲染需识别产物形状）与 **Task 3**（SSE 合同需定义产物事件的用户可读摘要字段）。修复后此三项即可转绿。

### 3.2 gate→router 交接缺口（回 **Task 4**）

cap-02：CapabilityGate 判定 VISUALIZATION（一级正确），但二级关键词路由未产出 visualization 任务、
回落 auto/tutor（orchestration_not_entered 1/8）。tutor 实际给出了带 mermaid 图的合格回答，但编排未按判定进入。

→ 回 **Task 4**：CapabilityDecision 应约束 RouterAgent 的中心选择（kind 一致性检查）。

### 3.3 内部核查提示文本泄漏（回 TutorAgent 回答路径，建议列为解冻前置清理项）

**15/60（29%）**条普通回答尾部拼接了知识核查管线的内部文本：
"内容核查提示：超过50%的内容未在教材中找到对应验证…以下内容置信度较低，仅供参考：…"（并复述正文句子）。
不属于 Task 8 的高置信机械检查范围，但属于用户可见的内部机制文本——解冻前应清理：
要么不再拼进回答正文，要么转为前端独立 UI 元素。

### 附：生产配置缺陷（评审中连带发现，与门禁无关但必须修）

`.env` 将聊天通道配为 `deepseek-v4-flash`——DeepSeek 官方 API 上这是**思考模型**
（reasoning_content 先行、content 常为空），而 `llm_service` 不读 reasoning_content →
**生产聊天链路存在空回答风险**（本轮冒烟实测 36 秒后空响应）。
本次评测以非思考别名 `deepseek-chat` 覆盖（运行器内置评测域覆盖，未改 `.env`；设 `EVAL_RESPECT_LLM_ENV=1` 可还原）。
建议：生产 `.env` 改用 `deepseek-chat`（或为思考模型增加 reasoning_content 处理），另行小步修复。
