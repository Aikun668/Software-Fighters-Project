# Haiku Relay｜总督—游击 Worker（v1）

目标：在 Claude Code + Haiku 的短上下文经济区间内持续开发。**对话可丢，代码、决策和任务状态必须留在仓库。**

## 0. 安装（在现有项目根目录）

把压缩包内的 `.claude/` 和 `relay/` 两个目录复制到**项目根目录**，保留现有的 `CLAUDE.md`、`.claude/settings.json`，不要覆盖它们。需要 Git + Python 3.9+ + Claude Code。

```bash
python3 relay/relay.py check
claude --model haiku
```

> Windows + WSL 也可以直接使用。`haiku` 是 CLI 模型别名；进入 Claude Code 后用 `/model` 核对实际模型是不是你购买的 Haiku 5.5。如果 API 中转站自定义了模型别名，按服务商要求选择，不要盲信名字。

## 1. 开工（双终端，串行 Worker）

**终端 A：总督**
```text
/g-governor 请梳理当前项目，给出下一批任务包，不要编码。
```

**终端 B：Worker**（先由总督建立并填好 `relay/tasks/T001.md`）
```text
/g-worker T001
```

Worker 完成后写 `relay/reports/T001.md`；总督检查 Git diff / 测试并决策是否验收、返工或补派任务。然后在 Worker 窗口执行：
```text
/clear
/g-worker T002
```

也可通过独立终端快速启动：
```bash
python3 relay/relay.py governor "本次需求：修复登录状态丢失"
python3 relay/relay.py worker T001
```

**严禁同时让多个 Worker 修改同一工作树。** v1 按顺序执行；确需并行，先由人工建立独立 Git worktree 并确认分支、路径隔离，另行管理合并。

## 2. 预算：上下文余额不是任务回合数

| 阶段 | 参考单次请求上下文占用 | 动作 |
|---|---:|---|
| 开局 | ~5–15K | 装载任务包、定位 1–3 个核心模块；不要全文扫描 |
| 正常执行 | 15–70K | 连续实现一个完整可验收的闭环 |
| 黄色 | ≥80K | 不开新子目标，优先跑测试、整理报告 |
| 红色 | ≥90K | 停止新增代码修改，写交接后 `/clear` |
| 越界 | ≥100K | 当次请求**已可能**触发高费率；仅允许必要的交接，最多 3 轮，绝不把这当正常策略 |

以上是**人工操作阈值**，不是已安装的技术强制限流。用 `/context` 观察，首次实现到一半、读大量文件后、接近结束时再次查看。界面上下文占用与 API 计费的输入 token（可能含缓存读取/写入）未必完全一致，须留余量。**不要为了凑满 80K 刻意延长任务**。

**总督退休规则**：总督不碰业务实现；上下文接近 60–70K，或做完约 5–8 次任务验收，执行 `/g-retire`，写好 `relay/state/GOVERNOR_WILL.md`，然后 `/clear`，再 `/g-governor 继任`。项目状态始终落盘。

## 3. 任务怎么切才划算

以「**一个可独立验收的功能闭环**」为基本单位，而不是一个函数 / 一个文件。总督必须同时比较：

- **重建成本**：新窗口重新理解代码需要多少上下文；同一个模块的相邻小改动可以合并。
- **膨胀风险**：跨 3 个以上领域（例如 UI、认证、部署、数据迁移）通常拆开；超长日志和大文件不要整段读。
- **依赖关系**：前一项的接口/行为尚未稳定，不要并行下游任务。
- **验收成本**：每包必须能给出明确测试/观察标准；一次任务预计超过 ~70–80K 峰值就先拆。

建议任务：常规 **35–70K 峰值**，可低可高；极小任务若同一模块、同一验收链路，聚合 2–4 项；如果复杂性不可预估，先做一个小的只读定位任务，**不要靠无限探索撞到 100K**。

## 4. 谁更新哪些文件

| 文件 | 用途 | 维护者 |
|---|---|---|
| `relay/state/PROJECT.md` | 项目地图/命令/长期约束 | 总督 |
| `relay/state/QUEUE.md` | 排序、阻塞、正在执行 | 总督 |
| `relay/state/DECISIONS.md` | 已确定的架构决策（短句） | 总督 |
| `relay/state/GOVERNOR_WILL.md` | 总督遗书，继任入口 | 总督 |
| `relay/tasks/Txxx.md` | 目标、边界、上下文入口、验收、预算 | 总督 |
| `relay/reports/Txxx.md` | 改动、测试证据、遗留风险 | Worker |

真相优先级：**Git 代码与测试结果 > 当前任务单 > 项目状态文档 > Agent 口头描述**。每份文档尽量短；过期状态及时替换，不堆会话日志。任何人不得把密钥/个人数据写进交接文件。

## 5. 新建任务 / 检查

```bash
python3 relay/relay.py new T001 "修复 SSE 流中断"
python3 relay/relay.py status
python3 relay/relay.py check
```

`new` 只生成待填任务单，不会自动规划。总督必须填好**允许修改的范围、现有入口、验收命令/预期、依赖、停止条件**后才可派发；状态值使用 `planned / doing / review / done / blocked`。Worker 不自动 Git commit，提交或合并由总督/人工在验收后处理。

## 6. 持久化原则

- 代码修改必须真实写到磁盘；清理会话前确认 `git status` 和报告存在。
- Worker 允许任务未完成提前撤退，但必须报告哪一步完成、下一步最短路径、现有未提交变更。
- 总督每次重要决策就更新 `DECISIONS.md` / `QUEUE.md`；退休时**覆盖更新遗书**，不复制几千行聊天记录。
- 已存在的工作区改动属于用户资产；禁止 `git reset --hard`、`git clean -fd`、强推等破坏性操作，除非用户逐项明确批准。
- 不自动启用繁重 MCP/大量 Skills；这些可能让每轮输入上下文膨胀。

## 7. 可用命令

- `/g-governor <新目标 / 继任>`：总督进岗、分析、派任务、验收。
- `/g-worker T001`：Worker 领取单个任务并实现。
- `/g-retire`：总督更新遗书并交班。
- `/context`：官方的上下文可视化。
- `/clear`：清空当前对话（不会撤销磁盘文件和 Git 修改）。

这里的额度控制**尚不是 API 级限流**，也不会替你发起 `/clear`；这是需要用户配合的安全流程。
